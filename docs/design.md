# wn-server design

wn-server is a headless music server. It scans a local music collection into SQLite and serves it to OpenSubsonic clients on the local network. It is one Rust binary with CLI subcommands and a TOML config file. This document describes the present design. A change to designed behaviour updates this document in the same PR.

## 1. Scope

### 1.1 Features

- One binary, `wn-server`, with subcommands `init`, `run`, `scan`, `user`, `config`.
- TOML config file in a data directory. No web UI.
- SQLite library database built by a scanner over configured music folders. Scans are incremental; moved and renamed files keep their identity.
- Tag reading with `lofty` for FLAC, MP3, M4A (AAC and ALAC), Ogg Vorbis, Opus, WAV and AIFF.
- OpenSubsonic-compatible HTTP API under `/rest/`, JSON and XML, Subsonic protocol version `1.16.1`, `openSubsonic: true`, extensions `formPost` and `transcodeOffset` (version 1).
- Auth: username and password (plain `p`, `enc:` hex, and `t`+`s` MD5 token). One owner account. `[auth] disabled_unsafe = true` turns auth off.
- Streaming of the original file with HTTP Range support. ffmpeg transcoding to Opus or MP3 when the client sends `format` or `maxBitRate`. `timeOffset` seeks inside a transcoded stream.
- Cover art from album-folder image files or embedded pictures, resized on request, cached on disk.
- Stars, ratings, play counts, playlists, play queue.
- mDNS/DNS-SD advertisement on the LAN.
- Logging to stderr. Graceful shutdown on SIGINT and SIGTERM (Unix) and console close (Windows).
- `download` is disabled: it returns Subsonic error 50, and `getUser` reports `downloadRole: false`.
- Builds and runs on Linux, Windows and macOS.

### 1.2 Deferred

Owner upload, multiple users, waxnerd-cloud registration, relay, guests, billing, web UI, API-key authentication (`apiKeyAuthentication`, `tokenInfo`), the `transcoding` extension (`getTranscodeDecision`, `getTranscodeStream`), HLS, video, podcasts, internet radio, shares, jukebox, chat, bookmarks, `getNowPlaying` content, `getAvatar` images, lyrics (the `songLyrics` extension), artist biographies and images, similar and top songs, external scrobbling, JSONP, TLS, transcode caching, full-text search (FTS5), MusicBrainz IDs, ReplayGain, multi-artist fields, filesystem watching.

### 1.3 Decisions

- Supported audio extensions: `flac mp3 m4a aac ogg opus wav aif aiff`, matched without regard to case. Other files are ignored. The extension in lower case is the track's suffix and selects the content type: `audio/flac`, `audio/mpeg` for `mp3`, `audio/mp4` for `m4a`, `audio/aac`, `audio/ogg` for `ogg` and `opus`, `audio/wav`, and `audio/aiff` for `aif` and `aiff`. A track is lossless when the suffix is `flac`, `wav`, `aif` or `aiff`, and when the suffix is `m4a` and the codec is ALAC.
- Tag reading (`library::tags`): lofty detects the format from the file content, and from the extension when the content does not decide it, so an Opus stream in a `.ogg` file is read. Fields come from the tag of the format's primary type, or from the first tag when the file has none. A missing title is the file stem, a missing artist is `[Unknown Artist]` and a missing album is `[Unknown Album]`. The year is the leading four digits of the recording date, or of the year tag when the date has none; `0000` is no year. A track or disc number such as `3/12` is 3. The values `1` and `true` set the compilation flag. A file that lofty cannot parse yields an error and no metadata.
- The tag bound: a tag read takes at most 32 MiB of a file (`tags::MAX_TAG_BYTES`). A file whose headers declare a larger tag is refused before lofty reads it, and so is a file of which lofty would read more than that. A scan gives a refused file no track, leaves a track that the file has as it is, and records an error that names the file. The file holds no deletion back. `getCoverArt` answers for its picture as for a missing cover (§3.10, "The tag bound").
- Library model: artists, albums, songs (the ID3 model). Folder-style browsing (`getIndexes`, `getMusicDirectory`) is simulated from the same data. One music folder per configured directory.
- Album identity: (album artist, album title), normalised (§3.3). Album artist falls back to the track artist. When the `compilation` flag is set and no album-artist tag exists, or the album artist is "Various Artists" (case-insensitive), the album artist is "Various Artists". A track whose album artist is "Various Artists" has the compilation flag. Disc numbers do not split albums.
- Artist identity: the album artist name, normalised. A track row holds two names as text: the track artist tag and the album artist of its file by the rule above. A track artist that differs from the album artist creates no artist row.
- Track identity is a surrogate ID assigned once. The scanner matches a vanished track to a newly seen file by fingerprint, so a rename, a move between directories, a move between music folders, and a change of a music folder's path keep the track's ID and everything attached to it. A file that changes at its path, by a retag or by other content, keeps its ID too, unless its old bytes are found at another path in the same scan. A retag that changes the file's first or last 64 KiB in the same scan interval as a move is treated as a deletion plus a new track (§3.3).
- Album and artist rows have surrogate IDs looked up by natural key. A row keeps its ID while a track row refers to it, so a rescan, a full scan, a new track of the album, a move of its files and a change of case, of surrounding white space or of Unicode form in its name keep the ID and the annotations attached to it. Such a change of the name reaches the row when no track carries the spelling that the row has (§3.3). An album row is deleted when no track row refers to it, and an artist row when no album row and no track row refers to it, both at the end of a scan that was not cancelled (§3.10 step 6); nothing else deletes these rows. Retagging an album title or album artist makes a new album (and artist) row with a new ID; the old row stays while one track still has the old tags. Annotations attached to the old album or artist ID are deleted when the row disappears. Track annotations are unaffected.
- A case-only rename on a case-insensitive filesystem (macOS, Windows) is a rename and matches by fingerprint.
- Scans run at startup when `library.scan_on_start = true` (default), on `startScan`, on `wn-server scan`, and every `library.rescan_interval_minutes` when set. The interval is 0 by default, which turns the periodic scans off. One scan of a library runs at a time, in the server process and in the `wn-server scan` command together. A trigger that finds a scan running starts none and queues none (§3.10).
- A track is deleted only when the scan knows that its file is gone. That needs two things. The scan read the directory of the file and found no file there, or the folder was removed from config. And the scan read every file that could be the file of the track. A path that cannot be read (a folder root, a directory, a symbolic link that cannot be resolved, a file whose state cannot be read) may hold any file, so a scan with such a path deletes no track. A file whose content cannot be read may be any file of its size, so a scan with such a file deletes no track of that size. A music folder that previously held tracks and now yields no supported file keeps its tracks. While a configured folder yields no supported file, the tracks of a folder removed from config are kept, because their files may be in it. Each of these cases is an error of the scan that names the folder, the path or the file. A track that cannot be deleted for one of these reasons while another track takes its path is kept without a file: it gets a placeholder path, so its ID does not name the file of the other track (§3.10).
- Cover art sources, in order: a cover file in the album's directory; then a cover file in the parent directory of the album's disc directories; then the embedded picture of the album's first track that has one. A cover file is a file named `cover`, `folder`, `front` or `album` with extension `jpg`, `jpeg`, `png` or `webp` (case-insensitive). The tracks of an album are ordered by disc number, where a track without one counts as disc 1, then by track number, where a track without one follows the numbered tracks, then by path. The album's directory is the directory of its first track. An album has disc directories when its tracks are in two or more directories that have the same parent directory in one music folder, as `Album/CD1` and `Album/CD2` have `Album`. The cover file of that parent directory is a source only when no track of another album is at or below the parent directory: a directory that holds the discs of two albums gives its cover file to neither. The parent directory is a directory of the music folder or the folder itself. The folder itself has no parent directory in the library, so tracks in the folder itself are in no disc directory, and no file outside the configured folders is a cover. No other directory is searched: not the directory of another disc, not a directory further up, and not the parent directory of an album whose tracks are in one directory, which is the directory of the artist in a library of `<artist>/<album>` directories. The track rows say where the tracks of an album are, and a track without a file (§3.4) is in no directory. Among several cover files of one directory the name decides first, in the order `cover`, `folder`, `front`, `album`, then the extension, in the order `jpg`, `jpeg`, `png`, `webp`. A file with such a name that is a symbolic link is not a cover, because a link can name any file that the server can read (§3.11); the directory of the file can be a link. A track without a file (§3.4) is not a first track and gives no picture. Artists have no image.
- `getCoverArt?size=N` returns a JPEG at the step of N. The steps are 80, 160, 320, 640, 1280 and 2000 pixels, and the step of N is the smallest one that is not smaller than N. An N over 2000 counts as 2000. The longer side of the JPEG is at most the step, so the JPEG can be larger than N, and it is smaller than N only when the image is. An image whose sides are within the step keeps its size: no image is enlarged. The sizes of one step get the same bytes, so a cover has at most six resized files in the cache (§3.11). A JPEG that declares an orientation in its Exif metadata is turned and mirrored accordingly when it is resized. Without `size`, and with `size=0`, the original bytes are returned when they are a JPEG, PNG or WebP image, with the content type of that format and with their metadata (§3.11).
- The server has no lyrics in version 1. The scanner reads no lyrics tag and no lyrics file. `getLyrics` and `getLyricsBySongId` answer every song with an empty result, as a server answers a song without lyrics (§4).
- Annotations (star, rating, plays) are per user and keyed by item ID in one table. A play is counted for a track. The plays of an album are those of its tracks and are not stored (§3.4).
- Playlists belong to the owner. `public` is stored and has no effect with one user.
- One play queue per user; `savePlayQueue` replaces it.
- `scrobble` with `submission=true` (default) increments the play count of the track and sets its last play to the later of the stored time and the time of the play. `submission=false` is accepted and writes nothing. Nothing is forwarded anywhere.
- Transcode targets: `opus` (libopus in Ogg, `audio/ogg`) and `mp3` (libmp3lame, `audio/mpeg`). A stream is the original file unless the request asks for another format than the file has, or for a bitrate below the bitrate of the file, so a lossless file stays lossless otherwise. `format=opus` and `format=mp3` select a transcode, except for a file that has that format already and is within the limit. `maxBitRate` alone selects Opus when the bitrate of the file exceeds it. `format=raw` serves the original. Another `format` value is read as no `format`. The bitrate of a transcode is clamped to 32–320 kbps (§3.9).
- Transcoded streams are not cached and do not support Range (`Accept-Ranges: none`). Seeking uses `timeOffset`. A transcoded stream never carries `Content-Length`, and its body is never cut: the server does not know the length of a stream before ffmpeg has written it, and measured Opus streams have 0.67 to 1.10 times the length that the bitrate and the duration give (§3.9). `estimateContentLength` is accepted and has no effect.
- Transcode concurrency: `transcoding.max_concurrent` (default 2). A request past the limit waits up to 5 s, then returns HTTP 503 with `Retry-After: 5`. A transcode that has written nothing after 10 s is ended, and its request is error 0. A transcoded stream whose client takes no chunk for 10 minutes is ended (§3.9).
- Open files of `stream`: the responses that serve an original file hold at most 64 files open at the same time. A request past the bound waits up to 5 s, then returns HTTP 503 with `Retry-After: 5`, as a transcode past its limit does. HEAD, HTTP 304 and HTTP 416 open no file and are not bounded. The two values are fixed and are not config keys (§3.9). Connections are not bounded at the listener.
- The owner password is stored as plain text in the database. Token auth (`t = md5(password + s)`) requires a recoverable password. Anyone who can read the data directory can read the password, so it must not be reused anywhere else. On Unix, `init` creates the data directory with mode 0700 and the database with mode 0600; on Windows, the user-profile ACL protects the directory.
- `init` and `user set-password` generate the password by default and print it once: four groups of five characters separated by hyphens (`xxxxx-xxxxx-xxxxx-xxxxx`), drawn from the operating system's random generator (`rand::rngs::SysRng`) from the 31-character alphabet `abcdefghjkmnpqrstuvwxyz23456789` (no `i`, `l`, `o`, `0`, `1`), which gives 99 bits of entropy and types easily on a phone. Random bytes of 248 and above are discarded, so every character is equally likely. The owner may supply a password instead through `--password-stdin` (the first line of stdin, without its line ending; an empty line is an error) or the `WN_SERVER_PASSWORD` environment variable (an empty value counts as unset); the flag wins over the variable. A supplied password is not printed. There is no interactive prompt.
- A password is never logged and never part of an error message or of a `Debug` output. The types that hold one (`cli::PasswordSource`, `users::UserRow`, `api::params::Params` and the credential types of `auth::extract`) leave it out of their `Debug` output. `Params` holds every parameter of a request, so its `Debug` output writes the name of every field and writes `[redacted]` in place of the value of `p`, `t`, `s`, `apiKey` and `password`, whatever the letter case of the name.
- Default port 4200, bind `0.0.0.0`.
- Search is a substring match with SQL `LIKE` and `ESCAPE '\'`. A query is split at white space into terms, and every term must be part of a name of the item. The names are compared in their normalised form (§3.3) through the columns `artists.key`, `albums.key` and `tracks.title_lc`, so the letter case and the Unicode form of a name and of a query have no meaning. The track artist has no normalised column: it is compared as the tag spells it, and `LIKE` ignores the case of ASCII letters only. A letter with a diacritic is not its base letter. An empty query returns everything, paged (§4).
- API errors use HTTP 200 and the Subsonic error envelope. Unknown `/rest/*` methods return error 0 with message `unknown endpoint`. Paths outside `/rest/` return 404.
- `v` and `c` are required by every method except the public `getOpenSubsonicExtensions` (error 10 when absent), also when authentication is disabled. The value of `v` is not compared; errors 20 and 30 are never produced.
- Music folder paths are absolute (`std::path::absolute`, no symlink resolution, no `\\?\` prefix). A configured folder can be a symbolic link, and its path can lead through links.
- Nothing outside the configured folders is indexed or served. The scanner applies the rule to the symbolic links in the folders (§3.10 step 3). `stream` and `getCoverArt` apply it again at each request, with one function, to the file that the request reads: the file of a track, a cover file, and the audio file that holds an embedded picture (§3.9, §3.11). A file whose path resolves outside the folders is error 70 for both methods. The scanner and the two methods resolve every link of a path with `fs::canonicalize` and compare the result with the resolved paths of the configured folders.
  - A link, to a file or to a directory, whose target is outside every configured folder is not followed. No file behind it has a track row. It is no error of the scan and holds no deletion back. An owner with music on another disk adds the directory of that disk to `library.folders` and does not link it into a folder.
  - A link whose target is inside a configured folder adds no second row for a file. When the walk of a folder reaches the target at its own path, the file has its row at that path and the link is not followed. When no walk reaches the target at its own path, because a name on that path is one that the walk skips, the link is followed, and the file has its row at the path through the link. A link from one configured folder into another one follows the same two rules.
  - A link that cannot be resolved is an unread path, because the scan does not know where it points (§3.10 step 3).
  - A track row at a path that these rules keep the walk from seeing is the row of a file that is gone. The scan relinks it to a file with its fingerprint that has no row, or deletes it with its annotations and its playlist entries (§3.10 step 5). The rows of albums that are linked in from another disk are therefore deleted by the first scan that read everything, unless the directory of that disk is a configured folder by then; the rows then follow their files into that folder and keep their IDs.
  - A cover image file that is a symbolic link is not a cover (see the cover art sources above).
  - Stated limits. A hard link cannot be told from the file that it names, so a hard link in a folder to a file outside the folders is indexed and served as a file of the folder. The scanner compares a link when the walk meets it and reads the tags and the fingerprint of the file later in the same scan, through the path of the link. A link that changes between the two can therefore lead that read out of the folders. `stream` and `getCoverArt` make their comparison at each request, so a link that changed after the walk leads no request out of the folders; each of them reads the path and opens the file after it, and a path that is exchanged between the two is followed for that one request (§3.9, §3.11). A file behind two links can have a second row for the time of an outage, and a volume that is mounted below a folder loses its rows while it is not mounted (§3.10 step 3).
- Entries whose name starts with `.` are skipped on every OS; the Windows hidden attribute is not checked. Directories with the names that an operating system gives to the directories it keeps at the root of a volume are skipped too: `System Volume Information` and `$RECYCLE.BIN`, matched without regard to case, and `lost+found`, matched in that spelling. They are skipped at every depth, because a volume can be mounted below a music folder. They hold no music, and the user of the server cannot list them. A skipped entry is not walked; when it cannot be read, that is no error and holds no deletion back. A file name that is not valid Unicode is skipped with a warning.
- `jsonp` is not supported; `f=jsonp` returns error 0 in XML.

## 2. Platforms and what CI verifies

| OS | Build and run | Verified by |
|---|---|---|
| Linux | native | CI: `cargo xtask check` (fmt, clippy `-D warnings`, full test suite) in a `rust:1.98.1-bookworm` container on the Woodpecker Kubernetes agent |
| Windows | native (MSVC or GNU host toolchain; `rusqlite` `bundled` needs the Visual Studio Build Tools or mingw) | CI: `cargo clippy --locked --workspace --all-targets --target x86_64-pc-windows-gnu -- -D warnings` in the same container with `gcc-mingw-w64-x86-64`; compiles every crate, every test and every build script for Windows. Tests do not run in CI. Native test runs are a manual step recorded in the end-to-end verification until a Windows agent exists |
| macOS | native | Not verified by CI. Developers work on macOS and run `cargo xtask check` before every push; that run is the macOS verification |

Woodpecker has one Linux Kubernetes agent, container steps and no build cache. Packages installed in one step are gone in the next, so each pipeline step installs what it needs.

Portability rules in code:

- Signals: `tokio::signal::ctrl_c()` everywhere; `#[cfg(unix)]` SIGTERM; `#[cfg(windows)]` `ctrl_break`, `ctrl_close`, `ctrl_shutdown`. `cli::OtherStopSignals` is the type that differs (§3.13). It holds the listeners only. Which signal shortens the stop is in the constants of `cli::StopSignal`, and the limits of the stop are in `server::Grace`; both are compiled and tested on every OS.
- File modes: `#[cfg(unix)]` only (`std::os::unix::fs::PermissionsExt`). Tests of modes are `#[cfg(unix)]`.
- Relative paths are built from `Path::components()` joined with `/`, stored and compared in that form on every OS. The absolute path is rebuilt with `folder.join(components)`.
- Folder paths in the config are written as TOML literal strings (`'C:\Music'`) so backslashes survive. A literal string cannot hold a single quote or a control character other than tab, so a folder path with one of those is written in the string form the `toml` crate chooses for it: `"/music/Guns N' Roses"` is a basic string, and `'''C:\Music\Guns N' Roses'''` is a multi-line literal string because the path also has a backslash. Every form reads back as the same path. `transcoding.ffmpeg` is written in the form the `toml` crate chooses, which is a literal string when the value has a backslash and no single quote.
- `transcoding.ffmpeg` is a program name or a path; Rust resolves `ffmpeg` to `ffmpeg.exe` through `PATH` on Windows. Arguments are passed as argv, never through a shell, so paths with spaces work.
- `kill_on_drop` is `TerminateProcess` on Windows and SIGKILL on Unix.
- Atomic cache writes use temp file plus rename. On Windows the rename fails with a sharing violation while another request reads the destination; a failed rename whose destination exists is treated as success.
- `.gitattributes`: `* text=auto eol=lf`, `tests/fixtures/audio/* binary`.
- Checks run through `cargo xtask check` on every OS; `xtask` invokes the cargo named by `env!("CARGO")` so the toolchain that runs it runs the checks. `scripts/check.sh` is a one-line wrapper for Unix and CI.

## 3. Architecture

### 3.2 Dependencies

All dependencies are declared in the root `Cargo.toml` from the start and `Cargo.lock` is committed; a feature issue adds no dependency. Every crate compiles on Rust 1.98.1. The project is Apache-2.0; every dependency has a compatible licence. The resolved tree has no GPL, LGPL or AGPL crate. `option-ext` (MPL-2.0, through `directories`) is used unmodified as a dependency, which the MPL permits.

Three small helpers are written in the crate rather than added as dependencies: the instance UUID is formatted from 16 random bytes with the version-4 and variant bits set, the `filename*=UTF-8''` percent-encoding for `Content-Disposition` is a short function over the unreserved set, and `Params` parses `application/x-www-form-urlencoded` data by the rules of the URL standard. axum's `Query` and `Form` extractors parse the same data and are not used: one function in `Params` parses the query string and the form body, the router applies its own content-type rule and the 8 MiB limit, and every failure is an `ApiError` in the requested format.

`sqlx` is not used: an async API adds nothing for a single-writer embedded database, its query macros need a database at compile time, and its tree is larger. `symphonia` is not used: ffmpeg decodes; `lofty` reads tags. `argon2` is not used: the password must be recoverable.

ffmpeg is an external program found on `PATH` or named by `transcoding.ffmpeg`. The project does not link, vendor or bundle ffmpeg or its libraries, so the licence of a user's ffmpeg build does not reach this project's licence boundary.

### 3.3 Identity

IDs are opaque strings of a two-letter prefix, a hyphen and 32 lower-case hex characters: `tr-`, `al-`, `ar-`, `pl-`. `ids::parse` accepts exactly that shape and returns the kind and the 32 hex characters; anything else is rejected before it reaches SQL or the filesystem. Music folder IDs are the integer `folders.id`, which Subsonic clients expect as a number. Cover-art IDs are an album ID (album art) or a track ID (embedded art).

- Track: `tr-` + 16 random bytes, assigned on first sight. `(folder_id, rel_path)` is the locator; it is unique and it changes when the file moves. A track that is kept without a file has the placeholder path `/<id>` as its `rel_path`; a relative path never starts with `/`, so no file has that path (§3.10). `db::queries::tracks::placeholder_path` builds the value and `db::queries::tracks::has_file` tests for it (§3.4).
- Fingerprint: `size` in bytes, a colon, and the first 16 bytes hex of SHA-256 over the first 64 KiB of the file followed by the last 64 KiB (the whole file when it is 128 KiB or smaller). A pure move, rename or copy keeps the fingerprint. A tag edit changes it, because tags live in the head (ID3v2, Vorbis comments, MP4 atoms) or the tail (ID3v1, APE). Two identical files share a fingerprint.
- Artist key: the normalised form (below) of the trimmed album artist name. Artist: `ar-` + random, `UNIQUE(key)`.
- Album key: the normalised form of the trimmed album title. Album: `al-` + random, `UNIQUE(artist_id, key)`.
- Playlist: `pl-` + random.

Normalised form: the server compares names in one form, and this paragraph defines it. The normalised form of a text is the text in Unicode form NFC, and then in lower case. `ids::normalise` computes it.

- NFC composes a base letter and its combining marks into one character where Unicode has that character: `e` followed by U+0301 becomes U+00E9. A text in decomposed form (NFD) and the same text in composed form therefore have one normalised form.
- Lower case is the default case mapping of Unicode for every character, which `str::to_lowercase` applies. It has no rule of a language: `I` becomes `i` in every text, and U+0130 becomes `i` followed by U+0307. U+03A3 becomes U+03C2 at the end of a word and U+03C3 elsewhere. An ASCII letter becomes its ASCII lower-case letter.
- Nothing else changes. No diacritic is removed, so U+00E9 and `e` stay different letters. A ligature is not its letters, and the white space of the text stays.
- The lower case of a composed text is taken as it is and is not composed again. `J` followed by U+030C has no composed character and its lower case has one, U+01F0, so the two texts have different normalised forms.

Three columns hold a normalised form, and the search compares its terms with them (§4): `artists.key`, `albums.key` and `tracks.title_lc`. A term of a query and `tracks.title_lc` are results of `ids::normalise`, so a term and a stored title are in one form. `ids::artist_key` and `ids::album_key` compute a natural key with statements of their own, because a key decides the identity of a row; a unit test checks that a key is `ids::normalise` of the trimmed name. No other column is normalised: `tracks.title`, `tracks.artist_name`, `tracks.album_name`, `tracks.album_artist_name`, the display names of the album rows and the artist rows and the genres hold the spelling of the tags.

Display names of album rows and artist rows: names that differ in case, in surrounding white space or in Unicode form have one key and are spellings of one name. A row is made with the spelling in the tags of the track that makes it (§3.10). At the end of every scan (§3.10 step 6) the stored name of a row is compared with the spellings that the track rows of the row carry:

- A row keeps its name while one track carries it, however many tracks carry another spelling.
- A row whose name no track carries takes the spelling that the most tracks carry. Among spellings that equally many tracks carry it takes the first in byte order of the UTF-8 text, as the album genre does (§3.10). Upper-case ASCII letters precede lower-case ones in that order, so `The Beatles` precedes `the beatles`.
- A row of which no track carries a spelling keeps its name.

The spelling that a track carries for its album is its album title, `tracks.album_name`. The spelling that a track carries for its artist is the album artist of its file, `tracks.album_artist_name`: the album-artist tag, the track artist of a file without that tag, and `Various Artists` for a compilation (§1.3). The scan finds the artist row of a track by this value, so the value has the key of that row. The track artist, `tracks.artist_name`, is not read for a track that has an album artist. When the files of an artist spell its name in one way in the album-artist tag and in another way in the track-artist tag, the album-artist tags decide the name of the row, and a new spelling in the album-artist tags alone reaches the row. The row of `Various Artists` always has that name: §1.3 gives every track of it that album artist in that spelling. A track without a file (§3.4) carries its spellings as every other track does.

A track row that a scan wrote at schema version 1 has no album artist: its `album_artist_name` is NULL (§3.4). Such a track carries its track artist when the track artist has the key of the artist row, and no spelling of the artist when it has another key. For a file without an album-artist tag and without the compilation flag, that is the spelling that the value holds once it is stored. For a file whose two tags spell one name differently, it is the spelling of the track-artist tag, and the value holds the spelling of the album-artist tag. The track artist of such a row does not rename the row of `Various Artists`.

A scan stores the album artist of a file when it reads the tags of the file: for a new file, for a file that changed, for a moved file whose tags are read again (§3.10 step 4), and in a full scan for every file that is at the path of its row. A library that was scanned at schema version 1 gets the values in this way and in no other. The migration writes no row, and it does not make the next scan a full scan. A scan that is not full reads no file that did not change, and a full scan reads the fingerprint and the tags of every file that is at the path of its row. A file that moved since the last scan is relinked by the rule of §3.10 step 4 in a full scan as well: its tags are read only when its `mtime`, its `size` or its extension differ, and the next full scan finds it at the path of its row. The value changes a name only for an artist whose files spell it differently in the two tags. Such an artist keeps the name from the track-artist tags while one track without the value carries it. It takes a spelling of the album-artist tags when a scan has read the files of those tracks: after a full scan (`wn-server scan --full`, or `startScan` with `fullScan=true`), or after those files changed. No ID changes in either case.

The step sets `name` of an album row, and `name` and `sort_name` of an artist row, which have one value. `artist_name` of an album row is the `name` of its artist row, and the same step sets it. The ID and the key of a row do not change, no row is inserted or deleted for a name, and the annotations of a row stay attached to it. A row that has its names is not written.

### 3.4 SQLite schema

Pragmas: `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`.

Migrations are numbered SQL files in `migrations/`, embedded in the binary in order (`db::MIGRATIONS`). Migration n moves the schema from version n − 1 to version n, and `PRAGMA user_version` holds the version of a database. `Db::open` applies the migrations that a database lacks, in order. Each one runs in one `BEGIN IMMEDIATE` transaction that also sets the version, and it runs only when the database still has the version that the migration starts from, so two processes that open one database apply a migration once. Every command that opens the database (`run`, `scan`, `user`, `init`) therefore upgrades a database of an earlier version in place, before it reads a row.

- `0001_init.sql` creates the tables and the indexes.
- `0002_tracks_album_artist_name.sql` adds the column `tracks.album_artist_name`. It writes no row: every row keeps its values and its ID and has NULL in the column (§3.3).
- `0003_scans_milliseconds_and_drop_has_lyrics.sql` changes the unit of the times of the scans, adds the column `scans.changed_library` with the index `scans_changed`, and removes the column `tracks.has_lyrics`. Its effect on the rows that exist:
  - `scans.started_at` and `scans.finished_at` held Unix seconds and hold Unix milliseconds. The migration multiplies every stored value by 1000, and a row without an end time keeps NULL. Two scans that ended in one second have the same end time afterwards, the start of that second. `lastScan` of `getScanStatus` is the same text before and after (§4).
  - Every scan row has `changed_library = 1`, the default of the column, because the earlier versions did not record what a scan wrote. `lastModified` of `getIndexes` is therefore the latest end time of the scans of the database (§4). Compared with the value that the same database gave before the upgrade, it is later, equal, or earlier by 999 milliseconds at most. When it is later, a client that holds the old value reads the artists once more. When it is equal, that client is answered without the artists. It is earlier only when the latest scan ended in the same second as a scan before it. That client is then answered without the artists, which did not change, and every scan that ends in a later second has a later end time than the old value.
  - `ALTER TABLE tracks DROP COLUMN has_lyrics` removes the column. No statement read or wrote the column, and no index, constraint, trigger or view names it, which the statement requires. SQLite rewrites each row in place without the column: a row keeps its rowid, its ID and every other value, no row is deleted and inserted again, and no row of `annotations`, `playlist_tracks` or `play_queue_tracks` is written. A row of an earlier build that held 1 in the column loses that value, which nothing read.
  - Every other row of every table keeps its values.

The schema below is the result of all migrations. A column that a migration adds is the last column of its table, and a column that a migration removes is not in the listing. A migration file that is on `main` is not edited, because databases exist that applied it and do not apply it again. A schema change is a new file with the next number and a new line in `db::MIGRATIONS`.

A migration that fails is rolled back with its transaction, whichever of its statements failed. The database keeps the version, the schema and the rows that it had before that migration, and the migrations before it stay applied. `Db::open` returns `DbError::Migration`, and the command fails with it (§3.6); `run` fails before it binds the address. The message is `migration <file> failed and the database was left at schema version <n>: <the error of SQLite>`. The file is the name of the migration in `migrations/`. The version is read from the database after the rollback; when it cannot be read, it is the version from before the migration, which the rollback leaves. The next command that opens the database runs the migration again.

`Db::open` returns `DbError::UnsupportedSchema` for a database whose `user_version` is negative or greater than the number of migrations in the build. A database that a newer build has migrated has such a version, so an older build does not open it. Every command that opens the database prints `the database has schema version N; this build supports versions 0 to M` and exits with 1, and `run` fails before it binds the address. The older build reads the version and applies no migration: the version, the schema and the rows stay as the newer build left them. No migration has a reverse step, so a database does not return to an earlier version. The owner runs the newer build, or puts back a copy of `library.db` from before the upgrade.

`Db` holds one writer `Connection` behind a `tokio::sync::Mutex` and four reader connections, each opened read-only behind its own `tokio::sync::Mutex`. Async callers use `db.read(|conn| ..)` and `db.write(|conn| ..)`, which run the closure on `spawn_blocking`. Blocking-thread callers use `db.with_writer(|conn| ..)` and `db.with_reader(..)`, which take the lock with `blocking_lock`: the scanner the first, the commands of the CLI both. The closures return `Result<T, DbError>`. `db.close().await` waits for the running reads and writes of the handle and runs `PRAGMA wal_checkpoint(TRUNCATE)`; it returns an error when a connection outside the handle blocks the checkpoint. The connections close when the last clone of the handle is dropped. Tests use `Db::open_memory()` (one shared connection) or a temp file.

Read limit: a read of `db.read` runs for 5 s at most (`db::READ_LIMIT`). Every read of a request is a call of `db.read`: the read of the accounts (§3.7), the reads of the handlers and the read of the cover service (§3.11). A statement of a request therefore does not hold one of the four read connections for longer.

- The time counts from the moment the closure starts on its connection. The wait for a free connection is no part of it.
- When the time ends, the statement that the closure runs is interrupted, and so is every statement that the closure starts after that moment. `db.read` returns `DbError::ReadLimit` when the closure returns the error of an interrupted statement, and the handler answers error 0 (§3.8).
- The connection serves the next read. No interrupt is issued after the closure has returned, and a transaction that the closure left open is rolled back.
- The limit holds for a read whose future is dropped, as the stop drops the handler of a request that outlasts the grace (§3.13). The closure runs on, and its statement is interrupted at the limit.
- `db.write`, `db.with_writer` and `db.with_reader` have no limit. The scanner reads and writes through `db.with_writer`, and the commands of the CLI use the blocking methods. The migrations run in `Db::open` on the write connection, before the handle exists. A write of a request goes through `db.write` and has no limit.
- The value comes from times measured on a library of 100 000 tracks, 8 400 albums and 2 100 artists (Apple silicon, release build, memory database; the ignored test of `db::queries::search` prints the times of the searches). A page of 500 tracks of an empty query takes 5 ms at the end of the library and 41 ms with a music folder. A query of one to three terms takes 50 to 110 ms. The statements of the list methods take 31 ms or less on 96 000 tracks. The slowest statement that was found within the bounds of the request parameters is the track statement of a query of 32 terms, 31 of which every track matches (§4): 1.4 s. The limit is 3.6 times that, so a machine that is three times slower answers that request. On a machine that is slower still, the query at the bound of 32 terms is interrupted, and a query that a user types is not.
- No configuration option names the limit. `Db::set_read_limit` changes the limit of a handle, and tests set milliseconds with it.

The limit needs no feature of rusqlite: `Connection::get_interrupt_handle` returns a handle that calls `sqlite3_interrupt` from another thread. One thread of the process keeps the limits of every handle (`db-read-limit`, started by the first read). The thread ends only by a panic; the next read then starts a new one, which keeps the limits of the reads that run. `db.read` adds its read to a list when the closure starts and removes it when the closure has returned. The thread sleeps until the limit of a read in the list ends, and then interrupts the connection of that read every 50 ms while the read is in the list. The thread is no part of the runtime, so it also keeps the limit of a read whose future was dropped and of a read that runs while the runtime shuts down. Three rules follow from what an interrupt does in SQLite 3.53:

- An interrupt stops the statements that run when it arrives, whichever closure started them. The thread interrupts while it holds the lock of the list, and a read takes that lock to leave the list. An interrupt therefore never arrives after the connection is released, and it never reaches a statement of the next read, of a write or of the scanner on the one connection of a memory database.
- An interrupt that arrives while the connection runs no statement stops nothing: SQLite clears its flag when the next statement is prepared or started. That is the case between two statements of a read and after its last one. The thread repeats the interrupt so that a read whose limit ends between two statements does not run the later ones without a limit.
- A handler reads inside a transaction, and rusqlite rolls the transaction back when the handler drops it. An interrupt can stop that `ROLLBACK`, and rusqlite ignores the error. After an interrupted read `db.read` therefore runs `ROLLBACK` when the connection still has a transaction. Without it the next handler on the connection could start no transaction, and a checkpoint could not truncate the write-ahead log.

`scans` holds one row for each run of the scanner (§3.10). `started_at` and `finished_at` are Unix milliseconds; `tracks.mtime` and `albums.cover_mtime` are Unix seconds. `finished_at` is NULL while the scan runs and for a scan whose process ended before the scan did. `changed_library` says whether the scan changed the library, and the scan stores it with its end time (§3.10 step 7). `indexes::last_modified` reads the latest end time among the rows with `changed_library = 1`, which is one entry of the index `scans_changed` whatever the number of rows (§4).

`tracks.album_artist_name` holds the album artist of the file in the spelling of the file (§1.3). The scan stores it with the other values of the tags (`tracks::insert_track`, `tracks::update_track_meta`), and a relink that reads no tag leaves it. It is NULL only in a row that was written at schema version 1 and whose tags no scan has read since (§3.3). `artists::update_names` is its one reader. `tracks::Track` does not hold it, as it does not hold `title_lc`.

`tracks.title_lc` holds the normalised form of `tracks.title` (§3.3), and `title` holds the title as the tag spells it. The scan stores both when it reads the tags of a file (`tracks::insert_track`, `tracks::update_track_meta`). A row whose `title_lc` is another text is corrected by the next scan and not by a migration: step 6 of every scan sets the value in each row that does not hold it (`tracks::normalise_titles`, §3.10). The schema does not change for that, so the schema version stays, and SQLite has no function that brings a text into NFC, which a migration in SQL would need. A row holds another text when it was stored by a build that lower-cased the title and did not compose it. The title of a tag in decomposed form is decomposed in such a row, and no term matches it until a scan has ended; the search finds the track through its album and its artist until then. The step writes `title_lc` and no other column: the row keeps its rowid, its ID, its title and its update time, and no row of `annotations`, `playlist_tracks` or `play_queue_tracks` is written. A scan that sets a value wrote a track row, so it counts as a scan that changed the library (§3.10 step 7).

Readers of `tracks`: a row whose `rel_path` starts with `/` has no file. The value is the placeholder path of §3.3. `db::queries::tracks::has_file(rel_path)` is the one test for it, and `Track::has_file` calls it; no reader tests the value itself. Code never joins such a `rel_path` to a folder path, because `Path::join` replaces the folder with a root path. `stream` and `getCoverArt` for the ID of the track answer error 70 for such a track. `getIndexes` and `getMusicDirectory` leave it out of the folder tree. `getSong`, `getAlbum`, `getPlayQueue`, search and playlist results may list it; it keeps its tags, its ID and its annotations. Aggregation (§3.10 step 6) treats it as a track of its album: the album row and the artist row stay while it refers to them, and `song_count`, `duration_ms`, `year` and `genre` count it, so the counts of an album agree with the rows that `getAlbum` may list. The names of the two rows count the spellings it carries (§3.3). Aggregation never takes such a row as the track that gives the album its directory or as the source of embedded cover art; an album whose tracks all have no file has no cover. SQL that needs files filters with `db::queries::tracks::HAS_FILE_SQL`, which is `rel_path NOT LIKE '/%'`. The constant is the one place that spells the test in SQL: every query module uses it, and a unit test checks that it agrees with `has_file`.

The library queries and the response models follow the rule (§3.8). `browse::tracks_of_album`, `browse::track` and `browse::tracks_by_ids` return such a row as every other row, and `browse::genres` counts it. `browse::list_artists` with a music folder counts only the tracks that have a file, because a track without a file is in no folder. `browse::file_path` returns no path for it. `model::child` leaves `path` out, and never gives the ID of the track as `coverArt`, because `getCoverArt` has no picture for it. The other fields of the element are those of the file the track had.

Genres are derived with `GROUP BY genre`. Cascades from `tracks` to `playlist_tracks` and `play_queue_tracks` are correct because a track row is deleted only when its file is gone and no new file carries its fingerprint, and never while a path or a file that the scan could not read may hold it, nor for a folder that is newly empty. Both child tables index `track_id`, so the deletion of a track does not scan them. The cascade deletes the rows of the track and writes no other row, so the `position` values that a playlist keeps can have a gap. The playlist queries order by `position` and depend on no value of it, and their next write of the entries stores the positions 0 to n − 1 (§4). The play queue queries order by `position` as well, and they depend on its sign: `savePlayQueue` stores the entry of the current song at position 0, and after the deletion of that song the first entry at a position above 0 is the current one (§4). A queue that is saved without `current` has no value in `play_queue.current_id`, and its entries are at the positions 1 to n. The queries read that column before the positions: the first entry of such a queue is the current one, also after the deletion of one of its tracks (§4).

Plays: `play_count` and `last_played_at` of the `annotations` table hold the plays of a track, and only the row of a track holds them. `scrobble` writes the row of the track and no other row (§4). The play count of an album is the sum of the play counts of its tracks, and the last play of an album is the latest play of one of its tracks. Both are computed from the rows of the tracks when they are read: by `annotations::get_many` for the response models (§3.8) and by the `frequent` and `recent` album lists (§4). In the row of an album and of an artist the two columns keep their defaults, and no reader reads them. The rows of the tracks are therefore the one place that holds a play. The plays of an album follow its tracks: they move with a track that a retag puts into another album, and they go with a track row that a scan deletes.

Multi-user readiness: every per-user table carries `user_id`; `users.role` separates the owner from future guests and has no default, so every insert names the role; the CLI finds the owner with `WHERE role = 'owner'`.

### 3.5 Data directory and config

Data directory, in order: `--data-dir`, `WN_SERVER_DATA_DIR`, then `directories::ProjectDirs::from("", "", "wn-server").data_dir()`: `~/Library/Application Support/wn-server` on macOS, `~/.local/share/wn-server` on Linux, `C:\Users\<user>\AppData\Roaming\wn-server\data` on Windows. An empty `WN_SERVER_DATA_DIR` counts as unset. The chosen path is made absolute with `std::path::absolute`.

```
<data-dir>/
  config.toml
  library.db  (+ -wal, -shm)
  instance.id          UUID string created by init, and by run when it is missing; the mDNS TXT id and the source of the SRV target
  scan.lock            empty file created by the first scan; the process that scans the library holds a lock on it (§3.10)
  cache/covers/        <coverId>-<step>-<coverMtime>-<version>.jpg, with one of the six steps of a size and the version of the resized covers (§3.11)
```

`config.toml` with defaults (`init` writes it with comments):

```toml
[server]
bind = "0.0.0.0"
port = 4200
name = "wn-server"              # instance name shown by discovery
log_level = "info"              # RUST_LOG overrides when set

[auth]
disabled_unsafe = false         # true turns authentication off; unsafe

[library]
folders = ['/Users/adnan/Music'] # TOML literal strings; 'C:\Music' on Windows
scan_on_start = true
rescan_interval_minutes = 0     # 0 disables periodic rescans

[transcoding]
ffmpeg = "ffmpeg"               # program name or path
max_concurrent = 2
opus_bitrate_kbps = 192         # used when format=opus and maxBitRate is absent
mp3_bitrate_kbps = 320          # used when format=mp3 and maxBitRate is absent

[discovery]
mdns = true
```

The default `server.name` is the fixed string `wn-server` (`config::DEFAULT_NAME`). `init` writes it to `config.toml`, and a config that omits the key gets it at load. An owner changes the name in `config.toml`. A name that `config.toml` holds is kept as written. No default and no other value of the configuration is taken from the host name of the machine, and no code reads that name.

Validation at load: at least one folder; each folder is an absolute path that does not name a file; `port != 0`; `server.name` is 1 to 63 bytes long; `max_concurrent >= 1`; bitrates 32–320. `server.name` is the DNS-SD instance name and the TXT `name` value (§3.12), and each holds at most 63 bytes. The error for `server.name` states the length of the name and names the key, the table and the file to edit. Unknown keys are an error (`deny_unknown_fields`). Internal limits and timing values are fields of the config structs with defaults and `#[serde(skip)]`. They are not config keys, a config file that names one is refused as a file with an unknown key, and `config show` and `init` write none of them. Tests set them. They are the grace of a stop and its short form (`server.shutdown_grace_ms`, `server.shutdown_grace_short_ms`, §3.13), the bound on the open files of `stream` and the wait for a slot of it (`server.max_streams`, `server.stream_permit_wait_ms`, §3.9), the scan poll (`library.scan_poll_ms`), and the permit wait, the limit of the first output and the write timeout of a transcode (`transcoding.permit_wait_ms`, `transcoding.first_output_wait_ms`, `transcoding.write_timeout_ms`, §3.9).

Music folders at load: a value of `library.folders` is malformed or unavailable, and the load treats the two differently.

- A malformed value fails the load, and the error names the key `library.folders`. The list is empty. A path is empty or is not absolute: a relative path names another directory for each working directory, and the row of a folder is found by its path (§3.10), so the load resolves none. A path names something that exists and is not a directory.
- An unavailable folder does not fail the load. Its path does not exist, or its state cannot be read: the volume of the folder is unplugged, or its network share is down. `run`, `scan` and `config show` start with it.

`Config::load` cleans each path with `std::path::absolute`, which removes `.` components and repeated separators and resolves no symbolic link. `Library::unavailable_folders` returns the folders of the config that `fs::read_dir` cannot open at the time of the call: a folder that does not exist, and a folder that exists and cannot be listed. `run` and `scan` log one warning for each of them when they start, with the path and the error of the operating system (`Library::warn_unavailable_folders`). The warning is logged at startup only: no request reads the state of a folder, and no request logs it. A scan logs its own error for the folder (§3.10). The folders are not watched: a folder that comes back is read by the next scan.

### 3.6 CLI

```
wn-server init  [--data-dir D] [--folder PATH]... [--username NAME] [--port N] [--password-stdin]
                creates the data directory (0700 on Unix), config.toml, instance.id,
                the database (0600 on Unix) and the owner account; generates the
                password and prints it once, unless --password-stdin or
                WN_SERVER_PASSWORD supplies one; with a config.toml and no
                owner account, keeps config.toml and creates what is missing
wn-server run   [--data-dir D]                 runs the server in the foreground
wn-server scan  [--data-dir D] [--full]        runs one scan and exits; --full re-reads every tag
wn-server user show                            prints the owner's name, role and creation date (UTC)
wn-server user set-password [--username NAME] [--password-stdin]
                generates a new password and prints it once, or stores the supplied one
wn-server config path                          prints the resolved config path
wn-server config show                          prints the effective config
wn-server --version
```

`--data-dir` is accepted before and after the subcommand. `init` checks that each `--folder` is an existing directory and writes it as an absolute path. It refuses a folder that does not exist, although the commands that load the config start with one (§3.5): a path that is typed on the command line and does not exist is most likely a typing mistake. Without `--folder` it writes `folders = []`, and the commands that load the config fail until the owner adds a folder. `init` does not overwrite an existing `config.toml`. On Unix it creates the directories that are missing with mode 0700 and leaves the mode of an existing data directory unchanged. `--port 0` is rejected.

`init` works in this order: it checks the folders, refuses a data directory that has `config.toml` and an owner row in `library.db`, obtains the password, creates the data directory, writes `config.toml`, writes `instance.id` when the file is missing, opens the database and inserts the owner. `--username` names the owner; the default is `owner`. The insert does nothing when an owner row exists, and `init` then fails. When a step after the config write fails, `init` removes the `config.toml` and the `instance.id` it wrote in that run, so the command can run again. An existing `instance.id` is kept.

A data directory that has `config.toml` and no owner row has lost its database or its owner: `library.db` is missing, or it exists without an owner row. `init` opens an existing `library.db` before it reads the password to tell this case from the refused one. It then keeps `config.toml` as it is and creates what is missing. `--folder` and `--port` do not change an existing `config.toml`, so `init` fails when either is given, before it reads the password. It skips the config write. The other steps are those of a first `init`: the password rules and `--username` are the same, a missing `instance.id` is written, a missing `library.db` is created (0600 on Unix) and the owner is inserted. The other rows of an existing database stay as they are. `init` prints `kept <config path>` and then `created <database path>` or `kept <database path>` in place of `wrote <config path>`. When a later step fails, this run removes no file: the next run keeps the `instance.id` and uses the database file that the failed run left. SQLite deletes a write-ahead log that it finds next to an empty database file, so a log that a lost database left behind does not reach the new one. Nothing of a lost database is recovered.

`init` and `user set-password` print `Password for <name> (shown once): <password>` when they generated the password, and then `The password is stored in plain text in the data directory. Do not reuse it elsewhere.` Both checkpoint the write-ahead log with `Db::close` before they print, so the stored password is on disk; a checkpoint that another process blocks is not an error.

`user set-password --username NAME` selects the account by name; without the option the account is the owner. The `user` commands fail when `library.db` does not exist or has no owner row, and do not create either. Only `init` creates them, so the error names `wn-server init`, which creates what is missing and keeps an existing `config.toml` and an existing database.

A command that fails prints `wn-server: <error>` to stderr and exits with 1. A usage error exits with 2.

`scan` loads the config, opens `library.db` and runs one scan in its own process. It fails when `library.db` does not exist and does not create it. It logs to stderr as `run` does. The scan holds the scan lock of the data directory (§3.10), so the command does one of three things:

- No server runs: the command scans.
- A server runs and does not scan: the command scans. WAL lets the server read while the scan writes, and a write of the server waits for one transaction of the scan at most (`busy_timeout`). The server starts no scan of its own while the command holds the lock.
- A server scans, or another `wn-server scan` runs: the command scans nothing, prints an error that says so and exits with 1. It does not wait for the other scan.

After the scan the command checkpoints the write-ahead log with `Db::close`; a checkpoint that a running server blocks is not an error. It then prints the summary to stdout: one `name: number` line for each of `seen`, `added`, `changed`, `moved`, `removed`, `albums`, `artists` and `errors`, and one `error: <message>` line for each error of the scan. It exits with 0, or with 1 when the scan recorded an error. A folder of the config that does not exist or cannot be read does not keep the command from scanning (§3.5). The command logs one warning that names the folder when it starts, and it scans the other folders. The folder is an unread root of the scan (§3.10): the scan deletes no track, the summary has an `error:` line that names the folder, and the command exits with 1. A malformed value of `library.folders` fails the config load, so the command exits with 1 and names the key before it opens the database. A process that is ended during its scan keeps the batches that the scan committed. Its `scans` row has no end time, and the next scan finishes the work.

`getScanStatus` reports `scanning` and `count` for the scans of the server process only. Its `lastScan` is read from the `scans` table and names the scans of the command as well (§4).

`run` opens `library.db` and needs its owner account, because every request acts as a user. It creates neither. When the file does not exist or has no owner row, `run` fails before it binds the address, and the error names `wn-server init`, which creates what is missing and keeps `config.toml`.

`run` starts when a folder of the config does not exist or cannot be read (§3.5). `run_server` logs one warning that names each such folder before it opens the database, and the log has that line once for a run of the server. The server serves the tracks of the other folders. The unavailable folder has its row, so `getMusicFolders` lists it. Its tracks stay in the database with their IDs, their annotations and their playlist entries, and the methods that read the database return them (§3.10). The cover service reads no source in such a folder: it has no stored image for it, and a resized cover only when the cache holds it (§3.11).

### 3.7 Authentication

Every method needs a user, except `getOpenSubsonicExtensions`, which is public. The router authenticates a request before it calls the handler of the method (§3.8). The check does not depend on the handler, so a method that a change adds to the method table is protected without any step in that change. `api::PUBLIC_METHODS` lists the public methods, and a test compares it with the rows that §4 marks `public`.

`auth::extract::authenticate(auth, db, params) -> Result<User, ApiError>` applies these rules in this order:

1. `v` and `c` are required: error 10 naming the parameter. The value of `v` is not compared.
2. With `auth.disabled_unsafe = true` the user is the owner, and no other parameter is read.
3. `apiKey` alone: error 42. `apiKey` with `u`, `p`, `t` or `s`: error 43. `p` with `t` or `s`: error 43.
4. `u` absent: error 10 naming `u`. None of `p`, `t` and `s`: error 10 naming `p, or t and s`. `t` without `s`, or `s` without `t`: error 10 naming the absent one.
5. The account is looked up by `u` without regard to ASCII case. `p` is compared with the stored password in constant time; an `enc:` prefix means hex-encoded, and a value with the prefix and invalid hex matches nothing (`auth::verify_password`). `t` must equal `md5(password + s)` as lower-case hex, compared in constant time; upper-case hex does not match (`auth::verify_token`). An unknown name and a wrong credential are both error 40 with the same message. The credential of an unknown name is checked against an empty password, so both cases run the same steps.

Both comparisons hash the two values with SHA-256 and compare the two 32-byte digests in a loop that does not stop at the first difference. No step of the comparison depends on the length of the stored password, which is empty for an unknown name. The time depends on a length only through the number of 64-byte blocks that SHA-256 reads.

Rules 1, 3 and 4 read no account, so their answers do not depend on the accounts of the server. An empty value is a value: `p=` is a password and `apiKey=` is an API key.

`Authed(User)` is the axum extractor through which a handler receives the user. It returns the user that the router stored in the request. For a request that the router did not authenticate it applies the rules itself, so a handler that takes `Authed` never runs without a user.

A request that breaks a rule is logged at `info` with the values of `u` and `c`, each cut to 64 characters, and the error code. The values of `p`, `t`, `s` and `apiKey` are never logged and are never part of an error message: an error names a parameter and holds no value of the request.

With `auth.disabled_unsafe = true`, `run` logs a warning at startup that names the key and says that the setting is unsafe. Every request that has `v` and `c` then acts as the owner.

Remote-mode seam: `users.role` and `auth::extract::authenticate` are the only places that turn parameters into a `User`. Guests and API keys extend that function and add a table.

### 3.8 Request pipeline and envelope

- Routes `/rest/{method}` and `/rest/{method}.view` for GET and POST, one route with a path parameter. A HEAD request is answered by the route of GET: the handler runs as for a GET request, and the router removes the body of the answer and keeps `Content-Length`. A static method table maps every name in §4 to a handler; names not yet implemented map to `not_implemented`, which returns error 0 with message `not supported`. Unknown names return error 0 with `unknown endpoint`. Paths outside `/rest/` return 404. An `OPTIONS` request to the route is answered as a CORS preflight request (see below). Any other HTTP method on the route returns 405.
- `AppState { config, db, covers, transcoder, streams, scan, cancel, started_at }` is shared through `State`. `streams` is the `tokio::sync::Semaphore` of `server.max_streams` permits that bounds the original files that responses of `stream` hold open (§3.9). `server::run_server` and the test server build it.
- The router handles a request in this order: it reads the parameters, selects the format, looks up the method, authenticates the request unless the method is public (§3.7), and calls the handler. An unsupported format, a form body that cannot be read and an unknown method name are therefore answered without a user. Every other response of a method that is not public needs one, including the `not supported` error of a method without a handler.
- CORS: a browser-based client such as Feishin calls the server from a page of another origin, and the browser lets the page read a response only when the response allows that origin. The route answers `OPTIONS` with the handler `api::cors::preflight`, and the middleware `api::cors::add_headers` wraps the route.
  - An `OPTIONS` request is answered by `preflight` with HTTP 204, an empty body, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: Content-Type, Range` and `Access-Control-Max-Age: 86400`. The request does not reach the steps above, so a preflight request needs no user and no parameter. `Content-Type` and `Range` are the request headers that the target clients set and that a browser may name in a preflight request: Feishin sets `Content-Type: application/json`, and a player sets `Range`.
  - The middleware adds `Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length` to every other response of the route. A player reads these headers from a media response.
  - The middleware adds `Access-Control-Allow-Origin: *` to every response of the route: an envelope, an error envelope, an authentication error, a body of `stream` or `getCoverArt`, the answer to `OPTIONS` and HTTP 405. The headers do not depend on the `Origin` header of the request.
  - No response carries `Access-Control-Allow-Credentials`. The credentials are request parameters and not cookies, so the wildcard origin is enough. The server has no list of allowed origins.
  - A path outside the route gets HTTP 404 without these headers.
  - With `auth.disabled_unsafe = true` (§3.7), every request that has `v` and `c` acts as the owner, and `Access-Control-Allow-Origin: *` lets a page of any origin read the responses. A web page that is open in a browser on the network can then use the server as the owner. It can read and stream the library, and it can call every method, including the methods that change state: `star`, `unstar`, `setRating`, `scrobble`, `createPlaylist`, `updatePlaylist`, `deletePlaylist`, `savePlayQueue` and `startScan`.
  - The handler and the middleware are functions in the crate. The `cors` feature of tower-http is not enabled, because its layer answers a preflight request with HTTP 200.
- `Params` is a multimap of query-string and form-body fields (`application/x-www-form-urlencoded` on POST; body values append to query values). A form body larger than 8 MiB returns error 0, which bounds the memory a request takes before it is authenticated; a POST body of another content type is not read. `req_str`, `opt_str`, `opt_i64`, `opt_u32` and `opt_bool` read the first value of a name; `all(name) -> Vec<&str>` returns every value. A missing required parameter maps to error 10 naming the parameter. For the typed getters an empty value counts as absent and a value of the wrong type returns error 0 naming the parameter; `opt_bool` accepts `true` and `false` in any letter case.
- A handler is an axum handler function. Its arguments are extractors (`Params`, `State<AppState>`, `Authed`), and the method table holds it through the `handler!` macro. Handlers return `Result<Payload, ApiError>`; `Payload` is a key plus a serialisable value, or empty. Neither knows the format, so the router renders the envelope after the handler returns. `Format` is parsed from `f` before dispatch so errors use the requested format: `json` selects JSON, and `xml` or an absent `f` selects XML. Any other value, `jsonp` included, returns error 0 with message `unsupported format`, rendered in XML.
- JSON envelope: `{"subsonic-response": {"status":"ok","version":"1.16.1","type":"wn-server","serverVersion":"<crate version>","openSubsonic":true, "<key>": ...}}`, with content type `application/json`. XML: the declaration `<?xml version="1.0" encoding="UTF-8"?>` followed by `<subsonic-response xmlns="http://subsonic.org/restapi" status="ok" version="1.16.1" type="wn-server" serverVersion="..." openSubsonic="true"><key .../></subsonic-response>`, with content type `application/xml`. The envelope fields are written in this order in both formats.
- XML rendering: the payload is serialised to `serde_json::Value` and walked: scalars become attributes, objects become child elements, arrays become repeated child elements named after the key, and a scalar field named `value` becomes text content. A scalar array item becomes an element with the item as text content (`"versions": [1]` renders `<versions>1</versions>`). Attribute values and text are escaped. Characters outside the XML 1.0 `Char` production (U+0000 to U+001F other than tab, line feed and carriage return; U+FFFE; U+FFFF) are dropped from attribute values and text, because a strict parser rejects a document that holds one, escaped or not. One set of `#[derive(Serialize)] #[serde(rename_all = "camelCase")]` models serves both formats. `None` fields are skipped; empty arrays are `[]` in JSON and absent in XML.
- Payload key order: `serde_json` is built without `preserve_order`, so the keys of every payload object are sorted by their bytes (upper-case letters sort before lower-case letters). In JSON that is the order of the keys of every object. In XML it is the order of the attributes of every element, and of the child elements of every element but four. The order of attributes has no meaning in XML. The order of child elements has one: the Subsonic 1.16.1 schema (`subsonic-rest-api-1.16.1.xsd`) defines each response type as an `xs:sequence`, and a validating parser rejects a document whose child elements are in another order. `searchResult2`, `searchResult3`, `starred` and `starred2` are the elements whose child elements have more than one name. The schema sequence of each is `artist`, `album`, `song`, and the byte order of these names is `album`, `artist`, `song`. In XML each of the four elements holds every `artist` element, then every `album` element, then every `song` element, also when one of the lists is empty. `api::xml::CHILD_ORDER` holds the four names, each with that sequence. `write_element` writes the attributes in byte order and then the child elements: the names of the entry of the element first, in the order of the entry, then the other names in byte order. An entry applies to every element of its name, at any depth, and an element without an entry keeps the byte order. Every other element of §4 has child elements of one name, or none. Array items keep their order in both formats.
- Errors: HTTP 200, `status: "failed"`, `error: {code, message}`. `ApiError` variants: `MissingParam` 10, `BadCredentials` 40, `AuthUnsupported` 42, `AuthConflict` 43, `Forbidden` 50, `NotFound` 70, `Other(msg)` 0.
  - A handler answers an error of the database with error 0 and a fixed message of its own, such as `the server cannot read its library`. The error goes to the log at `error`, in the span of the request, and no part of it goes into the response: no SQL text, no name of a table and no path.
  - A read that was interrupted at its time limit (§3.4) is such an error. The client gets the message that the method has for every error of the database, and the log line holds `a statement of a read was interrupted at the time limit of 5s`.
- `EXTENSIONS: &[(&str, &[u32])]` holds the advertised extensions, one entry per line.
- The method table, `EXTENSIONS`, the fields of `AppState` (in its definition and where it is built) and the list of handler modules in `src/api/mod.rs` hold one line for each entry that this document names, and a blank line follows every entry. An entry that is not built is a comment line with its name, or a method table line that maps to `not_implemented`. A change that builds an entry replaces that line and keeps the blank lines, so two changes never touch neighbouring lines and git merges them without a conflict. The arrays, the struct and the statements that build the struct carry `#[rustfmt::skip]`, because rustfmt removes the blank lines inside an array and the blank line between a comment and the struct field after it.
- The list of the query modules is `src/db/queries/mod.rs`, which holds that list and nothing else, and the list of the library modules is in `src/library/mod.rs`. Both follow the same rule: one line for each module that §3.1 names, in that order, a blank line after every entry, and a comment line with the name for a module that is not built. Their `mod` lines carry no `#[rustfmt::skip]`, because rustfmt orders only `mod` lines that follow each other without a blank line. A query module of a group of methods adds no function to another query module (see Library queries below). The module list of the crate, `src/lib.rs`, has the union merge driver instead (`.gitattributes`).
- The texts that the change of one handler module adds to this document follow the rule as well. A comment line `<!-- api/<module>.rs -->` holds the place of the module in §4, and a comment line `<!-- tests/<file>.rs -->` holds the place of its test file in §5. A blank line follows every comment line. A change replaces its comment line with its text and keeps the blank lines. `README.md` holds no such lines: a change adds the text of a method to the section of `README.md` that describes the methods of its kind.
- Request log: one line for each request, written when the response headers are ready. Its fields are `method` (the method name), `c`, `u`, `status` (the HTTP status) and `duration_ms` (the milliseconds from the arrival of the request to the response headers). The line never holds the query string, the form body or a value of `p`, `t`, `s` or `apiKey`. The method name, `c` and `u` are cut to 64 characters, because the client chooses them. `u` is the name the request sends, whether the request is authenticated or not. A request for a path outside `/rest/` has a line with the status and no method.
  - The level is `info`. It is `debug` for `stream` and `getCoverArt`, with and without the `.view` suffix and whatever the answer is, because a client that plays music or draws a list of albums sends many of them. `api::DEBUG_LOG_METHODS` names the two.
  - The tower-http trace layer makes the span of the request and calls `api::record_response`, which writes the line. The lines that the layer writes by default at the start of a request and at the end of a body are turned off, so the request log is this one line at every log level. A request that fails authentication has the line of §3.7 as well.
  - A body that is streamed after the headers adds no time to the line and no line of its own. When the client closes the connection during a stream, the server drops the body and logs nothing: an aborted stream has the one line of its request. The trace layer adds one line at `error` for a response that its classifier names a failure. `api::Failures` is the classifier: it names every response with a 5xx status, as `tower_http::classify::ServerErrorsAsFailures` does, except a response that carries the extension `api::ChosenStatus`. `media::stream` sets that mark on the HTTP 503 of a request that got no slot, for a transcode and for an original file (§3.9): the status is the answer that the server chose, and the handler logs the reason at `info`. The line of such a request keeps its level and its `status=503`. The classifier decides from the status and not from the body, so the layer logs no line for a body that ends with an error, such as a transcoded stream that the write timeout ended (§3.9).
- Binary endpoints (`stream`, `getCoverArt`) bypass the envelope on success and use it on error.
- Model constructors `model::child(&Song, Option<&Annotation>)`, `model::album(..)`, `model::artist(..)` and the others of `api/model.rs` are the only way a handler builds an element that several methods share; the caller passes the user's annotations from `annotations::get_many(conn, user_id, ids)`. An element that one method alone returns, such as the `searchResult3` that holds three lists of these elements, is a private type in the module of its handler.

#### Library queries

`db::queries::browse` reads the library for the API. Its rows are what the response models are built from: `Artist` and `Album` (rows of their tables), `Song` (a `tracks::Track` row and whether its album has a cover), `Genre`, and the `Folder` of `db::queries::folders`.

| Function | Result |
|---|---|
| `list_artists(folder_id)` | Every artist, in the order of the natural keys. With a music folder: the artists that have a track with a file in it. |
| `artist(id)`, `album(id)`, `track(id)` | One row, or none for an ID that no row has. |
| `albums_of_artist(id)` | The albums of one artist by year, where an album without a year follows the others, then by the natural key of the title. |
| `tracks_of_album(id)` | Every track row of one album in the track order of §1.3: disc, track, path. |
| `genres()` | Each genre tag of the tracks with the number of tracks that have it and the number of albums whose `genre` it is, in the order of the names without regard to ASCII case. |
| `folders()` | The music folder rows in ID order. |
| `artists_by_ids(ids)`, `albums_by_ids(ids)`, `tracks_by_ids(ids)` | The rows of the IDs, in the order of the IDs. An ID that no row has adds nothing. An ID that the list holds twice adds its row twice. |
| `file_path(track)` | The absolute path of the file of a track, or none for a track without a file (§3.4). |

- A query module of a group of methods (`lists`, `search`, `playlists`, `play_queue`) selects the IDs of its result with its own SQL, in the order of the result, and reads the rows with the `_by_ids` functions. It needs no column list and no row reader, and it adds no function to `browse` or to the module of a table.
- `db::queries::indexes` is the query module of the folder methods. `getIndexes` and `getMusicDirectory` read their rows with the functions of the table above. The module holds what `browse` does not have: `last_modified()`, the time at which the artists last changed in Unix milliseconds, and `scan_is_open()`, whether the scan that started last has no end time. Both read the `scans` table (§4).
- A list of IDs is one parameter of a statement: a JSON array that the statement reads with `json_each`. A list of any length is one statement, and no ID is part of the SQL text. `annotations::get_many` takes its IDs the same way.
- `album_count` of an artist and `song_count` and `duration_ms` of an album are the values that the last scan stored (§3.10 step 6). A music folder filter does not change them.
- The tracks are grouped by the genre tag as it is stored, so two spellings that differ by case are two genres. The album count of a genre is the number of albums whose `genre` column holds it. That column is the genre of most tracks of the album (§3.10 step 6), so an album counts for one genre.

`annotations::get_many(conn, user_id, item_ids)` returns a map from item ID to `Annotation { starred_at, rating, play_count, last_played_at }`. The IDs can be of tracks, albums and artists at once. The two times are Unix seconds. The star and the rating of an item are those of its row. The plays of a track are those of its row. The plays of an album are the sum of the play counts of its tracks and the latest of their plays (§3.4): a second statement reads them from the rows of the tracks, which it finds through the index `tracks_album`, so it reads neither table as a whole. It runs only when the list holds the ID of an album. The plays of an artist are none, because no element reports them. The map holds an entry for each ID that has a row of the user, and for each album of which the user played a track. An item without an entry has the annotation `Annotation::default()`: no star, no rating, a play count of 0 and no play. A handler calls the function in the read transaction of its answer, so the two statements read one state of the database.

### 3.9 Streaming and transcoding

`StreamRequest { format, max_bitrate_kbps, time_offset_s, estimate_content_length }` holds what a `stream` request asks for. `StreamRequest::from_params` reads `format`, `maxBitRate`, `timeOffset` and `estimateContentLength`: an empty value is an absent one, and a value of the wrong type is error 0 that names the parameter (§3.8).

`media::stream::decide(&Track, &StreamRequest, &config::Transcoding) -> StreamPlan` with `StreamPlan::Raw` or `StreamPlan::Transcode { target, bitrate_kbps, offset_s }`, where `target` is `Target::Opus` or `Target::Mp3`. The function is the one place of the rule, and the handler does what the plan says. The rule of a local stream: the answer is the original file, unless the request asks for a format or for a bitrate below the bitrate of the file. A lossless file stays lossless otherwise.

- `format=raw` → Raw, whatever `maxBitRate` is.
- `format=opus|mp3` → Transcode to that target at `maxBitRate` when it is above 0, else at the config bitrate for that target. A file that has the format already is Raw instead, unless its bitrate exceeds `maxBitRate`: `format=mp3` on an MP3 file serves the file, and a second lossy encoding of the same format gives the client nothing. The file has the format when its suffix is `mp3` for `format=mp3` and `opus` for `format=opus`. The track row holds no codec, so an Opus stream in a file with the suffix `ogg` is not told from a Vorbis stream and is transcoded.
- No `format`, and a `format` that names none of the three → `maxBitRate` decides. Absent or 0 → Raw. Above 0 → Transcode to Opus at `maxBitRate` when the bitrate of the track exceeds `maxBitRate`; else Raw. A lossless and a lossy track follow the same rule: a FLAC file of 900 kbps is Raw for `maxBitRate=1000` and Opus for `maxBitRate=320`.
- A track whose bitrate the scan could not read: for a `maxBitRate` above 0 a lossless one is transcoded, and a lossy one is Raw.
- The bitrate of a transcode is `maxBitRate`, or the config bitrate, clamped to 32–320. In the comparison with the bitrate of the track, a `maxBitRate` below 32 counts as 32, because no transcode has less: a source of 32 kbps is Raw for `maxBitRate=8`. A `maxBitRate` above 320 is compared as it is: a source of 500 kbps is Raw for `maxBitRate=1000`, and Opus at 320 kbps for `maxBitRate=400`.
- `format` is compared without regard to ASCII case, so `RAW` is `raw`. OpenSubsonic defines `format` as the target format that the client prefers among the transcodings of the server. A value that names no target, such as `flac` or `aac`, is a preference that the server cannot meet. It is no error, and the request is decided as a request without `format`.
- `timeOffset` is the `offset_s` of a transcode. It has no effect on Raw: a client seeks in the original file with a range. `estimateContentLength` is read and has no effect on any plan (see the response of a transcode below).

Remote-mode seam: remote mode adds a connection-kind argument to `decide` (forcing Opus 192 unless the connection is direct) and a second listener in `server::run` that tags its connections. In local mode there is one `TcpListener` and no connection kind.

Raw (`media::stream::raw`) serves the original file unchanged. The path of the file is the path of the folder row of the track joined with the components of `rel_path` (`browse::file_path`); no value of the request is part of it. Two checks precede the response, and each failure is error 70. The same two checks precede a transcode (see Transcode below):

- The file is inside a configured music folder. `fs::canonicalize` resolves every symbolic link of the path, and the result must be below the resolved path of a folder of `library.folders`. A link inside a folder, a link from one folder into another one and a folder that is itself reached through a link pass. A link that points outside the configured folders does not pass. The scanner makes the same comparison before it gives a file a row (§3.10 step 3), so no row names a path that led out of the folders when the walk read it. This check is the second one. It refuses a path that leads out of the folders at the time of the request: a link that took the place of a file or of a directory since the scan, and a link whose target changed since the scan. Such a track is listed until the next scan removes its row, and `stream` answers error 70 for it. A row whose folder left the config is not served either, until a scan removes it (§3.10 step 5). `media::stream::path_in_folders` is this check. `raw` and the transcode reach it through `library_file`, and the cover service calls it for the source of a cover (§3.11).
- The file is the file that the scan saw: a regular file whose size and whose modification time in whole seconds equal `size` and `mtime` of the row. That is the test by which the scanner decides that a file did not change (§3.10 step 3). A file that was replaced, exchanged with another file or retagged since the scan is not served until the next scan stores its state, so the bytes of another file are not served under the ID. A replacement with the same size in the same second is not detected, as the scanner does not detect it.

Both checks read the path, and `ServeFile` opens the path after them, as ffmpeg does for a transcode. A file that is exchanged between the checks and the open is served for that one request. A check through the open file needs a file service that takes an open file, which `ServeFile` is not. A request that waits for a slot (Open files below) waits between the checks and the open, for 5 s at most.

The file is served by `tower_http::services::ServeFile::new_with_mime(resolved path, content type of the row)`. It answers GET and HEAD with `Accept-Ranges: bytes`, `Content-Length`, `Last-Modified` and `ETag`, a range with HTTP 206 and `Content-Range`, a range that no byte satisfies with HTTP 416 and `Content-Range: bytes */<size>`, and `If-None-Match` and `If-Modified-Since` with HTTP 304. It reads the file in chunks of 64 KiB as the client takes the body, so the memory of a response does not grow with the file. No task outlives the body, and the file is closed when the body is dropped, which is what a client that disconnects causes. The handler builds the request that `ServeFile` gets:

- A HEAD request is passed on as a HEAD request, for which `ServeFile` opens no file. Every other request is passed on as a new GET request: the router has read the form body of a POST (§3.8), and the method has no other meaning for `stream`.
- The request carries `If-None-Match` and `If-Modified-Since` of the client request, and `Range` unless the request is a HEAD, for which a range is not defined (RFC 9110 section 14.2). No other header and nothing of the URI is passed on.
- Range unit: `stream::file_request` passes `Range` on only when its value starts with `bytes=`. An origin server ignores a `Range` header whose unit it does not understand (RFC 9110 section 14.2), and `ServeFile` answers such a header with HTTP 416. A range in another unit, such as `items=0-1`, is therefore not passed on, and the response is the whole file with HTTP 200 and `Accept-Ranges: bytes`. The test is the prefix as the client wrote it. The names of range units have no letter case (RFC 9110 section 14.1), so `Bytes=0-1` names the unit that the server understands. The server ignores the header in that spelling and answers with the whole file, which section 14.2 allows for every `Range` header; `ServeFile` answers that spelling with HTTP 416. A `bytes=` range that `ServeFile` cannot parse keeps its HTTP 416. No target client sends another unit.
- `If-Range`: `ServeFile` does not read the header, so the handler evaluates it. When the answer to a range request is HTTP 206 or 416 and the `If-Range` value is neither the `ETag` nor the `Last-Modified` value of that answer, the handler drops the answer, which closes its file, and asks `ServeFile` again without the range, so the client gets the whole file. Both answers are under the one permit of the request (Open files below). A weak tag equals no `ETag`.
- Several ranges: `ServeFile` builds no multipart response. With `ignore_multi_range_requests(true)` it answers such a request with the whole file.
- A suffix range that is longer than the file selects the whole file (RFC 9110 section 14.1.2). `ServeFile` answers it with HTTP 416, so the handler passes `bytes=0-` in its place.

Open files: a response that serves the file holds it open until its body is dropped, and its connection holds a socket. A process has 256 file descriptors by default on macOS and 1024 on Linux. When none is left, `ServeFile` cannot open a file, so `stream` answers error 0, and `axum::serve` waits one second after an `accept` that fails. `AppState.streams`, a `tokio::sync::Semaphore`, bounds the files that responses of `stream` hold open.

- Values: `server.max_streams` is 64 permits, and `server.stream_permit_wait_ms` is a wait of 5000 ms. 64 open files and the 64 sockets of their connections are half of the 256 descriptors of macOS, which is the lowest default of the supported systems. The other half is left to the database connections, the scanner, the cover service, the pipes of ffmpeg and the connections of the other requests. The wait is the permit wait of a transcode, so both limits answer after the same time and with the same `Retry-After`. Both values are fields of `config::Server` and are not config keys (§3.5).
- Which requests take a permit: `ServeFile` opens the file of a GET request before it reads the conditions and the range of the request, and closes it again for HTTP 304 and 416. `raw` therefore asks `ServeFile` first with a HEAD request that carries the same headers and the same range (`stream::answer`). For a HEAD request `ServeFile` reads the state of the path and opens nothing, and the status and the headers of its answer are the ones of the GET request. A HEAD request of the client, HTTP 304, HTTP 416 and an error are answered from that first answer. They take no permit and never wait, whatever the state of the bound is. For HTTP 200 and 206 `raw` takes a permit with `acquire_owned` under a timeout of the wait (`stream::permit_of`), and then asks `ServeFile` with the GET request, which opens the file. One request costs one more read of the state of the path than a request without the bound.
- Who holds the permit: the body of the HTTP 200 or 206 response. `stream::holding` wraps `ServeFileSystemResponseBody` in the `InspectFrame` body of `http_body_util` with a closure that owns the `OwnedSemaphorePermit`. The wrapper implements `http_body::Body`, forwards every poll, the size hint and the end of the body, and changes no frame. It is that type and no type of the crate, because the crate cannot name `http_body::Frame` without a dependency on `http-body`, which `Cargo.toml` does not declare. The permit returns when the body is dropped: the client has read the response, or it has disconnected. When the GET answer has another status than 200 or 206, because the file changed after the first answer, the response holds no file, and the permit returns when the response is built (`stream::finish`).
- No path keeps a permit: the permit is an owned value of the handler and then of the body. A handler that is dropped while it waits for a permit has taken none. A handler that is dropped after it, an error of `ServeFile`, a response that is dropped unread and a task that panics with the response drop the permit with its owner.
- Past the bound: a request that gets no permit within the wait answers HTTP 503 with `Retry-After: 5`, an empty body and the CORS headers of the route (§3.8), and opens no file. It is the response of a transcode past its limit. The handler logs it at `info`, and the trace layer does not log it at `error` (§3.8). A client repeats the request after 5 s, or after it has ended one of its own streams.
- What the bound does not cover: a transcode takes no permit of it. It is bounded by `transcoding.max_concurrent`, and ffmpeg holds its file. `getCoverArt` takes none, because its service holds no file across a response (§3.11), and `download` serves no file (§4). A client that reads nothing holds its file and its permit for as long as its connection lives: the stream of an original file has no write timeout in this version. Connections are not bounded at the listener, so the sockets of requests that wait or that hold no file are not counted. tokio closes a file whose read is in progress on a blocking thread when that read returns, so a file can stay open for the length of one read of 64 KiB after its permit has returned.

A 404 from `ServeFile` (file removed after the checks) becomes error 70, and another failure status becomes error 0. `ServeFile` writes the modification time as an HTTP date and panics for a time before 1970 or after the year 9999. A row with such an `mtime` is answered with error 0 before the file is read. HTTP 200 and 206 get `Content-Disposition: inline; filename="<plain>"; filename*=UTF-8''<encoded>` with the file name from `rel_path`. `<plain>` is the name with `_` in place of every character outside ASCII, every control character, `"` and `\`. `<encoded>` is the exact name, percent-encoded outside the unreserved set of RFC 3986.

Transcode (`media::stream::transcoded`) answers a `Transcode` plan with the stream of the transcoder of the state. The two checks of Raw come first, with error 70 for each failure, and the transcoder gets the resolved path of the file. A file that `stream` does not serve as it is, is not transcoded either.

`Transcoder` is a trait with `fn spawn(&self, job: TranscodeJob) -> TranscodeFuture<'_>`. The future is boxed, so that the state holds an `Arc<dyn Transcoder>`, and it yields `Result<TranscodeStream, TranscodeError>`. `TranscodeJob { track, path, target, bitrate_kbps, offset_s }` is one transcode; `track` is the ID of the track, which the transcoder names in its log. `TranscodeStream { body, content_type }` is its stream. `FfmpegTranscoder { bin, semaphore, permit_wait, targets }` runs

```
ffmpeg -nostdin -v error -protocol_whitelist file -format_whitelist aac,aiff,flac,mov,mp3,ogg,wav [-ss <offset>] -i <path> -map 0:a:0 -vn -c:a libopus -b:a <N>k -f ogg -
ffmpeg -nostdin -v error -protocol_whitelist file -format_whitelist aac,aiff,flac,mov,mp3,ogg,wav [-ss <offset>] -i <path> -map 0:a:0 -vn -c:a libmp3lame -b:a <N>k -f mp3 -
```

- Arguments: `FfmpegTranscoder::argv(job)` is the argument vector, which starts with the program of `transcoding.ffmpeg`. `-ss` is absent for an offset of 0. The process is started from that vector with `tokio::process::Command` and never through a shell. The program and the path are one argument each, whatever characters they hold, and the other arguments are fixed texts and two numbers. A file name with spaces, with quotes or with shell syntax is therefore the name of the file and nothing else, and a name that starts with `-` is the value of `-i` and no option.
- Paths: ffmpeg reads the argument after `-i` as a URL. A text that starts with the name of a protocol and a colon, such as `concat:a|b` or `http://host/a`, is not opened as a file. An absolute path starts with a separator or with a drive, which no protocol name does, so ffmpeg opens it as a file, whatever the name of the file is. `spawn` therefore returns `TranscodeError::Spawn` for a path that is not absolute and starts no process. The path that `transcoded` passes is resolved and absolute.
- Input options: ffmpeg detects the format of a file from its content and not from its name. A file with the name of an audio file can therefore be a playlist or a script that names other files and URLs for ffmpeg to open. Two options keep a file of the library from making ffmpeg read another file or open a network connection. Both are options of the input: ffmpeg applies an option to the next file of the command line, so they stand before `-i`.
  - `-protocol_whitelist file` (`transcode::PROTOCOLS`): ffmpeg opens the input, and whatever the input names, through the `file` protocol only. That excludes every network protocol (`http`, `tcp`, `udp`, `rtp` and the others) and the protocols that wrap another resource (`concat:`, `subfile:`, `data:`, `crypto:`).
  - `-format_whitelist aac,aiff,flac,mov,mp3,ogg,wav` (`transcode::DEMUXERS`): ffmpeg reads the input only with one of these demuxers, and fails with `Format not on whitelist` for a file whose content is anything else. They are the demuxers of the audio containers that the scanner supports (§1.3), under the names of `ffmpeg -demuxers`: `aac` (raw ADTS) for the suffix `aac`, `aiff` for `aif` and `aiff`, `flac`, `mov` for `m4a` (ffmpeg lists the demuxer as `mov,mp4,m4a,3gp,3g2,mj2`, and an entry of the list matches each of its names), `mp3`, `ogg` for `ogg` and `opus`, and `wav`. The list holds no playlist format and no script format (`hls`, `concat`, `dash`, `sdp`, `image2` and the others).
  - What the whitelists do not cover: an MP4 file can name a second file as the place of its audio data (a data reference), and the `mov` demuxer, which the list needs for `m4a` files, can open that file through the `file` protocol. ffmpeg does so only with the option `enable_drefs` of that demuxer (`mov_open_dref` has one caller, which tests the option). The option is off by default, and the server does not pass it. The server relies on this default of ffmpeg. With ffmpeg 8.0, a crafted `m4a` file whose data reference names a second file in its directory gives a stream without audio, and ffmpeg logs `Skipped opening external track`; with `-enable_drefs 1` the same file gives the audio of the second file. With an ffmpeg that follows the reference, a crafted MP4 file of the library makes ffmpeg read a local file that a relative path from the file reaches, and the stream goes to the client, which is the authenticated owner. A network connection stays excluded by the protocol whitelist, and ffmpeg refuses a reference that is an absolute path. The option cannot be passed for every input: it is a private option of the `mov` demuxer, and ffmpeg fails with `Option enable_drefs not found` for a FLAC, an MP3 or an Ogg input. The other six demuxers read the one file.
  - With ffmpeg 8.0, a script of the concat demuxer in a file named `script.flac` that names a second file is transcoded as that second file without the two options, and fails with them. The ignored tests `real_ffmpeg_does_not_follow_a_playlist_with_an_audio_file_name` and `real_ffmpeg_does_not_follow_a_data_reference_of_an_mp4_file` cover the two cases (§5).
  - The options do not limit what a demuxer or a decoder does with the bytes of the file itself.
- Process: the standard input is null, the standard output is piped, and the error output is null. When the `debug` level is on, the error output is piped to a task that logs each line at `debug`, in pieces of 1 KiB at most. `kill_on_drop(true)` is set.
- Limit: a semaphore holds `transcoding.max_concurrent` permits. `spawn` waits for a permit for the permit wait of 5 s and then returns `TranscodeError::Busy`. The command is built and the process is started when the permit is held, so a job without a permit starts no process.
- End: the body is `Body::from_stream` over a stream that wraps `ReaderStream::new(stdout)` and owns the `Child` and the permit. When the stream is dropped before the output has ended, the stream calls `start_kill()`. `transcoded` and the task of the response drop it in the cases of the response below: no first output within the limit, a handler that is dropped while it waits, a client that disconnects and a client that reads nothing. When the output has ended, the process ends by itself; a process that has not ended 5 s later is killed. In both cases a task calls `wait()` and then drops the permit. The wait lets the system release the process. The permit returns after it, so the server never has more ffmpeg processes than the limit, and a response that is held after its process ended holds no permit. When the server stops, the connections close, and the handlers and the bodies are dropped (§3.13); `kill_on_drop` kills a process whose waiting task the end of the runtime drops.
- Failure: a process that ended by itself with a failure status is logged once at `warn`, with the status and the ID of the track (`transcode::log_end`). That is an ffmpeg that could not read or decode the file, and a file that the whitelists refuse. A process that failed before its first output gave its request error 0, and one that failed after it gave it an incomplete stream after HTTP 200 (First output below). A process that the server killed is not a failure and is not logged at `warn`: the stream checks with `try_wait()` whether the process has ended before it kills it, because on Windows the status of a killed process equals a failure status.
- Startup: `FfmpegTranscoder::probe(&config.transcoding)` runs the program of `transcoding.ffmpeg` twice, in `run_server` after the listener is bound: `<ffmpeg> -version`, and then `<ffmpeg> -hide_banner -encoders`, which lists the encoders of the build (`transcode::probed`). Each run waits 10 s at most, and the probe reads 64 KiB of the output of a run; the list of ffmpeg 8.0 with 204 encoders has 12 KiB. The probe closes the output at that limit, so a program that writes more ends with a failure or not within the 10 s and counts as one that does not run. No request runs the probe again.
  - The program does not run: it cannot be started, it ends with a failure status, or it has not ended after 10 s. It is not asked for its list. A program whose list cannot be read counts as one that does not run.
  - A target is available when the list holds the line of its encoder, `libopus` for Opus and `libmp3lame` for MP3 (`transcode::encoder`, which is also the value of `-c:a`). A line of an encoder holds six flags, of which the first is `A` for audio, then the name, then a description: ` A....D libopus              libopus Opus (codec opus)`. `transcode::lists_encoder` compares the second field with the whole name, so the line of the encoder `opus`, which ffmpeg has itself, is not `libopus`.
  - Log: the first line of the version at `info`, and at most one warning (`Probe::warning`). The warning names the program and the reason when the program does not run. For a build that lacks an encoder it names the encoders that are missing, the format whose requests get an error and the format that works.
  - `spawn` starts no process for a target that is not available and returns `TranscodeError::Unavailable`: for every job when the program does not run, and for the jobs of one target when the build lacks one encoder. The other target is transcoded. `decide` does not read the probe: a request with `maxBitRate` and no `format` selects Opus (§1.3) and gets the error on a build without libopus. The server runs and serves original files in each case, and no request logs the warning again.

The response of a transcode:

- First output: `transcoded` returns the response when the stream of the transcoder has yielded its first chunk that holds a byte (`stream::body_from_first_output`), so the response headers follow the first output of ffmpeg. A stream that ends before that is error 0 with the message `ffmpeg produced no output`, and not HTTP 200 with an empty body. That is an ffmpeg that failed for the file: a file that it cannot read or decode, a file without an audio stream, and a file that the whitelists refuse. The `warn` line of the process has its status, and `transcoded` logs the error of the request at `info`, so such a request has one warning. An output that cannot be read, and the limit below, are logged at `warn` by `transcoded`: the process of the first has no failure status of its own, and the process of the second is killed. A `timeOffset` past the end of the track is no such case: ffmpeg 8.0 writes the header of an Ogg or MP3 stream without audio and ends with success, and the response is that short stream.
- Limit of the first output: the wait has a limit of 10 s (`transcoding.first_output_wait_ms`, §3.5). After it `transcoded` drops the stream, which kills the process and returns its permit, logs one line at `warn` and answers the same error 0. Without the limit an ffmpeg that writes nothing and does not end holds its permit until the client disconnects. ffmpeg 8.0 writes the first byte about 40 ms after its start, for Opus and for MP3, from the start of a FLAC file of ten minutes and from `timeOffset=540` alike (measured on the development machine). 10 s is the time that the startup probe gives the same program, and it leaves room for a disk that has to spin up. A request waits 15 s at most before its answer: 5 s for a permit and 10 s for the first output.
- A handler that is dropped while it waits for the first output drops the stream with it, and the process is killed. That is the request of a client that disconnects, and every request in progress when the grace of a stop is over (§3.13): 10 s, and 1.5 s for a stop with `hurry`. The limit of the first output does not have to fit into the grace, because the stop does not wait for it: the dropped handler drops its timer and its stream, and the stream kills the process. The task that waits for the killed process returns the permit while the stop goes on, and `kill_on_drop` kills a process whose waiting task the end of the runtime drops. No response has begun in these cases, and no task was started.
- Hand-over: from the first output on, a task owns the stream (`stream::hand_over`). It sends the chunks to the body of the response through a channel that holds one chunk, and it holds the next one. The body of the response is the first output and every chunk after it, so a transcode that writes output has the headers and the bytes that the stream of the transcoder has. The task ends and drops the stream when the output has ended and the body has its last chunk, when the output fails, in which case the body ends with that error, and when the body is dropped, which is what a client that disconnects causes. It notices a dropped body also while it waits for ffmpeg, while a chunk waits for the client under the write timeout, and after that timeout. A stop closes the connections that are open at the end of its grace, which drops their bodies (§3.13), so neither the write timeout nor the limit of the first output delays a stop. The task logs in the span of the request.
- Write timeout: when the body takes no chunk for 10 minutes (`transcoding.write_timeout_ms`, §3.5), the task drops the stream, which kills ffmpeg and returns the permit, and logs one line at `info`. The server neither polls nor drops the body of a connection whose client reads nothing, so without the timeout such a client holds a permit for as long as its connection lives. The time runs only while a chunk waits for the body: the time that ffmpeg takes for a chunk does not count. After the timeout the body ends with an error behind the chunk that it holds. A client that reads again therefore gets a connection that ends without the end of the body, and not a short stream that looks whole. A client that is gone ends the task when its connection closes.
- The value of the write timeout: a client that plays a stream takes it at least as fast as it plays it. A player that stops loading when its buffer is full loads again when the buffer has drained. Media3, the player library of Android, buffers at most 50 s of audio by default (`DefaultLoadControl.DEFAULT_MAX_BUFFER_MS`), so a client that plays takes a chunk at least every 50 s. A client that is paused stops reading once its buffer is full, and it reads again when playback goes on. A timeout near the length of that buffer, such as 60 s, ends the stream of a long track during an ordinary pause. 10 minutes is longer than an ordinary pause. The cost: a client that reads nothing, because it is paused or gone, holds its permit for up to 10 minutes. `transcoding.max_concurrent` such clients make every other transcode request wait 5 s and get HTTP 503 for that time, while original files are served. ffmpeg 8.0 transcodes a FLAC file of ten minutes in about 2 s on the development machine, so a client that does not limit its buffer has the whole stream long before the timeout and holds no permit. A client that was paused for longer than the timeout gets the rest of the track with a new request and `timeOffset`.
- Headers: the `Content-Type` of the target, `Accept-Ranges: none` and `Cache-Control: no-store`. It has no `ETag`, `Last-Modified` or `Content-Disposition`. A `Range` header and the conditional headers are not read: the body is the whole stream from `timeOffset` on.
- Length: the response never has a `Content-Length`, and the body is every byte that the transcoder produces. No audio is cut. `estimateContentLength=true` changes nothing. The length of a stream is not known before ffmpeg has written it, and the estimate that the parameter asks for, the bitrate times the remaining duration divided by 8, is not close enough to announce. Measured with ffmpeg 8.0 on two files of 60 s: an MP3 stream is 514 bytes (128 kbps) and 1219 bytes (320 kbps) longer than the estimate, because of its header, so a body that is cut at the estimate loses its last frame. libopus encodes at a variable bitrate, and the Opus streams were 0.67 to 1.10 times the estimate: a body that is cut at the estimate loses up to the last tenth of the track, and a body that is shorter than an announced length ends the connection early. `transcoded` builds the body of the response from a stream, which has no known length, so no layer adds the header.
- A HEAD request gets the headers and starts no process. It therefore reports neither a transcoder that is busy nor one that is not available.
- `TranscodeError::Busy` → HTTP 503 with `Retry-After: 5` and no body. The response carries `api::ChosenStatus`, so the trace layer does not log it at `error` (§3.8). `TranscodeError::Unavailable` → error 0 `ffmpeg not available`. `TranscodeError::Spawn` → error 0 `the server cannot start ffmpeg`, and the cause is logged at `error`. A transcode without output → error 0 `ffmpeg produced no output`.

`Child.transcodedContentType` and `transcodedSuffix` are not set because the server does not transcode by default.

No transcode cache: local streams serve originals by default and transcodes happen only on request.

### 3.10 Scanner

`library::scanner::scan(db, folders, cancel, full, options) -> Result<ScanSummary>` runs on one blocking thread; an async caller runs it with `spawn_blocking`. `folders` holds the configured folder paths. `ScanOptions { batch_size: usize, on_batch: Option<Box<dyn Fn() + Send>>, progress: Arc<AtomicU64>, covers_cache_dir: Option<PathBuf> }` defaults to 500, `None`, a new counter and `None`; tests set a small batch and a hook that runs after each batch, which makes cancellation deterministic. The scan adds 1 to `progress` for each supported file it has finished with. `covers_cache_dir` is `cache/covers` of the data directory (§3.5). Every caller that scans the library of a data directory sets it to `DataDir::covers_cache_dir()`: the scan at startup, `startScan`, the periodic scan and `wn-server scan`. Without it the scan removes no cached cover, and a resized cover of an old image can be served for a new image with the same modification time. `ScanSummary { seen, added, changed, moved, removed, tags_read, albums, artists, errors }` holds the supported files seen, the track rows inserted, updated in place, relinked and deleted, the calls of the tag reader, the album rows and the artist rows in the database when the scan ended, and one message per problem of the scan: each problem that kept the scan from deleting tracks, each track that is kept without a file, and each file that is over the tag bound.

1. Insert a `scans` row with the start time in Unix milliseconds, read whether the scan before this one, in the order of the IDs, has no end time, and sync the folder rows with the configured paths (see the end of this section).
2. Load every existing track of every folder into a map keyed by `(folder_id, rel_path)` with `(id, mtime, size, fingerprint)`. Steps 1 and 2 are one transaction.
3. For each configured folder, `walkdir` with `follow_links(false)` and the entries of a directory in name order; skip entries whose name starts with `.` and the system directories of §1.3 (the name of the folder itself is exempt), names that are not valid Unicode (warning), entries that are not regular files, and unsupported extensions. A skipped directory is not walked, and a skipped entry that cannot be read is no unread path. The walk reads directory entries and file states, not file content. For each file, build `rel_path` from components. Existing and unchanged (`mtime`, `size`) → the row is present and the file needs no work. Existing and changed, or existing while `full` is set → a changed path. No row → a new path. For step 6 the walk also records each directory in which it saw a supported file, and the cover image file of each directory (§1.3) with its modification time. A cover image file that is a symbolic link is skipped, so that the scanner stores no cover that `library::covers` does not read (§3.11). A cover image file whose state cannot be read is skipped with a warning; it is no unread path, because it is the file of no track.

   Symbolic links: before the first walk the scan resolves the path of every configured folder with `fs::canonicalize`. A folder whose path does not resolve is an unread root; `stream` serves no file of such a folder either (§3.9). The walk reads a folder as a tree, and the directory behind each link that it follows as a further tree. `walkdir` follows the link at the root of each tree and no other link: the root of a tree is the folder, which can be a link, or a link that the walk resolved. The walk resolves each link that it meets in a tree with `fs::canonicalize`, unless the link has a name that the walk skips, and compares the result with the resolved folders component by component, as `stream` does. Both paths come from `fs::canonicalize`. On Windows both have the `\\?\` form. On macOS and on Windows, whose file systems ignore the letter case by default, each name has the case that the file system stores. The comparison therefore does not ignore the case. A directory junction on Windows is a link.

   - The target is outside every configured folder. The link is skipped. A skipped link is no unread path: it gives no row and no error, and it holds no deletion back. The walk reads the path of the target and nothing at the target. It lists no directory and opens no file there. The link is one line of the `debug` log, and the walk of a folder writes the number of such links in one line at `info` that names the folder.
   - The target is inside a configured folder, and the walk of that folder reaches it at its own path: no name between the folder and the target is one that the walk skips, and a file has a supported extension under its own name. The link is skipped. The file has its row at its own path. A link to the directory that holds it, to a directory above it or to the folder itself is such a link, so it starts no loop.
   - The target is inside a configured folder, and no walk reaches it at its own path: a name on the way starts with `.` or is the name of a system directory, or the file has no supported extension under its own name. The link is followed. A linked file is taken under the name of the link. A linked directory is walked after the folder, also with `follow_links(false)`, and its files have their paths through the link. The walk reads a folder first and then the directories behind its links in the order in which it met them, and the folders in the order of the config. A file has its row at the path through the first link in that order that leads to it; a later link to the same file gives no row. A directory is walked through one link in a scan. A second link to it is skipped, so the walk ends for every arrangement of links.
   - The target is no regular file and no directory: a device, a named pipe or a socket. The link is skipped, and nothing opens the target.
   - The link cannot be resolved: its target is gone, a directory on the way to the target cannot be searched, or the link leads back to itself. The link is an unread path (next paragraph).
   - On Windows a volume that is mounted at a directory is reported as a link that resolves to its own path. The walk reads it as the directory that it is.

   A row at a path that the walk does not see is the row of a file that is gone (step 4). This holds for a row at or below a skipped link. A row behind a link whose target is outside the folders is relinked when a file with its fingerprint has no row, which is the case when the directory of the target became a configured folder, and it is deleted otherwise. A row at a path through a link whose target the walk reaches at its own path is deleted when the file has a row at its own path, and relinked to that path when it has none. Step 5 decides each deletion as it decides the deletion of the row of a deleted file: a scan with an unread path deletes none of these rows, and a folder that yields no supported file keeps its rows. A deleted row takes its annotations and its playlist entries with it.

   What the walk cannot read is an unread path: the whole folder when its root cannot be read, cannot be resolved or is not a directory, and otherwise the path of the entry that failed (a directory that cannot be listed, a symbolic link that cannot be resolved, a file whose state cannot be read). A configured folder that is unavailable (§3.5) is an unread root: its path does not exist, or it cannot be listed. A scan sees one at the startup of `run` and of `scan` as at every other time. The scan does not know whether the files at and below an unread path exist, so their rows are neither matched nor deleted. It does not know which other files are there either, so no track is deleted in a scan with an unread path (step 5). The scan records an error that names the folder and the path. The walk continues with the next entry or the next folder.

   A link that cannot be resolved is an unread path and not a skipped link. The scan does not know where the link points. The target can be inside a configured folder at a place that the walk reaches through the link only, and the files of rows are then behind the link. A link whose target is on a volume that is not mounted is such a link for as long as the volume is away: the rows at and below the link stay, and the scan deletes no track. The rule for a configured folder does not cover this case alone. When the volume holds a configured folder and its mount point stays as an empty directory, that folder is no unread root. It is a folder without a supported file, which keeps the rows of that folder only (step 5), and a row behind the link is a row of the folder that holds the link. The unread path keeps that row. When the volume is back, the link resolves. A target inside the folders is read as before, and the walk finds the files at the paths of their rows. A target outside the folders makes the link a skipped link, and the rows behind it go by the rules above.

   Limits of these rules:

   - A file behind two links can have a second row for the time of an outage. The first link in the order of the walk gives the file its row. That link is out of reach for a scan when its folder is an unread root, or when the link or a directory above it is an unread path. The row at its path is kept and is not missing (step 4). The second link is then the first that leads to the file, so the file gets a second row with a new ID at the path through the second link. The first scan that reads the first link again gives the file to that link. The second row is then at a path that the walk does not see, and the scan deletes it under the rules of step 5, with the annotations and the playlist entries that the row got in between. The first row keeps its ID throughout. The case needs two links to one file that no walk reaches at its own path, in one folder or in two, and a scan in which the first one cannot be read. The walk does not limit a link to targets in the folder that holds the link.
   - A volume that is mounted at a directory below a configured folder is not protected while it is not mounted. Its mount point is then an empty directory, which the walk reads without an error. The rows of the files of the volume are rows of files that are gone, and a scan that read everything deletes them. The rule for a folder that yields no supported file covers a whole folder only (step 5). The same holds for such a mount point behind a link that the walk follows. A volume whose mount point is a configured folder has the protection of that rule.
4. Fingerprints, matching and writes:
   - Fingerprints: the fingerprint of every changed and every new file is read. The pass is skipped when no row can be matched, which is when no path changed and no file of a row is gone; every new file is then a new track. A changed path whose fingerprint equals the stored one keeps its row and has its tags re-read in place. A changed path whose fingerprint differs makes its stored row displaced and the file a candidate. A new file is a candidate. A file whose fingerprint cannot be read is an unread file: it is no candidate, its row, when it has one, stays as it is, and the scan records an error that names the file and keeps its size for step 5.
   - Missing = the rows whose file is gone, plus the displaced rows. The file of a row is gone when the walk read the path and found no file, and when the folder of the row is no longer configured. Rows at and below unread paths are not missing.
   - Matching is missing-driven, in the order of `(folder_id, rel_path)`: for each missing track, among the candidates with the same fingerprint that no earlier track took, choose the one with the same file name, then the shortest path distance (the directory steps between the two relative paths), then the order of the relative paths; a match relinks the row (`folder_id`, `rel_path`, `mtime`, `size`; tags re-read only when `mtime`, `size` or the extension differ) and counts as moved. A displaced row without a match stays at its path and takes the fingerprint and the tags of the file there, which counts as changed; when another track took that file, the displaced row leaves its path (the exchange batch below). A file that is retagged in place is the first case: the retag changes the fingerprint, no file carries the old one, and the row keeps its ID. Candidates that no track took and that update no row become new rows with new IDs. Two files that exchange paths in one interval are two displaced rows and two candidates, so both rows are relinked and keep their identities.
   - Writes: the changes are stored in batches of `batch_size` files. For each batch the tags are read first, and the fingerprints when the fingerprint pass was skipped; then one write transaction stores the batch; then `on_batch` runs. The writer is held for the statements only. A file is opened once for its fingerprint and once for its tags. The token is checked before each of these reads. When it is cancelled, the scan reads no further file, the batch is not stored and `on_batch` does not run, so a batch is stored whole or not at all.
   - The exchange batch: the changes that vacate or take the path of a displaced row are the first batch and one transaction whatever their number, because one row takes the path that another row leaves. They are the relink of a displaced row, the relink of a row to the path of a displaced row, the new row of a file at the path of a displaced row that moved, and the removal of a displaced row whose path another track takes. In the transaction the deletions run first, then every displaced row that leaves its path is given the placeholder path `/<id>`, which no file can have, and then the rows that move are given their new paths, because SQLite checks `UNIQUE(folder_id, rel_path)` per statement. A cancellation while the files of the exchange batch are read stores none of its changes.
   - A track without a file: a displaced row leaves its path in the exchange batch when its own file is found at another path, and when another track takes the file at its path. It is relinked in the first case and deleted in the second. In two cases the scan can do neither, and the row keeps the placeholder path `/<id>` as its `rel_path`: another track takes its path and an unread path or an unread file may hold its file (step 5), or its file was found and the tags of that file cannot be read. The scan records an error that names the track, its old path and the reason. The row keeps its ID and everything attached to it. It has no file to serve, and its ID does not name the file that is now at its old path. A later scan treats it as a missing row: it relinks the row when a file with its fingerprint is found and its tags can be read, and it deletes the row under the rules of step 5.
   - A file whose tags cannot be read is left for the next scan with a warning: a new file gets no row, a changed file leaves its row as it is, and a moved file does not get its row. The row of the moved file stays at its old path when no file is there, and it becomes a track without a file when it is displaced. The next scan matches the row again and reads the tags again.
   - A file over the tag bound (see "The tag bound" below) is a file whose tags cannot be read, and the rule above holds for it: a new file gets no row, a changed file leaves its row as it is with its ID and its annotations, and a moved file does not get its row. One thing differs. The scan records an error that names the file by its path below its folder, once for each scan that reads the file, because the file stays out of the library until its tags are smaller. The file is no unread path and no unread file. An unread path is a path that the walk could not read (step 3): a folder root, a directory that cannot be listed, a symbolic link that cannot be resolved, a file whose state cannot be read. An unread file is a file whose fingerprint could not be read. In both cases the scan does not know which file is there. Here the walk read the state of the file, and resolved the link when the file is behind one, and the scan read the fingerprint. The scan therefore matches the file to a missing track as it matches every file: a track with the fingerprint of the file is not missing, and its row stays where it is; a track with another fingerprint has another file. The file holds no deletion back (step 5): a scan with such a file deletes the tracks whose files are gone, in every folder. Otherwise one file would hold every deletion of the library for as long as it exists. The scan checks the token before each tag read, so a cancelled scan has the error of a file over the bound only when it read the file before the cancellation; the error then stays although the batch of the file is not stored.
5. Deletion: a missing track without a match is deleted when the scan knows that its file is gone. The scan does not know that in these cases, and the track stays:
   - The scan has an unread path. Any file may be at or below it, so no track is deleted in that scan.
   - The scan has an unread file whose size is the size at the start of the track's fingerprint (`size:hash`). The file may be the file of the track. Tracks of other sizes are not affected.
   - The track is in a configured folder that previously had tracks and yielded no supported file this scan.
   - The track is in a folder that is no longer configured, and a configured folder yielded no supported file, or no folder is configured. The files of the track may be in a folder whose volume is not mounted.

   Each case is named in `scans.error`, with the number of tracks that were kept: one message counts the tracks that an unread path or an unread file kept, and the message of a folder that is no longer configured counts the tracks kept in it. The row of a folder that is no longer configured is deleted when no track is left in it. These rules hold the deletions back on every scan, with an error each time, for as long as their cause stays: a path that cannot be read (a directory without permission, a link that cannot be resolved) until it is fixed or removed, a configured folder that is unavailable (an unplugged volume, a network share that is down) until it is back or leaves the config, and a configured folder without a supported file (an import folder that is still empty) until it holds a file.

   An unavailable folder therefore has these effects on a scan, in every configured folder and not only in its own. No track is deleted: a track of the unavailable folder stays, and so does a track of another folder whose file is gone, because that file may have moved to the unavailable folder. The scan stores every other change of the folders it read: new files, changed files, and moves between the paths it read. When the folder is back, the next scan finds its files at the paths of their rows, so each track keeps its ID and what is attached to it, and that scan deletes the tracks that were held back and whose files are gone.
6. Aggregate, in one write transaction that reads no file:
   - Delete the albums that no track row refers to, then the artists that no album row and no track row refers to. These are the only deletions of album rows and artist rows. A track that step 5 kept, and a track without a file, keep their album and their artist.
   - Set `title_lc` of every track row to the normalised form of its `title` (§3.3, `tracks::normalise_titles`). The step reads the ID, the title and `title_lc` of every row and no tag. A row that has its value is not written. Step 4 stores the value with the tags, so the step writes only the rows that were stored under another rule for the column (§3.4), in the first scan that follows, and a scan that finds nothing changed writes no track row.
   - Recompute for every album `song_count`, `duration_ms`, `year` (the smallest year of a track) and `genre` (the genre of the most tracks; the first in byte order among genres of equally many tracks), and for every artist `album_count`. A row that has its values is not written, so a scan that finds nothing changed writes no album row and no artist row.
   - Set the display names (§3.3): `name` and `sort_name` of every artist row whose name no track carries, then `name` of every album row whose name no track carries, then `artist_name` of every album row that differs from the `name` of its artist row. Each of the first two reads the tracks of one row through the index on `artist_id` or `album_id`, and stops at the first track that carries the name. A row that has its names is not written.
   - Set `cover_source` and `cover_mtime` of every album whose directory the walk saw: the absolute path and the modification time of the cover image file of the directory, else those of the cover image file of the parent directory of the album's disc directories, else `embedded:<track id>` and the modification time of the first track that has a file and a picture, else NULL for both (§1.3). The walk saw a directory when it listed the directory and saw a supported file in it. It did not see the directory of an album in a folder that is not configured or yields no supported file, a directory at or below an unread path, and the directory of a row that step 5 kept although its file is gone; the cover of such an album stays as it is stored. A walk that saw a directory listed its parent directory before, so the scan knows the cover image file of the parent directory whenever it knows the one of the album's directory. The step reads the album and the path of every track row that has a file (`albums::tracks_with_file`). From these rows it takes the albums whose tracks are in disc directories and, for each directory, whether the tracks at and below it belong to one album. A row counts while it exists, also a row that step 5 kept although its file is gone. A cover file that was replaced, added or removed, in the album's directory or in the parent directory of its disc directories, is therefore found by a scan in which no track changed.
   - Delete the `annotations` whose `item_id` is the ID of no track, album or artist.

   After the commit, with the write connection released, a scan that completed removes the stale files of `covers_cache_dir`. It lists the directory once and removes two kinds of files:

   - The files `<album id>-*` of every album that was deleted and of every album whose `cover_source` or `cover_mtime` changed. The name of a cached file holds the modification time and not the source (§3.5), so a new source with the same modification time needs the removal too. An album whose stored cover was NULL is included: the cache holds files of such an album when a scan without `covers_cache_dir` cleared its cover, and when a process ended between the commit and the removal. A file of another album stays, also when no row has the ID of that album.
   - The files `<track id>-*` of every track that has no row. The scan collects the names of the directory that start with the ID of a track, and then asks the database for each of these IDs, 500 IDs to one read connection. The cover service writes a file only for a track that has a row, and an ID is given once (§3.3), so a track that has no row after its file was listed is a deleted track. The rule needs no list of the tracks that this scan deleted. It removes the files of every track that any scan deleted: those of this scan, those that a version of the server left that removed no file of a track, and a file that the cover service wrote after the scan that deleted its track had listed the directory.

   The removal runs at the end of every scan that completed, whatever started the scan: the scan at startup, a periodic scan, `startScan` and `wn-server scan`. It runs on the thread of the scan and holds no write connection. `run` waits for no scan, so a cache with many stale files delays neither the start of the server nor a request. The scan removes entries of `covers_cache_dir` and nothing else: each path that it removes is a name that the listing of the directory returned, joined to the path of the directory. It builds no path from an ID, a size or another value. It writes no file in the cache, and it removes, renames and writes no file of a music folder. An entry that is a symbolic link is removed as a link, and its target stays. A file that cannot be removed stays, with a warning. When the database cannot be read, the files of the tracks stay, with a warning, and the next scan removes them.

   A cancelled scan sets the normalised titles, runs the recomputation and sets the display names only: it deletes no album, no artist and no annotation, sets no cover and removes no file of the cover cache. It has not stored every change it found, so an album without a track may get a track from a file whose change waits for the next scan, and a row may name a path at which the walk saw no file. Until a scan completes, an album that lost its tracks is listed with `song_count` 0 and a new album has no cover. Step 6 keeps no state between scans: a scan that completes sets the counts and the covers of every album, also of albums whose tracks an earlier scan stored without reaching step 6.
7. Close the `scans` row (`scans::finish`) with the counts, with `error`, with `changed_library` and with the end time.
   - `error` holds the messages of the scan joined with `; `, `cancelled` for a cancelled scan, or the database error that ended the scan.
   - `changed_library` is 1 when the scan changed the library, and 0 otherwise. The scan changed the library when one of these holds:
     - A transaction of step 4 wrote a row: a track row that was inserted, updated in place, relinked, deleted or given its placeholder path, with the album rows and the artist rows that were made for it. A track row that is given its placeholder path and kept is in none of the four counts.
     - Step 5 deleted a track row.
     - Step 6 deleted or wrote an album row or an artist row, or set `title_lc` of a track row. The deletion of annotations in step 6 does not count, and neither does the removal of files from the cover cache.
     - The scan before this one has no end time (step 1). The process of that scan ended before the scan did, and the rows that it stored are covered by no `scans` row with an end time.

     The scanner does not derive the flag from the counts or from `error`. The transactions of steps 4 and 6 report whether they wrote a row, which they read from the number of rows that SQLite counts for the statements of a connection (`sqlite3_total_changes`), and step 5 reports the number of track rows that it deleted. A scan that found nothing changed has the flag 0, because a row that has its values is not written (step 6). A cancellation, an unread path, an unread file and a database error do not set the flag by themselves: a scan that was cancelled before it stored a batch has the flag 0, and a scan that was cancelled or that a database error ended after it stored a batch has the flag 1. A batch that a cancellation stops is not stored (see below) and does not count. A scan that could not read a path and stored no change has the flag 0, each time it runs.
   - The end time is the time of the clock in Unix milliseconds, or the latest end time of the other rows plus one millisecond when that is later. Scans run one at a time (see below), so the end times are strictly increasing in the order of the scans, also when two scans end in one millisecond and when the clock of the host went back. After the clock went back, the end time of a scan can be ahead of the clock by the difference, until the clock has passed the latest end time. `lastScan` of `getScanStatus` (§4) shows such an end time. The statement reads the end time of every other row, once for each scan.

First-scan cost: the fingerprint reads up to 128 KiB per new file (12.8 GB for 100 000 files), which is acceptable on a local disk and slow on a network share; later scans fingerprint only new and changed files.

#### The tag bound

`library::tags` reads a file for the scanner (`read`) and for the cover service (`read_front_picture`). Each read takes at most 32 MiB of the file (`tags::MAX_TAG_BYTES`). The value is twice the 16 MiB that the cover service accepts for one picture (§3.11), so a tag with a picture of that size is read, also in Vorbis comments, which hold a picture in Base64. lofty has no option for this. Its `ParseOptions` choose what is read and not how much. Its `GlobalOptions::allocation_limit` of 16 MiB holds for one item of a tag and not for the number of items, and it does not hold for a frame of an ID3v2 tag in an MP3 file, which lofty reads without it. The bound is therefore built in `library/tags/bound.rs`, in two parts with the one limit:

- The headers. Before lofty reads a file, `bound::declared` reads the container headers and adds up the sizes that they declare for the parts that lofty reads into memory. A file whose headers declare more than the bound is refused. The walk reads headers of a few bytes each and at most 4096 of them, and no byte of a tag, of a picture or of the audio. A header declares its size whether or not the bytes are in the file, so a file of ten bytes that declares a tag of 256 MiB is refused after fewer than 40 bytes are read, and nothing is allocated for its tag.
- The reader. lofty reads every file through `bound::Capped`, which hands out 32 MiB of the file and fails every read after that. It counts the bytes of all three steps of a read: the detection of the format, the headers, and lofty. A file that asks for one byte more is refused, whatever lofty returned. This part holds for every container and for whatever the first part does not see.

lofty detects the format, and the file is measured as that format. What the headers declare, for each format that lofty detects:

| Format | What is added up | The reader |
|---|---|---|
| FLAC | An ID3v2 tag before the stream marker, the first metadata block, and every block of the types `VORBIS_COMMENT` and `PICTURE`. Padding, seek tables and other blocks are not read into memory and are not added | applies |
| MP3, ADTS AAC | The ID3v2 tags at the start of the file, and the ID3v1 tag and the APE tag at its end | applies |
| MP4 (M4A) | The first `moov` atom, which holds the `ilst` tag and the sample tables | applies |
| Ogg Vorbis, Opus, Speex | The header packets, three for Vorbis and two for the others; the comment packet is one of them. The segment tables of the pages give the sizes | applies |
| WAV | The chunks `LIST`, `ID3 `, `id3 ` and `fmt ` | applies |
| AIFF | The chunks `ID3 `, `id3 `, `NAME`, `AUTH`, `(c) `, `ANNO`, `COMT` and `COMM` | applies |
| Monkey's Audio, Musepack, WavPack, which lofty detects by content in a file with a supported extension | Nothing: no header is read | applies, and is the only part |

The walk of the headers follows the layout of each format and not every case that lofty accepts. It does not see zero bytes before an ID3v2 tag, an ID3v2 tag behind other bytes at the start, an APE tag at the start of an MP3 file, or an atom layout that lofty reads in another way than the format describes. In each of these cases the reader is the limit: lofty reads up to 32 MiB of the file and is stopped there.

A refused file never panics the scanner or the cover service; it is an error value. A file that is cut inside its tag is not over the bound. lofty fails to read it and returns an error, with at most one allocation of the size that the header before the cut declares, which the bound and lofty's limit of 16 MiB for one item keep small.

Memory. For a refused file the read takes the bytes of the headers. For a file within the bound, lofty holds what it builds from at most 32 MiB of the file:

- The bytes. lofty holds the bytes of the tag, and for a time a second copy of an item: a FLAC block and the picture taken from it, an Ogg packet and the comment taken from it, and a buffer that grows by doubling while a frame or a packet is read. `read_front_picture` copies the picture that it returns. By these copies the bytes take at most four times the bound, 128 MiB. The figure follows from the code of lofty 0.25.4 and is not measured. For the properties of an MP4 file, lofty also reserves 8 bytes for each entry that an `stts` atom declares, before it reads the entries, and its limit of 16 Mi holds for the number of entries: up to 128 MiB of address space, of which the entries that are read are used.
- The items. lofty builds a structure for each item of a tag, and a second one when it converts the tag to its common form: 48 bytes for a Vorbis comment, 144 for an ID3v2 frame, 64 for an APE item, 128 for an MP4 atom, and 64 for an item of the common form. The smallest item takes 5 bytes of a file in Vorbis comments and 11 bytes in ID3v2. A tag that consists of millions of such items therefore takes many times its size in the file: For Vorbis comments, lofty reserves 12 times the size of the block for the number of items that the block declares, before it reads them, and the items in the common form take 13 times: about 26 times the size together with the block. An ID3v2 tag takes about 23 times its size: 208 bytes and the text of the frame ID for each 11 bytes. A vector that grows by doubling has up to as much spare capacity again, which gives about 40 times at most. These are estimates from the sizes above and not measured figures. For a tag of 32 MiB they are about 750 MiB to 1.3 GiB. The bound limits the bytes and not the number of items, and lofty has no option for the number.

Reads at the same time. The server has two callers of the tag reader, and each reads one file at a time. The scanner reads the tags of one file after the other on its one thread, and one scan of a library runs at a time (see the scan triggers below). The cover service reads the picture of one file while it holds its one permit (§3.11). So at most two tag reads run at the same time in the server process: one of the scan and one for a cover. The memory of a read is freed before the next file is read, so a scan takes the memory of one read and not the sum over its files. The worst case of a scan together with a cover request is therefore twice the worst case of one read: 256 MiB for the bytes, and by the estimate above up to 2.6 GiB for the items of two tags of 32 MiB that consist of the smallest items. A `wn-server scan` process holds one read.

Present limits of the bound:

- A compressed ID3v2 frame is not bounded. The bound limits the bytes that lofty reads and not what lofty makes of them. lofty is built with its default feature `id3v2_compression_support` and inflates such a frame without a limit. A unit test in `src/library/tags.rs` holds the figures: for an MP3 file of 67 547 bytes with one compressed picture frame and a limit of 64 KiB, lofty reads less than the limit and holds a picture of 10 320 001 bytes, 158 times the limit. With that stream a frame of 32 MiB inflates to 5 GiB, and Deflate allows about 1000 times the size. `Cargo.toml` cannot turn the feature off: lofty 0.25.4 does not compile without it, because the code that it then uses names two types that are not in scope there.
- The number of items is not bounded, as described under Memory.
- An MP4 file is refused when its `moov` atom is over the bound. The atom also holds the sample tables, which take about 170 bytes for each second of AAC audio, so a file of more than 50 hours is refused without a large tag.
- An ADTS file (`.aac`) is refused when it is larger than about 900 MiB at 128 kbit/s. lofty reads the header of every frame for the bitrate, by its code about 13 bytes for each frame, and these bytes count. The size is an estimate; the suite has no ADTS file.
- A file that starts with more than 32 MiB of zero bytes or of other bytes that are no audio frame is refused, because lofty reads them one by one.
- A part of a tag of more than 16 MiB that lofty reads into one allocation is refused by lofty's own limit, within the bound: an ID3v2 tag before a FLAC stream, an `ID3 ` chunk of a WAV or an AIFF file, the `ilst` atom of an MP4 file, and one comment in the Vorbis comments of an Ogg file. lofty returns an error, so the file is a file whose tags cannot be read: the scan logs a warning and records no error. A FLAC block is under 16 MiB by the three bytes of its size, and a frame of an ID3v2 tag in an MP3 file is not under that limit.

Cancellation is checked during the walk, before each file read and between batches. A file read is the read of one fingerprint or of the tags of one file, in the fingerprint pass and in a batch. After the cancellation the scanner finishes at most the file read in progress. A cancelled scan keeps the batches it committed and stores nothing of the batch it was reading; the next scan finds the changes of that batch again. It deletes nothing: step 5 does not run, because a scan that has not read every file does not know that the file of a row is gone. Of step 6 it runs the normalised titles, the recomputation and the display names only.

Scan triggers (`library::scan_controller`): one scan of a library runs at a time. The scan decides its changes from the rows it read at its start (step 2), and a second scan that writes rows in the meantime would make those decisions stale. Two rules keep it to one scan:

- `ScanController` in `AppState` runs the scans of the server process: the scan at startup, the periodic scans and `startScan`. `start(full) -> Started | AlreadyRunning | RunningElsewhere` starts a scan with `spawn_blocking` and returns without waiting for it, so a scan delays no request and not the start of the server. `status() -> { scanning, count }` reports whether a scan of the controller runs, and the `progress` counter of the scan that started last. The counter is 0 when a scan starts and keeps its value when the scan has ended.
- `ScanLock` is an exclusive lock of the operating system on the file `scan.lock` in the data directory (`File::try_lock`: `flock` on Unix, `LockFileEx` on Windows). Every scan holds it from its start to its end: a scan of the controller and a scan of `wn-server scan`. A process asks for the lock without waiting. The operating system ends the lock when the process ends, so a process that was killed leaves no lock behind.

| Trigger | No scan runs | A scan of the server process runs | Another process holds the scan lock |
|---|---|---|---|
| startup, with `library.scan_on_start` | starts a scan that is not full | does not occur: the controller is new | starts none and logs a warning |
| periodic, with `library.rescan_interval_minutes > 0` | starts a scan that is not full | starts none; the next one is due one interval later | starts none and logs a warning |
| `startScan` | starts a scan, a full one with `fullScan=true`, and answers `scanning: true` | starts none and answers `scanning: true` with the count of the running scan | starts none and answers error 0 `another process is scanning the library` |
| `wn-server scan` | scans in its own process (§3.6) | scans nothing and exits with 1 | scans nothing and exits with 1 |

No trigger queues a scan. A `fullScan=true` or a `--full` that finds a scan running is not carried out, and the caller asks again. When the lock file cannot be opened or locked, no scan starts: `startScan` answers error 0, the startup and the periodic trigger log a warning, and `wn-server scan` fails.

`run` (`server::start_scans`) works in this order after it has bound the listener and before it serves the first request. A second server on the same data directory fails at the bind, so it stores no folder and starts no scan.

1. It stores the configured folders in the `folders` table (see the folder sync below), so folder listings are right without a scan. It reads no folder, so a folder that is unavailable gets its row or keeps it.
2. It builds the controller with `DataDir::covers_cache_dir()` and `DataDir::scan_lock_path()`.
3. With `library.scan_on_start` it calls `start(false)`.
4. With `library.rescan_interval_minutes > 0` it starts a task that calls `start(false)` every interval, the first time one interval after the start.

`run` waits for no scan. The token of the controller is a child of the token that asks the server to stop, so a stop cancels the running scan and ends the periodic task at once. Step 3 of the stop waits for both, for a limited time, and the scan ends as a cancelled scan (§3.13).

The controller keeps no state of a scan that has ended. After a scan that recorded errors, after a scan that a database error ended and after a scan whose thread panicked, `scanning` is `false`, the lock is free and the next trigger starts a scan. The errors of a scan are in `scans.error` and in the log.

The walk sees each directory once. A file that moves during a scan from a directory the walk has not reached into one it has passed is not seen in that scan: its row is deleted, and the next scan inserts the file with a new ID. A walk without a filesystem watch cannot see such a move.

Album and artist rows are upserted by natural key when a track row is written, so a track that is written finds the row of its key with the ID the row has. A new album row takes the compilation flag of the track; a later track with the flag sets it. Nothing clears the flag while the album row exists. A new album row and a new artist row take the spelling of the names in the tags of that track. A later track with the key of a row does not change `name`, `sort_name` or `artist_name` of the row when it is written; step 6 sets them (§3.3). A correction of the tags that keeps the key, such as the capitalisation of an album title, therefore shows on the album row when no track carries the old spelling. A change of the key makes a new row with a new ID.

Folder sync at `run` and at the start of every scan: folders from config are upserted by path. The stored path is rebuilt from `Path::components()`, so a trailing separator, a `.` component or a repeated separator does not make a second row for one directory; `..` components are kept, as `std::path::absolute` keeps them. The name of a folder is the last component of its path (the whole path for a root such as `/` or `C:\`). A folder removed from config has its tracks deleted and its row removed in step 5 (tracks of a folder whose path changed are relinked by fingerprint into the new folder row first, because deletion happens after matching). The sync at `run` only upserts, in one transaction. It deletes no folder row and no track row, so a folder that left the config keeps its row and its tracks until a scan applies the rules of step 5. The sync reads no folder at `run` and at the start of a scan: a configured folder that is unavailable (§3.5) gets a row when it has none, and keeps its row and its tracks when it has them. Its row is that of a configured folder, so the rules for a folder removed from config do not apply to it.

### 3.11 Cover art

`library::covers::Covers` is the cover service. `Covers::new(cache_dir, db, folders)` takes `cache/covers` of the data directory (§3.5) and the configured music folders, and `AppState` holds the value; its clones share the cache and the work in progress. `get(id, size: Option<u32>) -> Result<Option<Cover>, CoverError>` returns `Cover { bytes: Bytes, content_type: &'static str, mtime: i64 }`. `mtime` is the modification time that the last scan stored for the source of the cover. `CoverError` is a database error, or `Unfinished` when the work on the cover ended without a result, which happens when the runtime shuts down. Every other failure is `None`.

Resolution:

- `al-` → the cover that the last scan stored for the album: `cover_source` and `cover_mtime` of the row that `browse::album` returns (§3.10 step 6). The source is the absolute path of an image file, or `embedded:<track id>`, which is the embedded picture of that track. An album without a stored cover → `None`.
- The image file of an album is the cover file in the album's directory, which is the directory of its first track. An album without one whose tracks are in two or more directories of one parent directory, as `Album/CD1` and `Album/CD2` are, has the cover file of that parent directory, when no track of another album is at or below the parent directory (§1.3). The scanner applies the rule and stores the path. The service opens the stored path and searches no directory.
- `tr-` → the embedded picture of the track when `has_picture`, with the modification time of the track.
- A track without a file (§3.4) gives no picture, for its own ID and as the source of the cover of an album. `browse::file_path` returns no path for it.
- A track whose file is over the tag bound (§3.10) gives no picture, for its own ID and as the source of the cover of an album. The tag of the file is not read. The result is `None`, as for a file without a picture, and nothing is recorded for the request: the scan records the file.
- An ID that `ids::parse` rejects, an ID of another kind and an ID that no row has → `None`.
- The embedded picture of a track is its first picture of the type front cover, or its first picture when none has that type; M4A stores no picture type.

Result:

- No `size`, and `size` 0: the bytes of the image file or of the embedded picture, when they start with the header of a JPEG, PNG or WebP image (see Files). The content type is the type of that format: `image/jpeg`, `image/png` or `image/webp`. The extension of the file and the MIME type that a tag names do not decide it. The image is not decoded, so an image with a whole header and damaged data is returned as it is. The service changes no byte of the source: the image keeps its metadata, and the orientation that it declares is not applied (see Orientation).
- `size`: a JPEG of quality 85 whose longer side is at most the step of `size` (see Sizes). The image is decoded with `image`. An image with a side over the step is scaled down with `thumbnail(step, step)`, which keeps the proportions. An image whose sides are within the step keeps its size and is encoded as a JPEG; no image is enlarged. The pixels are converted to 8-bit RGB, which drops an alpha channel, and are then turned and mirrored as the orientation of a JPEG says (see Orientation). The cover is read from `cache/covers/<id>-<step>-<cover_mtime>-<version>.jpg` (see Cache version). On a miss it is made, written there and returned.
- An image that cannot be decoded logs a warning and gives `None` for a request with `size`: a damaged image, an image over the limits below, and a WebP image that is lossless or in the extended file form.
- A source that is gone or that cannot be read gives `None` without `size`, and with `size` when the cache does not hold the cover. `library::covers::load` logs a source that is gone at `debug` and a source that cannot be read at `info`, not as a warning. A client asks for the cover of every item of a list, so the line is written for each request while its cause stays, and the scan has reported a folder that cannot be read once, as a warning (§3.10).
- A source outside the configured music folders gives `None` with and without `size`, also when the cache holds a cover of it (see Files).

Sizes: a `size` is served at its step. The steps are 80, 160, 320, 640, 1280 and 2000 pixels (`covers::SIZE_STEPS`); each is twice the one before it, up to the limit of 2000. `covers::served_size` returns the step of a size: the smallest step that is not smaller than the size, and 2000 for every larger size. The sizes 290, 300 and 310 have the step 320. A size is rounded up and never down, so a client gets at least the pixels that it asked for, unless the image has fewer: for `size=300` an image of 1000 pixels gives a JPEG of 320 pixels, and an image of 200 pixels gives a JPEG of 200 pixels. For `size=5000` an image of 4000 pixels gives 2000 pixels, and an image of 1000 pixels gives 1000 pixels. The step is rounded before the cache is read, and it is the size in the name of the cache file and in the entity tag (§4), so the sizes of one step are answered with the same bytes from one file. The series holds 320 and 640, so the sizes 300 and 600 get a JPEG that is 20 and 40 pixels larger than they asked for.

Orientation: a JPEG can declare an orientation in its Exif metadata. It is one of eight values: the image as it is stored, a half turn, a quarter turn to either side, and each of these four mirrored. A viewer applies it before it shows the image. A resized cover of a JPEG has the orientation applied to its pixels and holds no metadata, so a client shows it as a viewer shows the source. A cover without `size` is the bytes of the source, and the client applies the orientation that they declare.

- The service reads and applies the orientation with `image`, without a dependency of its own for metadata. `ImageDecoder::orientation` of the JPEG decoder returns the value of the entry with the tag 0x0112 in the first directory of the Exif data, and `DynamicImage::apply_orientation` turns and mirrors the pixels.
- The orientation is applied after the image is scaled down and converted to 8-bit RGB. The step bounds the longer side, which no orientation changes, so the cover has the size that the turned image has at that step. An image that is stored 1000 × 2000 pixels and declares a quarter turn is shown 2000 × 1000 pixels, and its cover at the step 320 is 320 × 160 pixels. An image within the step is turned and keeps its pixels.
- The orientation is the value of the first entry of the directory that has the tag 0x0112 and holds a single 16-bit number. The reader passes over an entry with the tag that has another format or another count, as it passes over an entry with another tag, and goes on with the next entry.
- An orientation that cannot be read counts as none, and the image is resized as it is stored. That holds for a JPEG without Exif data, for a directory in which no entry holds the orientation, for a value of that entry that is none of 1 to 8, which ends the read, for data that starts with no byte order of TIFF, for a directory offset outside the data, and for data that ends before the end of the entry.
- A file that ends inside its Exif segment has a damaged header, and so has a file whose Exif segment declares a length of less than 2 bytes or of more bytes than the file holds. Such a file is not decoded and not served, as every other file with a damaged header (see Result and Files). A segment that declares fewer bytes than it holds gives those bytes as the Exif data, and the decoder passes over the rest up to the next marker.
- The Exif data of a JPEG is one segment of at most 64 KiB. The decoder copies the segment for the read (see Memory). The reader takes the 12 bytes of each entry of the first directory in turn, and it stops at the entry of the orientation or at the end of the data. It follows no offset but the one of the first directory, and it allocates nothing. Data that declares 65535 entries is therefore read once to its end.
- The orientation of a JPEG is the only metadata that the service reads. A WebP image that the service decodes is in the simple file form, which holds no metadata.

Cache size: the cache holds at most six files of one version for one cover and one modification time, one for each step. Together they hold at most 80² + 160² + 320² + 640² + 1280² + 2000² = 6 182 400 pixels. The service sets no limit on the bytes of a JPEG that it encodes, so the bytes follow from two measured figures. An image of noise, in which each channel of each pixel is 0 or 255, takes 2 bytes for a pixel at most; a unit test checks this figure. It is the largest figure that was measured, and the JPEG format allows more. A photograph takes less: an image of gradients with fine noise, which was measured in its place, takes about a quarter of a byte for a pixel. With the first figure the six files of one cover take 11.8 MiB, and with the second one 1.5 MiB, both for an image that is larger than every step. An album has one cover, whose ID is the ID of the album. A track whose file holds a picture is a cover of its own when a client asks for it by the ID of the track, which `coverArt` names only for a song whose album has no cover (§3.8). An album with n such tracks therefore has at most 6 × (1 + n) files, which are 11.8 × (1 + n) MiB with the first figure. The files of an old modification time are removed for an album and stay for a track (see Present limits).

Cache version: the name of a cache file and the entity tag of a resized cover (§4) end with the version of the resized covers, `covers::CACHE_VERSION`, which is 2. A change of the service that makes other bytes from the same image at the same step raises the version. A cover of version 2 has the orientation applied, and a file without a version in its name has not. The service builds the name of a file with its own version, so it reads and writes the files of that version and of no other. A cover that another version cached is therefore not served: the first request makes it again from its source. The entity tag of such a cover is not the tag of the cover now, so a client that holds it and asks again gets the new cover and not HTTP 304. `Cache-Control` lets a client use a cover for one day before it asks again. The version is no part of the entity tag of a cover without `size`, whose bytes the service does not make. The scanner reads the cover ID at the start of a name and no other part (§3.10 step 6), so it removes the files of every version for an album whose cover changed and for a track without a row. The other files of another version stay (see Present limits).

Values from the client: `id` and `size` come from the client, and neither is part of a file path. The ID selects a row, and the service opens the path that the scanner stored for that row. A stored cover source that is not an absolute path with the extension `jpg`, `jpeg`, `png` or `webp` is not opened. The name of a cache file is built from the ID that the row holds, the step of the size, the stored modification time and the version of the resized covers, which is a constant. `cache_name` builds a name only from an ID in the form that `ids::parse` accepts. A name therefore holds two letters, hex characters, digits, hyphens and `.jpg`, and no path separator: it is one component of a path, and the file is in the cache directory. The service writes its files there and in no other directory.

Files: the files come from the music folders. A file there can be damaged, and it can be put there to make the server return another file or to exhaust its memory. Three rules hold for every request. The first keeps the service from reading a file outside the configured folders, the second keeps it from reading an image file through a link, and the third keeps it from returning a file that is no image.

- No source outside the configured music folders is read. The service resolves every symbolic link of the path of a source with `fs::canonicalize`, and the result must be below the resolved path of a folder of `library.folders`. The check is `media::stream::path_in_folders`, which `stream` applies to the file of a track (§3.9): the two methods share the function, so a track and a cover are under one rule. The source is the image file of an album or the audio file that holds a picture. A regular cover file in a directory that is reached through a link to a place outside the folders is therefore not served, and a link inside a folder, a link from one folder into another one and a folder behind a link pass. The scanner follows no link out of the folders (§3.10 step 3), so a row names such a path when a link changed after the walk, and when the row is older than that rule and no scan has removed it. The source of a row whose folder left the config is not served either, until a scan removes the row (§3.10 step 5). The check runs before the source is read and, for a request with `size`, before the cache is read: a source outside the folders gives `None`, is not decoded, gets no cache file, and a cover that the cache holds for it is not returned. The refusal is one line of the log at `info`, as for `stream`. A path that cannot be resolved names a source that is gone or that cannot be read; the cache answers for it, and no such source is read.
- No symbolic link is followed to an image file. The service reads an image file when its path names a regular file. It reads the state of the path without following a link (`fs::symlink_metadata`), and the file that it then opens must be the file of that state. On Unix it compares the device and the inode. The standard library gives no file identity on Windows, where the test of the path is the only one and creating a link needs a privilege. A path that names a link, a directory or a device gives `None`, with and without `size`. A directory in the path can be a link when the first rule lets it pass. The scanner follows the same rule: it stores no link as the cover of an album (§1.3, §3.10 step 3), so such an album has its embedded picture as its cover, or none. A cover file in the parent directory of disc directories is under the rule as one in the album's directory is: a link there, to a file inside or outside the music folders, is not stored and not read. The rule also holds for a file of the cache.
- Only an image is returned. Without `size` the service returns the bytes of a source when the decoder of JPEG, PNG or WebP accepts their header. It reads the header and no pixel. With `size` the service returns the JPEG that it encoded. Other bytes give `None` and a warning: text, a file of another kind under the name of a cover, and a picture in GIF, BMP or TIFF, for which `image` is built without a decoder.

An audio file is read through a symbolic link whose target is inside a configured folder, as the scanner reads it (§1.3). The service takes from an audio file the picture that lofty finds in its tag, under the third rule, and never the bytes of the file.

Limits:

- A source image of more than 16 MiB has no cover, with and without `size`. The service checks the size itself: of an image file before it reads the file, and of an embedded picture when the tag reader has returned it. 16 MiB is the limit of lofty for one allocation, which holds for a picture in a FLAC block, in Vorbis comments and in an MP4 atom, and not for a picture frame of an ID3v2 tag in an MP3 file (§3.10, "The tag bound").
- An image is decoded when its width and its height are at most 4096 pixels and its decoded pixels take at most 64 MiB, which is an image of 4096 × 4096 pixels with four bytes for each pixel. Both are set as `image::Limits`. The decoder reads the size from the header of the image and returns an error before it allocates the pixels, so a small file that declares a huge image takes no memory.
- A WebP image is decoded when it is lossy and in the simple file form, which is a file whose first chunk is `VP8 `. For a lossless image and for the extended file form, which holds an alpha channel, an animation or metadata, the WebP decoder builds tables and planes whose size the two limits above do not bound.
- The service holds the source of one image at a time. One permit of a semaphore covers the read of a source and then its verification, or its decoding, scaling and encoding. A job and a request without the permit wait without a thread.
- Reading, verifying, decoding and encoding run on `spawn_blocking`. A tag reader or a decoder that panics gives `None` and a warning.

Memory: with these limits the work of the service on images takes 242 MiB at most. It is the largest sum in the table. Each row counts the buffers that exist at one time: the copies of the source, the working memory of the decoder, and the pixels. An image of 4096 × 4096 pixels has 16 Mi pixels, so one byte for each pixel is 16 MiB.

| Case | Copies of the source | Decoder and pixels | Sum |
|---|---|---|---|
| JPEG with four components that is progressive or has a scan for each component | 64 MiB: the source (16), the copy that `image` hands to zune-jpeg (16), and the metadata segments that zune-jpeg copies and joins (32, for a file that holds nothing else) | 178 MiB: two bytes for each coefficient of each component (8 × 16 = 128), the RGB pixels (3 × 16 = 48), and the buffers for one row of blocks (2) | 242 MiB |
| JPEG with three components, of the same kind | 64 MiB | 146 MiB: coefficients (6 × 16 = 96), pixels (48), row buffers (2) | 210 MiB |
| JPEG, baseline with one scan | 64 MiB | 50 MiB: pixels (48), row buffers (2) | 114 MiB |
| PNG | 32 MiB: the source (16), and its text chunks as strings, which can take twice their bytes (16 more) | 128 MiB: the pixels (64), and the buffers of the `png` crate, which holds them under the same limit of 64 MiB: one chunk, the ICC profile and the text chunks | 160 MiB |
| WebP, lossy, simple form | 64 MiB: the source (16) and the copies of its partitions (48 while the last one is read, 16 after) | 76 MiB: the RGB pixels (48), the three planes of the frame (1.5 × 16 = 24), the records of the macroblocks (4) | 140 MiB |
| Reading the orientation of a JPEG, before its pixels are allocated | 64 MiB: the source (16), the copy that `image` hands to zune-jpeg (16), and the metadata segments of one more parse of the header (32); with them a second copy of the Exif segment (64 KiB at most) | none | 64 MiB |
| Scaling and encoding, when the decoder and the source are freed | none | 95 MiB: the pixels (64) and the scaled pixels (31, for 2000 × 2000 pixels of 8 bytes); after that the scaled pixels and their RGB form (12); then the RGB form and, for an orientation with a quarter turn, its turned copy (12); then the RGB pixels and the JPEG | 95 MiB |
| Verifying a cover without `size` | as in the rows above | no pixels; for PNG the buffers of the `png` crate (64) | 96 MiB |

The orientation adds to no sum. It is read while no pixels exist, and the buffers of that read are freed before the JPEG is decoded. It is applied to the scaled pixels in 8-bit RGB, which are 2000 × 2000 pixels of three bytes at most. A half turn and a mirroring change them in place, and a quarter turn writes them to a second buffer of that size. Applied to the decoded pixels, the second buffer would hold up to 64 MiB.

The figure leaves out two things. The read of the tag of an audio file, which finds the embedded picture, is under the tag bound and has the memory that §3.10 states for it ("The tag bound"); it runs under the permit, before the work on the image, and its memory is freed when the picture is returned. The scanner reads the same tags on its own thread. A cover that `get` returned is held by its request until it is sent: at most 16 MiB for each request in progress.

Requests at the same time: the first request for a resized cover that the cache does not hold starts a job in a task of its own, under the name of the cache file. Every request for the same file while the job runs waits for that job and gets its result, a failure included, so the image is decoded once. The job looks in the cache again before it decodes, because another job can have written the file after the request looked. Jobs for different cache files wait for the one permit in the order in which they asked. A job that waits for the permit is dropped when no request waits for it any more, so a client that ends its requests leaves no work in the queue. A job that has the permit runs to its end and fills the cache, also when every request that waited for it is gone. A request that comes while a job is dropped starts a new job. A request without `size` waits for the permit itself and leaves the queue when it ends.

Cache writes: the JPEG is written to the new file `tmp.<32 hex characters>` in the cache directory, flushed to the disk and renamed (§2), so a reader opens the whole file or none. The file is flushed before the rename, so that a power failure leaves no file with the final name and without its bytes. The directory is not flushed: a power failure can undo the rename, and the cover is then made again. The service creates the cache directory at the first write. A cover that cannot be written to the cache is returned without being cached, with a warning. The scanner removes every file of the cache whose name starts with the ID of an album and a hyphen when the cover of that album changes or the album is deleted, and every file whose name starts with the ID of a track that has no row and a hyphen (§3.10 step 6), so the name of the temp file has no hyphen and starts with no cover ID.

Present limits:

- The cache has no limit on its total size, and no file is evicted. A cover has one file for each of the six steps that a client asked for, also when the files hold the same JPEG because the image is smaller than the steps.
- The files of a track keep the modification time of its file in their name. After the file changed they are not read again, and they stay until the row of the track is deleted. A scan removes the old files of an album and not those of a track that has its row.
- A file that another version of the server wrote is not read again: a file without a version in its name, with or without a step as its size, and a file with another version. It stays until a scan removes the files of its album or of its track.
- A file of an album whose ID no row has stays when the scan that deleted the album did not remove it. A job that resolved a track before a scan deleted its row can write its file after the removal of that scan; the next scan that completes removes that file.
- Nothing removes a temp file that a crash left behind.
- The check of the folders reads the path of a source, and the source is opened after it. A directory of the path that is exchanged for a link between the two is followed for that one read, as for `stream` (§3.9).
- The orientation that a PNG declares in an `eXIf` chunk is not applied to a resized cover. A client that applies it to the cover without `size` shows the two in different orientations.
- A JPEG with more than one Exif segment has the orientation of the last one applied, because zune-jpeg keeps the last segment. A viewer that reads the first one shows the cover without `size` in another orientation.
- The image is scaled before it is turned. `thumbnail` takes the block of source pixels for each pixel of the result from the left and the top edge, so it does not treat an image and its mirror image alike when the scale is no whole number. A resized cover can therefore differ in single pixel values from the turned image scaled down. The two have the same size.
- An embedded picture in GIF, BMP or TIFF is not served, with or without `size`. `has_picture` is set for such a track, so `coverArt` can name a cover that `get` does not return.
- A WebP image that is lossless or in the extended file form is served without `size` and is not resized.
- An image with a side over 4096 pixels, or with more than 64 MiB of pixels, is served without `size` and is not resized.
- A cover without `size` is held in memory: at most 16 MiB for each request in progress. `get` returns bytes and no stream.
- An image that cannot be decoded is read and tried again for each request with `size`, with a warning each time. Nothing remembers the failure.
- A scan that stores a new cover with the modification time of the old one removes the cache files after its commit. A job that resolved the old source before the commit can write its file after that removal, and the file then holds the old image under the name of the new cover until the cover changes again.
- A hard link to a file outside the music folders is read as the regular file that it is. Its bytes are returned only when they are an image.
- A cover file in the parent directory of disc directories is not told from an image of the artist. When the directory of an artist holds the disc directories of one album and no track of another album, as `Artist/Album CD1` and `Artist/Album CD2`, a `folder.jpg` in it is the cover of that album.
- An album whose tracks are in one directory has no cover file from the parent directory, also when that directory is the one disc directory of the album, as `Album/CD1` without a second disc.

`getCoverArt` sends `Cache-Control: public, max-age=86400` and an `ETag`, which is `"<id>-0-<cover_mtime>"` for the image as it is stored and `"<id>-<step>-<cover_mtime>-<version>"` for a resized cover, and answers `If-None-Match` with 304 (§4).

### 3.12 mDNS

No DNS-SD type exists for Subsonic servers; the server registers its own and the mobile app browses for it. This section is the contract between the server and a client that discovers it, and a client can be written from it alone. Unit tests in `discovery` pin the service type, the SRV target, the TXT record and the address choice.

#### Records

A client browses the service type `_waxnerd._tcp` in the domain `local.`. The server registers no subtype. A running server is one service instance with these records:

| Record | Content |
|---|---|
| PTR `_waxnerd._tcp.local.` | `<instance name>._waxnerd._tcp.local.` |
| SRV | priority 0, weight 0, port `server.port`, target `wn-server-<hex>.local.` |
| TXT | the keys of the next table |
| A and AAAA of the target | the addresses under Addresses |

- The instance name is `server.name`: 1 to 63 bytes of UTF-8, which the validation at load enforces (§3.5). When another responder on the link holds that name with other records, the daemon renames the instance by appending ` (2)`, then ` (3)` and so on. Two servers on one link that keep the default name `wn-server` are such a case. TXT `name` keeps `server.name`. A client does not identify a server by its instance name.
- The target is the server's own host name, `wn-server-<hex>.local.`. `<hex>` is the first 8 hexadecimal digits of the UUID in `instance.id`: the target for an `instance.id` of `1a2b3c4d-5e6f-4a7b-8c9d-0e1f2a3b4c5d` is `wn-server-1a2b3c4d.local.`. `discovery::host_name` builds the name from the instance ID and from no other input. The A and AAAA records that the server publishes are records of this name only.
- The server never claims the host name of the machine. It does not read that name, and it publishes no record for it and answers no query for it. The responder of the operating system owns the machine's host name, and a second responder that publishes records for that name makes the operating system rename the machine: macOS changes the local host name `studio` to `studio-2`.
- The target says nothing about the machine. It is not the machine's host name, and a client derives no name and no property of the machine from it. A client takes the target from the SRV record and builds it from no other value. It resolves the target to the A and AAAA records and connects to one of their addresses, on the SRV port.
- The A and AAAA records that the server publishes for the target hold the addresses under Addresses and no other. An address can still fail for a client: a link-local IPv6 address needs a zone index, and a server that binds `::` on Windows does not accept its IPv4 addresses. A client therefore follows three rules.
  1. It skips every link-local IPv6 address (`fe80::/10`). A connection to such an address needs a zone index, and the URL of this contract carries none.
  2. It tries the other addresses one after the other, in an order of its own choice. It bounds each attempt with a timeout of its own choice.
  3. It goes on to the next address when an attempt fails for any reason: the connection is refused, the attempt times out, the address is unreachable, or any other error occurs. The server is unreachable for the client when no address is left.

#### TXT record

| Key | Value | What a client does with it |
|---|---|---|
| `txtvers` | `1`. A decimal number: the version of this table. | Ignores an instance whose `txtvers` it does not know. |
| `api` | `opensubsonic`. | Ignores an instance with another value. |
| `path` | `/rest`. A URL path that starts with `/` and does not end with `/`. | Builds the URL of an API method as `http://<address>:<port><path>/<method>`, for example `http://192.168.1.5:4200/rest/ping`. The scheme is `http` because `tls` is `0`. An IPv6 address is in brackets. |
| `id` | The UUID in `instance.id`: 36 characters, lower-case hex digits in groups of 8, 4, 4, 4 and 12, separated by hyphens. | Stores the server under this key. Two instances with one `id` are one server: the client keeps the instance whose SRV and TXT records it received last, with the port and the addresses of that instance, and drops the other. |
| `name` | `server.name`: 1 to 63 bytes of UTF-8. | Shows it as the name of the server. |
| `auth` | `password`, or `none` when `auth.disabled_unsafe` is set. | `password`: sends `u` with `p`, or with `t` and `s` (§3.7). `none`: sends none of them. Ignores an instance with another value. |
| `tls` | `0`: the server speaks plain HTTP. No other value is defined. | Ignores an instance with another value. |
| `ver` | The Cargo version of the server, unchanged: `MAJOR.MINOR.PATCH`, for example `0.1.0`, with a suffix for a pre-release, as in `0.2.0-beta.1`. | Shows the text as it is. A client does not parse it and derives no behaviour from it. |

- The record holds no other key today. Every device on the network can read the record, so no key carries a credential, an account name or a folder path.
- `txtvers` is the first key. The order of the other keys is not part of the contract. Each key appears once. The keys are lower-case ASCII, and a client compares keys without regard to case (RFC 6763 section 6.4). The values are UTF-8; only `name` can hold characters outside ASCII.
- A new key does not change `txtvers`, and a client ignores a key it does not know. `txtvers` increases when a key is removed or when the format or the meaning of a key changes.
- `id` stays the same across restarts and across changes of `server.name`, the machine's host name, the port and the addresses. It is new after `init` on a new data directory, and after `run` wrote a missing `instance.id`. The SRV target is built from `id` and changes only when `id` does.

#### Addresses

`discovery::addresses` and `discovery::interface_kinds` choose the addresses from `server.bind`:

| `server.bind` | A and AAAA records |
|---|---|
| `0.0.0.0` | Every IPv4 address of the interfaces that are up, the loopback interface included. The daemon follows address changes. No AAAA record. |
| `::` | Every IPv4 and IPv6 address of those interfaces, link-local IPv6 addresses included. The daemon follows address changes. |
| another IPv4 address | That address. No AAAA record. |
| another IPv6 address | That address. No A record. |

- The daemon announces an address on the interface whose subnet holds it and on no other. A client therefore receives the addresses of the link it is on. A server that binds one address is announced on the link of that address only: a server on `127.0.0.1` is visible to clients on the same machine and not on the LAN.
- The daemon does not use point-to-point interfaces, such as VPN tunnels, or the Apple peer-to-peer interfaces `awdl` and `llw`.
- The daemon publishes the link-local IPv6 addresses of a server that binds `::`. A client skips them (Records, rule 1).
- Windows: a listener on `::` accepts IPv6 connections only, because Windows sets `IPV6_V6ONLY` on a new socket and the listener does not clear it. The A records of a server that binds `::` on Windows therefore name addresses that the listener does not accept. Linux and macOS accept both families on that listener.

#### Start, failure and stop

- `discovery::TxtRecord::build`, `discovery::host_name`, `discovery::addresses` and `discovery::interface_kinds` are pure. `discovery::Advertiser` owns the `mdns-sd` `ServiceDaemon`, which runs on its own thread. For `0.0.0.0` and `::` the registration names no address and uses `enable_addr_auto()`. For another address the registration names that address. For an IPv4 bind the daemon disables IPv6 interfaces (`disable_interface(IfKind::IPv6)`).
- The `run` command starts the advertisement before `run_server` when `discovery.mdns` is on. Step 1 of the stop withdraws it, at the moment the server is asked to stop (§3.13). `run` withdraws it itself when `run_server` fails before it serves, and it waits for a withdrawal that is running when a second signal ends the stop. The step runs once, and the process does not exit during it. Before the start it writes a new `instance.id` when the file is missing and `library.db` exists, and logs one warning. `init` refuses a data directory that has a config file and an owner account, so no other command restores the file. The ID must be a UUID in the form `init` writes.
- The daemon probes for its names for 750 ms to one second and then announces the instance (RFC 6762 section 8.1).
- The server runs without the advertisement when the advertisement cannot start. `run` logs one warning when `instance.id` cannot be read or is not a UUID, or when `mdns-sd` returns an error. No host name is built from a text that is not a UUID. `discovery` checks the length of `server.name` as well and reports it the same way. `run` does not reach that check with a name outside 1 to 63 bytes, because the validation at load fails first (§3.5). `mdns-sd` opens its multicast sockets on the daemon thread and reports a socket it cannot open in its debug log only, so a second thread waits for the first announcement: it logs the announced name at `info`, or one warning when nothing was announced within 10 s.
- Withdrawal: `unregister` sends a goodbye packet on every interface, the daemon repeats it after 120 ms, and `shutdown` ends the daemon thread. A client then sees the instance removed. `Advertiser::stop` returns when these steps are done: it waits for the reply to `unregister`, which the daemon sends after the first packet, then 200 ms for the repeat, then for the reply to `shutdown`. It waits 1 s at most for each reply, so it returns after 200 ms when the daemon answers and after 2.2 s at most. A stop before the first announcement sends no goodbye packet, because nothing was announced. The thread that waits for the first announcement records it; a stop after the 10 s of that thread always sends the packet. A goodbye packet for an instance that was not announced would remove the records of another running server with the same instance name from the clients, for example when `run` is started twice and the second server cannot bind its port.
- A server that ends without the goodbye packet stays in the caches of clients until its records expire. `mdns-sd` sets 120 s for the SRV and address records and 4500 s for the PTR and TXT records. These times are not part of the contract, and a client does not depend on them.
- Windows Firewall prompts on first start for TCP 4200 and UDP 5353.

### 3.13 Logging and shutdown

`tracing_subscriber::fmt` to stderr with an env filter from `RUST_LOG`, else `server.log_level`. An empty `RUST_LOG` counts as unset. Colours are written only when stderr is a terminal. No log files.

Startup log: `run_server` logs one line at `info` when the listener is bound and the scans are started. The message is `listening on <address>` with the address of the listener, and the fields are `version` (the Cargo version), `data_dir`, `folders` (the number of configured music folders) and `auth` (`password`, or `none` with `auth.disabled_unsafe`, as the TXT key of §3.12). §3.8 describes the request log.

#### Stop signals

One `CancellationToken` asks the server to stop. `run_server` receives it, and `AppState.cancel` holds it. The `run` command cancels it at the first stop signal:

| OS | Stop signal | Time after which the system ends the process | `short` |
|---|---|---|---|
| Linux, macOS | Ctrl-C (SIGINT) | none | no |
| Linux, macOS | SIGTERM | none; the sender decides, as `docker stop` does with SIGKILL after 10 s | no |
| Windows | Ctrl-C | none | no |
| Windows | Ctrl-Break | none | no |
| Windows | the console event close | 5 s | yes |
| Windows | the console event shutdown | 5 s; 20 s for a service process. By the documentation of Windows the event does not reach the server (see the end of this section) | yes |

`cli::forward_stop_signals` listens with `tokio::signal::ctrl_c()` on every OS and with `cli::OtherStopSignals` for the signals that differ, which is behind `#[cfg(unix)]` and `#[cfg(windows)]`. It sends a `cli::StopSignal { name, short }` for each signal to `cli::run_until_stopped`. `short` is true when the operating system ends the process a fixed time after the signal. The constants of `StopSignal` hold the name and `short` of every signal of the table. They are compiled on every OS, and `OtherStopSignals` only pairs each of its listeners with its constant. The two listeners do not depend on each other. When the process cannot listen for Ctrl-C, or cannot listen for the other signals, `run` logs a warning and listens for the rest. A signal without a listener keeps the action of the operating system, which ends the process without the stop.

`run_until_stopped` logs the first signal. When the signal is `short`, it cancels a second token, `hurry`. Then it cancels the token of the stop. `cli::serve_until_stopped` makes the two tokens and gives `hurry` to `run_until_stopped` and, in `ServerOptions::hurry`, to `run_server`. The default of that option is a token that nothing cancels. `server::Grace` holds the two limits of the stop and `hurry`. Step 2 and step 3 of the stop each ask it for their limit when they begin: `server.shutdown_grace_short_ms` (1.5 s) when `hurry` is cancelled, and `server.shutdown_grace_ms` (10 s) otherwise. Neither value is a config key (§3.5). `hurry` is cancelled before the token of the stop, so step 2 finds it set.

#### The stop

`run_server` stops the server in four steps and returns after the last one. Steps 1 and 2 start when the token is cancelled and run at the same time. `server::withdraw_at_stop` is step 1, `server::serve` is step 2 and `server::stop` is steps 3 and 4.

| Step | Starts | What it does | Time limit |
|---|---|---|---|
| 1. Advertisement | when the token is cancelled | Calls `ServerOptions::withdraw` on a blocking thread. The `run` command passes `Advertiser::stop`, which returns when the goodbye packets are sent (§3.12). | 2.2 s inside `Advertiser::stop`; 200 ms when the mDNS daemon answers. |
| 2. Requests | when the token is cancelled | The listener is closed, so the port refuses a new connection. A connection without a request in progress is closed. A request in progress is answered, and its connection is closed after the response. | The grace: 10 s, and 1.5 s with `hurry`. The connections that are open after it are closed, with one warning. |
| 3. Scan | when step 2 has ended | Waits for the task of the periodic scans and for the running scan, which the token cancelled. | The length of the grace again: 10 s, and 1.5 s with `hurry`. A scan that runs after it is left behind, with one warning. |
| 4. Database | when steps 1 and 3 have ended | `Db::close` waits for the running reads and writes of the handle and runs `PRAGMA wal_checkpoint(TRUNCATE)`. | None for the wait for the reads and writes of the handle. 5 s, the `busy_timeout`, for the checkpoint when a connection of another process holds the log. |

`run` then ends its runtime and exits with status 0. A stop without a request in progress and without a scan takes the time of step 1. Steps 2 and 3 take the two limits of 10 s at most. Step 4 has no limit of its own: `Db::close` waits for the running reads and writes of the handle, a read ends at its limit of 5 s (§3.4), and a write has no limit. The checkpoint then waits 5 s at most for a connection of another process. A stop with `hurry` reaches step 4 within 3 s: steps 2 and 3 take 1.5 s each at most, and step 1 runs during them and takes 2.2 s at most. The log of a stop has these lines at `info`: the signal, `the mDNS advertisement is withdrawn`, `waiting for the running scan to stop` when a scan runs, the end of that scan, and `the server has stopped`.

- Step 1 comes first, because the listener is closed at the same moment: from then on the advertisement would name a server that refuses every connection. The advertisement serves new connections only, so the requests in progress do not need it. A process that is ended from outside during a later step, by `docker stop` after its 10 s or by a service manager after its limit, has sent its goodbye packet. Step 4 waits for the end of step 1, so the process does not exit while the packet is sent.
- Step 2 is `axum::serve(..).with_graceful_shutdown(token.cancelled())`. The grace starts when the token is cancelled. The server does not wait the whole grace: the step ends when the last connection is closed. `axum::serve` runs each connection in a task and gives no handle of it, so the listener hands out streams that the stop can end (`server::ClosableListener`). After the grace every read and write of such a stream fails, the task of the connection ends, and the handler and the body of its request are dropped. The client reads the end of the connection in place of the response, or after the part of the body that was sent. A dropped handler and a dropped body end what they own: the ffmpeg process of a transcode is killed when the handler that waits for its first output is dropped, and when the body of its response is dropped, also while the stream waits for a client that reads nothing (§3.9). The limit of the first output (10 s) and the write timeout (10 minutes) are longer than the grace with `hurry`, and no stop waits for either. When step 2 has ended, no handler runs.
- Step 3: the token of the scans is a child of the token of the stop (§3.10), so the scan was cancelled when the stop began and stops during step 2 in most cases. The scanner checks the token during the walk, before each file read and between batches. After the cancellation a scan finishes at most the file read in progress and stores nothing of the batch it was reading. It then recomputes the album and artist rows and closes its `scans` row with `cancelled` (§3.10). The server waits for that for the limit of the step. A scan that has not ended then reads a file that does not answer, or runs a write transaction that takes longer. The server goes on without it: the thread of the scan ends with the process, its `scans` row keeps no end time, and the next scan finishes the work. That is the state that a process leaves that is killed during a scan (§3.6).
- Step 4: a scan that was left behind holds a connection for the statements of one write transaction only, so the checkpoint runs when that transaction has ended. A checkpoint that a connection of another process blocks, such as a running `wn-server scan`, is logged at `info` and is no error. The log then holds the changes, and that process or the next start moves them. Another error of the checkpoint is the error of `run`, which exits with 1. After the step the file `library.db` holds every change that was committed before it, and `library.db-wal` is empty unless a scan that was left behind commits another batch.

A second stop signal during the stop ends the process without the steps that have not run. `run_until_stopped` drops `run_server` where it is. `run` then calls the step that withdraws the advertisement. The step runs once: the call does nothing when step 1 has ended, which is the case 2.2 s after the first signal at the latest, and it waits when step 1 is running. `run` prints `wn-server: <signal> ended the server before its stop had finished` and exits with 1. A scan that still runs ends with the process, as the scan of a process that is killed does (§3.6).

The database is consistent after a stop in order, after a stop that left a scan behind, after a second signal and after the operating system has ended the process at any moment. Every change of the server and of the scanner is one SQLite transaction, which is applied in full or not at all, and the write-ahead log that a process leaves behind is read at the next start. What a stop that was cut short leaves undone is the work of the scan: its `scans` row has no end time, and the next scan finishes the work.

`run` ends its runtime with `shutdown_background`, which waits for no blocking thread. A scan that was left behind and a blocking call of a request that step 2 dropped, such as a file read on a mount that does not answer, therefore do not keep the process from exiting.

When `run_server` returns an error before it serves (§3.6), `run` withdraws the advertisement and exits with 1.

Windows ends a console process a fixed time after the close event and after the shutdown event, whatever the process does (https://learn.microsoft.com/en-us/windows/console/handlerroutine, Timeouts). The time is 5 s after the close event (the system parameter `SPI_GETHUNGAPPTIMEOUT`). It is 5 s after the shutdown event (`SPI_GETWAITTOKILLTIMEOUT`), and 20 s for a service process (`SPI_GETWAITTOKILLSERVICETIMEOUT`). Ctrl-C and Ctrl-Break have no such limit. The system also ends the process when the handler of the event returns. The handler of tokio does not return after these two events, so the process has the whole time, and it ends when `run` returns.

The two events are the signals with `short`. The stop after the close event reaches step 4 within 3 s of the event, which leaves step 4 the other 2 s. Step 4 takes milliseconds unless something holds the database. A read or a write of the server that still runs holds it: the blocking call of a request that step 2 dropped, or a write transaction of a scan that step 3 left behind. A connection of another process can hold it for the 5 s of the `busy_timeout`. A server whose step 4 does not end within the 2 s is ended by the system without the checkpoint. The database is consistent as described above, and the next start reads the log.

The server promises no stop when the user logs off and when the system shuts down. It does not listen for the logoff event, so that event keeps the action of the system. It listens for the shutdown event, and the documentation of Windows gives two reasons why that event does not reach it:

- The page of `HandlerRoutine` (`dwCtrlType`) says of the logoff event: "this signal is received only by services. Interactive applications are terminated at logoff, so they are not present when the system sends this signal." It says of the shutdown event: "Interactive applications are not present by the time the system sends this signal, therefore it can be received only be services." A server that the user started in a console is an interactive application.
- The page of `SetConsoleCtrlHandler` (https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler, Remarks) states that Windows calls no handler for the logoff event and the shutdown event in a console process that has loaded `user32.dll` or `gdi32.dll`, and it names the Shell functions as a cause. `wn-server` links the Shell function `SHGetKnownFolderPath` of `shell32.dll` through the `directories` crate (§3.5).

The server may therefore be ended at a logoff and at a system shutdown without the stop. The database is consistent as described above, and the next start reads the log. The listener for the shutdown event and its `short` are kept: a stop that this event starts has the short limits. No native run has checked whether the shutdown event reaches the server, and none has checked a stop after the close event (§2).

### 3.14 Remote-mode seams

1. `server::run` owns the single `TcpListener`; remote mode adds a TLS-terminating listener fed by the relay and tags its connections.
2. `media::stream::decide` gains a connection-kind argument; it is the only function that decides lossy versus lossless.
3. `users.role` and `auth::extract::authenticate` extend to guests and API keys.
4. The cloud client attaches as a new module with its own background task started from `server::run`.
5. `annotations`, `playlists` and `play_queue` already carry `user_id`.

Browse methods (`api/browse.rs`): the six methods of the ID3 model read the library with `db::queries::browse` and build their elements with the constructors of `api/model.rs` (§3.8). A method that returns artists, albums or songs reads the annotations of the user of the request for the IDs of its answer with `annotations::get_many`, so the elements carry `starred`, `userRating`, `playCount` and `played` as §3.8 describes them.

- `getMusicFolders` returns `musicFolders`, whose `musicFolder` list holds the rows of the `folders` table in ID order, each with its integer `id` and its `name`. `run` stores the folders of the config before it serves (§3.10), so the list holds them before the first scan. A folder that left the config is listed while its row exists, which is until a scan removes the row (§3.10 step 5); its tracks are in the library for the same time. The IDs are the ones that `getUser` reports as `folder` and that `musicFolderId` names.
- `getArtists` returns `artists` with `ignoredArticles` and the `index` list of `model::index` (§3.8). `musicFolderId` limits the list to the artists that have a track with a file in that folder, and `albumCount` stays the stored count. An ID that no folder has gives `artists` without an index: no artist is in such a folder. An empty value counts as absent, and a value that is no integer is error 0 that names the parameter (§3.8).
- `getArtist` returns `artist` with its `album` list in the order of `albums_of_artist`. `getAlbum` returns `album` with its `song` list in the order of `tracks_of_album`, which is the track order of §1.3. `getSong` returns `song`. A track without a file is listed by `getAlbum` and returned by `getSong`, without `path` (§3.4).
- `getArtist`, `getAlbum` and `getSong` require `id`, and an absent one is error 10. Error 70 answers an ID that no row of the kind of the method has. That includes a value without the shape of an ID (§3.3), an empty value and the ID of an item of another kind: `ids::parse` rejects them before a statement runs.
- `getGenres` returns `genres`, whose `genre` list holds the rows of `browse::genres`. In XML the name of a genre is the text of its element (§3.8).
- A list without an item is `[]` in JSON and absent in XML (§3.8). A server without a library answers `getArtists` with `ignoredArticles` and no index, and `getMusicFolders` and `getGenres` with an element that holds nothing.
- Each handler runs its statements in one read transaction (`read_library` in `api/browse.rs`), so the rows of one answer are of one state of the database. A scan that commits between two statements of a request does not change the answer. A database that cannot be read is error 0 with the message `the server cannot read its library`.
- The order of every list is the order of its query, which ends with a unique column (§3.8, Library queries), and of `model::index`, which ends with the ID. Two requests on a library that did not change return the same document.

Folder methods (`api/folders.rs`, queries in `db/queries/indexes.rs`): `getIndexes` and `getMusicDirectory` serve the clients that browse by directory. The server stores no directory of a music folder (§1.3), so the two methods list the rows of the ID3 model as a tree of three levels: the album artists, the albums of an artist and the songs of an album. The parameters and the elements follow the OpenSubsonic pages of the two methods (https://opensubsonic.netlify.app/docs/endpoints/getindexes/, https://opensubsonic.netlify.app/docs/endpoints/getmusicdirectory/) and of the `indexes`, `index`, `artist`, `directory` and `child` responses, and the types `Indexes`, `Index`, `Artist`, `Directory` and `Child` of the Subsonic 1.16.1 schema.

- IDs: every ID of the tree is the ID of its row (§3.3), which is the artist, album or track ID of every other method. `getArtist`, `getAlbum`, `getSong`, `star`, `unstar` and `setRating` take the IDs that the tree lists, and an item has one star and one rating in the tree and in the ID3 methods. `coverArt` of an album and of a song is the cover art ID of §3.8, which `getCoverArt` takes. An artist has none, in the indexes and as a directory. `parent` of a song is the ID of its album, and `parent` of an album is the ID of its album artist (§3.8), so every `parent` is an ID that `getMusicDirectory` takes. An artist is at the first level and has no `parent`.
- `getIndexes` returns `indexes` with `ignoredArticles`, `lastModified` and the `index` list. The artists are the rows of `browse::list_artists`, grouped and ordered by `model::index` (§3.8), as in `getArtists`: the two methods return the same artists in the same indexes for the same `musicFolderId`. Each artist is the `Artist` element of the folder methods, with `id`, `name`, and `starred` and `userRating` of the user. The element has no `shortcut` and no `child`: the server has no shortcut directories, and every song is in the directory of its album.
- `musicFolderId` limits the indexes to the artists that have a track with a file in that folder. An ID that no folder has gives no index. An empty value counts as absent, and a value that is no integer is error 0 (§3.8). `getMusicDirectory` has no such parameter, and the directory of an artist holds its albums of every folder.
- `lastModified` is the time at which the artists last changed, in milliseconds since the Unix epoch (`indexes::last_modified`). The artists follow from the rows of the library (§1.3), and only a scan writes those rows. A scan knows whether it wrote one, and it stores that in `scans.changed_library` when it closes its row (§3.10 step 7). The time is the end time of the last scan whose flag is set: `SELECT max(finished_at) FROM scans WHERE changed_library = 1`. The statement reads one entry of the index `scans_changed` (§3.4), whatever the number of scans.
- What follows for a client: `lastModified` is the same before and after a scan that found nothing changed, so the scan at a start of the server and a periodic scan do not make a client read the artists again. A scan that could not read a path and stored no change keeps it too, each time it runs (§3.10 step 5). It is greater after every scan that added, changed, moved or removed a track or gave a track its placeholder path, also when the artists are the same as before. It is greater after a scan that only set the cover of an album or recomputed a count, because the scan wrote an album row; the flag does not tell the rows of the library apart. It is greater after a scan that follows a scan without an end time. A star and a rating of an artist do not change it: they are no change of the library, and neither Airsonic nor Navidrome counts them.
- The end times of the scans are milliseconds, and each scan ends later than the scan before it (§3.10 step 7). Two scans that change the library therefore have two values in their order, also when they end in one millisecond. The scans of a database from before schema version 3 all have the flag, and two of them that ended in one second have one end time (§3.4). `lastModified` is 0 while no scan that changed the library has ended.
- `ifModifiedSince` is a time in milliseconds. A request whose `ifModifiedSince` is at or after `lastModified` gets `indexes` with `ignoredArticles` and `lastModified` and without `index`: the key is absent in JSON, and the element has no content in XML. A request with an earlier time, with an empty value or without the parameter gets the artists. A client that sends the `lastModified` of its last answer back therefore gets the artists when a scan that changed the library has ended since. Two cases return the artists whatever the time is. While no scan that changed the library has ended, there is no time to compare with. While the scan that started last has no end time (`indexes::scan_is_open`), it runs or its process has ended, and it can have stored changes that `lastModified` does not cover yet. A value that is no integer is error 0 (§3.8).
- The API says of `ifModifiedSince`: "only return a result if the artist collection has changed since the given time". Airsonic, which carries the code of the Subsonic server, answers with the empty response when `lastModified <= ifModifiedSince` (`SubsonicRESTController.getIndexes`). Its time is the latest change of the settings and of the directories of the music folders (`LeftController.getLastModified`), so it stays while nothing changes. Navidrome answers with `indexes` that holds `lastModified` and `ignoredArticles` and no `index` (`getArtistIndex` in `server/subsonic/browsing.go`). Its time is the start of the last scan, in whole seconds, and every scan sets it (`scanner/scanner.go`). This server sends the answer of Navidrome, which has the two fields that the OpenSubsonic API requires of `indexes`, and it keeps the time through a scan without a change, as Airsonic does. Navidrome answers `getIndexes` for a library without an artist with error 70. This server returns `indexes` with an empty list, as `getArtists` does.
- `getMusicDirectory` requires `id`, which is the ID of an artist or of an album, and returns `directory`.
  - For an artist the element holds `id`, `name`, and `starred` and `userRating` of the artist. It has one `child` for each album row of the artist, in the order of `getArtist` (`browse::albums_of_artist`: by year, then by title). A child is the album as a directory (§3.8): `isDir: true`, the title as `title` and as `album`, the album artist as `artist`, the ID of the artist as `parent` and as `artistId`, `coverArt` when the album has a cover, and `year`, `genre`, `duration`, `created`, `mediaType: album` and the four annotation values.
  - For an album the element holds `id`, `name`, `parent` (the ID of the album artist), and `starred`, `userRating` and `playCount` of the album. It has one `child` for each track of the album that has a file, in the order of `getAlbum` (`browse::tracks_of_album`: disc, track, path). A child is the `Child` element of the song (§3.8), which is the element that `getSong` returns for it: `isDir: false`, and `parent` and `albumId` are the ID of the album.
  - The `directory` element has the fields of the Subsonic schema. Navidrome adds `coverArt`, `songCount`, `albumCount`, `played` and other fields of the ID3 elements to it. This server sends those values on the children.
- Errors: an absent `id` is error 10. Error 70 answers a value that names no directory: an artist or album ID that no row has, the ID of a track or of a playlist, an empty value and a value without the shape of an ID (§3.3). The handler finds the last three with `ids::parse`, before a statement runs. Airsonic answers an absent `id` with error 10 and an unknown one with error 70. Navidrome answers both with error 70, and the ID of a song as well.
- Tracks without a file (§3.4): such a track is no child of the directory of its album, so a walk of the tree reaches the songs that have a file. `getAlbum` lists the track and `getSong` returns it. The album row and the artist row stay while the track refers to them (§3.10 step 6), and the tree lists them as the ID3 methods do: the album is a child of its artist and the artist is in the indexes, also when none of their tracks has a file. The directory of such an album has no child. `getIndexes` with `musicFolderId` leaves out an artist that has no track with a file in the folder, as `getArtists` does.
- Each handler runs its statements in one read transaction (`read_library` in `api/folders.rs`), as the browse methods do. `lastModified` of an answer is therefore the time of the artists in that answer, also when a scan ends during the request. `getIndexes` reads the time, the open scan and the artists with one statement each, and the annotations of all artists with one call of `annotations::get_many`. `getMusicDirectory` reads the row of the directory with one statement and its children with one, and the annotations of the directory and of all children with one call of `annotations::get_many` (§3.8). The number of statements does not depend on the number of children, and no statement runs once for each child. A database that cannot be read is error 0 with the message `the server cannot read its library`.
- A list without an item is `[]` in JSON and absent in XML (§3.8). The order of every list is the order of its query and of `model::index`, so two requests on a library that did not change return the same document.

List methods (`api/lists.rs`, queries in `db/queries/lists.rs`): `getAlbumList2` returns `albumList2`, whose `album` list holds `AlbumID3` elements. `getAlbumList` returns `albumList` with the same albums in the same order, each as a directory (`isDir: true`, `parent` is the ID of the album artist). `getRandomSongs` returns `randomSongs` and `getSongsByGenre` returns `songsByGenre`, each with a `song` list of `Child` elements. A list without an entry is `[]` in JSON and absent in XML. The parameters, their defaults and their bounds are those of the OpenSubsonic API, which takes them from Subsonic 1.16.1. Subsonic 1.16.1 does not name `highest` for `getAlbumList2` and OpenSubsonic does; both album methods serve the ten types.

- Parameters: `type` is required by the two album methods. An absent `type` is error 10, and a value that is none of the ten names in their letter case is error 0. `byYear` requires `fromYear` and `toYear`, and `byGenre` requires `genre` (error 10); the other types ignore these three. `getSongsByGenre` requires `genre` (error 10). `size`, which `getSongsByGenre` calls `count`, is 10 without a value, and a value above 500 is lowered to 500. `offset` is 0 without a value, and `getRandomSongs` has none. `musicFolderId` restricts each of the four methods to one music folder, and an ID that no folder has gives an empty list. `size`, `count`, `offset`, `fromYear` and `toYear` are integers from 0 to 4294967295 and `musicFolderId` is an integer; another value is error 0 (§3.8). An empty value counts as absent, also for the optional `genre` of `getRandomSongs`. An empty `genre` of `byGenre` and of `getSongsByGenre` is a value, as the value of every required text parameter is (§3.8), and no genre matches it.
- A value of a request is a parameter of a statement, or it is compared in Rust. The SQL text of the lists is built from constants of the query module.
- Each handler reads its list in one read transaction (`read_lists` in `api/lists.rs`), as the browse methods do. The IDs of a page, the rows of these IDs and their annotations are of one state of the database, so a scan that commits during a request takes no row out of the answer. A page of a list that has an order is shorter than its size only where the list ends. A database that cannot be read is error 0 with the message `the server cannot read its library`.
- The albums and the order of each `type`:
  - `random`: every album, drawn at random for every request.
  - `newest`: every album, `created` descending.
  - `highest`: the albums that the user rated, rating descending.
  - `frequent`: the albums of which the user played a track, play count descending.
  - `recent`: the albums of which the user played a track, last play descending.
  - `alphabeticalByName`: every album, by title.
  - `alphabeticalByArtist`: every album, by the name of the album artist and then by title.
  - `starred`: the albums that the user starred, time of the star descending.
  - `byYear`: the albums of the years from `fromYear` to `toYear`, both included, year ascending. When `fromYear` is greater than `toYear`, the range is the same and the year descends.
  - `byGenre`: the albums whose genre is `genre`, by title.
- Order: the order of every type but `random` ends with the natural key of the title, the natural key of the artist and the album ID (§3.3), so it is total. Two requests return the albums in one order, and the pages that `offset` selects neither repeat nor skip an album while the library and the annotations stay as they are. Titles and names are compared by their natural keys, as `getArtist` orders albums (§3.8). `getSongsByGenre` orders the songs by the normalised title (`tracks.title_lc`, §3.3), then by the track artist, the album title and the track ID.
- Annotations: `highest` and `starred` read the rating and the star of the album. `frequent` and `recent` read the plays of the tracks of the album, because `scrobble` records the play of a track: the play count of an album is the sum of the play counts of its tracks, and its last play is the latest play of one of them. Each of the four lists holds only the albums that have such a value, so it is empty for a user without a rating, a star or a play. They are the lists of the highest rated, the most played, the recently played and the starred albums, and an album without a rating or a play is none of these. The code of the Subsonic server, as Airsonic carries it, and Navidrome answer the same way: both select the albums with a play count above 0, with a last play and with a rating.
- Years: an album or a track without a year counts as year 0 in a year range, which is `byYear` and the `fromYear` and `toYear` of `getRandomSongs`. No item has the year 0 for another reason, because the tag reader stores no year for `0000` (§1.3). `byYear` from 0 lists the albums without a year first, and `byYear` down to 0 lists them last. Feishin asks for all albums by year with the range from 0 to the present year. Navidrome stores the year 0 for an album without one, so it answers that range with these albums. In `getRandomSongs`, a range whose first year is greater than its last year holds no song.
- Genres: `genre` matches the stored genres that equal it without regard to case, as whole texts. `LIKE` is not used, so `%` and `_` are plain characters. Two texts are equal when their lower-case forms are (`str::to_lowercase`). `byGenre` compares with the genre of the album (§3.10 step 6), and the two song methods compare with the genre tag of the track. `getGenres` lists spellings that differ by case as separate genres (§3.8). A list for `Rock` holds the items of `rock` as well, so it can hold more items than `getGenres` counts for one of the two.
- Random lists: `random` and `getRandomSongs` draw their rows anew for every request. No row is in an answer twice, and every row that the request allows is equally likely to be in it. No request sorts a table, and a request that many rows match reads only the rows that it looks up. `tracks` and `albums` are rowid tables, and the query depends on that. It reads the smallest and the largest rowid, draws distinct rowids of that range in random order with the `rand` crate, and looks each one up by its key. A rowid without a row and a row that the request does not allow add nothing. For `n` rows the query looks up `n + n/8 + 8` rowids first and twice as many each further time, up to `16 n + 64` in all. When that limit is at least the number of rowids, every rowid is looked up and the answer is exact. Otherwise lookups that find fewer than `n` rows mean that few rows count: the request allows few rows, or the table has lost most of its rows. The query then reads the IDs of the rows that count and keeps a random sample of `n` of them in one pass, without a sort. With a `genre` it reads the tracks of that genre through the index `tracks_genre`, and without one it reads the table. The stored genres that a `genre` is compared with are read through the genre index, one lookup for each distinct genre.
- `offset` selects no rows of `random`, because every request draws anew, and two pages can hold the same album. It lowers the number of albums instead: a request returns at most the number of albums of the list less the offset. A client that reads pages until one is short therefore comes to an end. A request with an offset counts the albums, which reads the album table once.
- Tracks without a file (§3.4): such a track is in no music folder. A list with `musicFolderId` leaves it out, and an album is in a music folder when one of its tracks has a file there. `getRandomSongs` never returns it, because a client plays the songs it gets and `stream` answers error 70 for it. `getSongsByGenre` without `musicFolderId` lists it without a `path`, as `getGenres` counts it. The album lists without `musicFolderId` list every album row, also one whose tracks all have no file.

Search methods (`api/search.rs`, `db/queries/search.rs`): `search3` returns `searchResult3` with the lists `artist` (`ArtistID3`), `album` (`AlbumID3`) and `song` (`Child`). `search2` finds the same rows and returns `searchResult2` with `artist` (the `Artist` of the folder methods), `album` (a `Child` that is a directory) and `song` (`Child`). The parameters and their defaults are those of the Subsonic API 1.16.1 and of the OpenSubsonic API (https://opensubsonic.netlify.app/docs/endpoints/search3/). A list without an item is `[]` in JSON and absent in XML.

- `query` is required, and an absent one is error 10. It may be empty. Every double quote is removed from it, and so is one `*` at its end: the search of the Subsonic API 1.x took `*` as a wildcard, and some clients still append it. The rest is split at white space into terms. A `*` at another place is a character of its term. A query without a term, such as `query=` and `query=""`, matches every artist, album and song. The OpenSubsonic API requires that, and Symfonium reads the whole library that way.
- A term is brought into its normalised form (§3.3) with `ids::normalise`, the function that gives `tracks.title_lc` its value. An item is a match when every term is part of one of its names. The terms may be parts of different names, their order has no meaning, and a term may be a part of a word: `beat` matches "The Beatles". A term that the query holds twice counts once.
- The name of an artist is its name. The names of an album are its title and the name of its artist. The names of a song are its title, the title of its album, its track artist and the name of its album artist.
- `artists.key`, `albums.key` and `tracks.title_lc` hold a name in its normalised form, so the letter case and the Unicode form of a name and of a term have no meaning. A title whose tag is in decomposed form is found by a composed query and by a decomposed query, and so is a title whose tag is in composed form. The title of the album of a song and the name of its album artist are compared through the keys of its album row and of its artist row. `tracks.artist_name`, the track artist, is stored as the tag spells it and in no other form. `LIKE` ignores the case of the letters A to Z only, so a letter outside ASCII in a track artist matches a term only when the tag has it in lower case. The track artist is in the Unicode form of the tag, and a term is in NFC, so a letter with a combining mark in a track artist matches a term only when the tag has the letter as one character. A track artist that is the album artist of its track is found through the key of the artist row in every case. A letter with a diacritic is not its base letter: `edith` does not match "Édith", whatever the Unicode form of the tag is.
- The terms are one parameter of a statement: a JSON array of `LIKE` patterns that the statement reads with `json_each`. A pattern is a term between two `%`, and a `%`, a `_` and a `\` of the term follow the escape character `\`, so each matches itself. No text of a request is part of a statement, and a query with any number of terms is the same statement.
- A query of more than 1024 characters is error 0, and so is a query of more than 32 different terms. Both are refused before a statement runs. The work of a search grows with the number of terms: the statement of the tracks tests the key of every album and of every artist against every term, and then every track against the terms until one does not match. A query that a person types has fewer than 32 terms. The limit of the characters bounds the length of a pattern. A term that holds the character U+0000 matches nothing, because SQLite reads a pattern and a name up to that character.
- `artistCount`, `albumCount` and `songCount` are 20 by default, and a value above 500 counts as 500. `artistOffset`, `albumOffset` and `songOffset` are 0 by default. Each is an integer from 0 to 4294967295, and another value is error 0. A negative limit is no limit in SQLite, and none reaches a statement. An answer holds 500 items of each kind at most.
- Each list is in the order of the normalised names: `artists.key`, `albums.key` and `tracks.title_lc`, in the byte order of the UTF-8 text. Albums with one title and tracks with one title are in the order of their rowids, which is the order in which the scanner stored them. A rowid changes only when the database is rebuilt with `VACUUM`, which the server never runs. The order is total and the same for every page, so a client that reads a list with offsets gets every item once while the library does not change.
- The statements read the unique index of `artists.key`, the index `albums_key` and the index `tracks_title_lc` in their order, stop when the page is full and sort nothing. The rows before the offset of a query without a term and without a music folder are read from the index alone. A pattern that starts with `%` cannot be looked up in an index, so a query with a term tests every row up to the end of its page. For the tracks, the statement first collects the IDs of the albums and of the artists that each pattern matches. The test of a track then reads no album row and no artist row.
- The three lists and the annotations of the user for their items are read in one read transaction. A list is shorter than its count only when it holds the last match, also while a scan deletes rows. A client that reads page after page takes a short page for the last one.
- `musicFolderId` limits the lists to one music folder: the tracks that have a file in it, and the albums and the artists that have such a track. The ID of no folder gives three empty lists. A value that is no integer is error 0.
- A track without a file (§3.4) is a match as every other track, and its element has no `path`. It is in no music folder, so a request with `musicFolderId` leaves it out.
- `search` returns error 0 with the message `deprecated; use search3`. Its handler reads no parameter.

Annotation methods (`api/annotate.rs`): `star`, `unstar`, `setRating`, `getStarred`, `getStarred2` and `scrobble`. A star and a rating are values of the row that the `annotations` table holds for the user of the request and the item (§3.4). A play is counted in the row of a track.

- `id` of `star`, `unstar` and `setRating` takes the ID of a track, an album or an artist; the prefix of the ID names the kind (§3.3). `albumId` takes the ID of an album and `artistId` the ID of an artist. The folder methods list an album and an artist under the same IDs, so an item has one star, whichever parameter set it. `star` and `unstar` take each parameter any number of times and require none: a request without an ID changes nothing and answers `ok`. `setRating` requires `id` and reads its first value.
- A value that is not the ID of an existing item of the kind its parameter takes is error 70: a text that `ids::parse` rejects, an empty value, the ID of a playlist, an ID that no row has, and the ID of a track in `albumId`.
- A request changes every item it names or none. `annotations::apply` checks that every item has a row and writes the items in one `IMMEDIATE` transaction. After error 70 and after a write that failed, no item of the request is changed. The check is in the transaction, so a scan in another process deletes no item between the check and the write.
- `star` sets `starred_at` to the time of the request in Unix seconds. The time is read once the write connection is held, and the items of one request get one time. `star` for an item that has a star replaces the time with the time of the new request. The API does not define that case. Navidrome and Airsonic replace the time, and the server does the same. `unstar` sets `starred_at` to NULL. `unstar` for an item that exists and has no star answers `ok`.
- `setRating` requires `rating`. 1 to 5 is stored, and 0 sets the rating to NULL. An absent or empty `rating` is error 10. A value that is no integer, and an integer outside 0 to 5, is error 0 and changes nothing. The rating is checked before the item.
- Each write sets the star, the rating or the plays of the row and leaves the other two. A star, a rating and the plays of an item therefore do not depend on the order of the requests that set them. No method deletes a row: `unstar` and `setRating` with 0 keep the other values of the row. A row without a star, a rating and a play reads as the annotation of an item without a row.
- `getStarred2` returns `starred2` with the lists `artist` (`ArtistID3`), `album` (`AlbumID3`) and `song` (`Child`). `getStarred` returns `starred` with `artist` (the `Artist` of the folder methods), `album` (directories) and `song`. The elements are those of the model constructors (§3.8), so `starred` and `userRating` have the form they have in every other method. `ArtistID3` has no `userRating`: the rating of an artist is part of `getStarred` and not of `getStarred2`. A list without an item is `[]` in JSON and absent in XML.
- Each list has the item that was starred last as its first (`annotations::starred`). Items with the same time are in the order of their IDs.
- `musicFolderId` limits the three lists to one music folder: a track whose file is in the folder, and an album or an artist that has such a track. A track without a file is in no folder (§3.4); without `musicFolderId` it is listed, and it takes a star and a rating as every other track does. An ID that no folder has gives three empty lists. A value that is no integer is error 0.
- A star whose item has no row is not listed. Such a row exists from the deletion of a track row until a scan completes and deletes the annotation (§3.10 step 6).
- A scan keeps the ID of a track through a rename and a move of its file, and the ID of an album and of an artist through a new spelling of the name (§1.3, §3.3). The scan does not write the `annotations` rows of these items, so their stars, their ratings, their plays and the times stay.
- `scrobble` counts plays of tracks for the user of the request and returns the empty response (https://opensubsonic.netlify.app/docs/endpoints/scrobble/, and the same parameters in Subsonic 1.16.1). `id` is required and takes the ID of a track. It may occur any number of times, and a track that a request names twice gets two plays. `time` is the time of a play in milliseconds since 1970. A request has no `time` or one for each `id`: the first `time` is the time of the first `id`, wherever the parameters are in the request. An empty `time` counts as absent (§3.8). A play without a `time` has the time of the request in Unix seconds. That time is read once the write connection is held, and the plays of one request get one time. `submission` is `true` or `false` in any letter case (§3.8), and `true` without a value.
- A play is stored in the row of its track: `annotations::record_play` adds 1 to `play_count` and sets `last_played_at` (§3.4). The time is stored in whole seconds, so the part of `time` below a second is dropped. The last play of a track is the latest of the times of its plays. A play whose time is earlier than the stored time is counted and leaves the stored time. A client can report a play long after it happened and the plays of one request in any order, and the plays of a track then do not depend on the order of the reports. Navidrome stores the later time as well. A `time` is stored as the request gives it, also when it is far in the past or later than the time of the request. The server does not compare it with its clock: a server without a real-time clock can have the wrong time while the client has the right one.
- Every request that passes the checks counts its plays. The API has no value that tells a repeated report from a second play. A request that is sent twice therefore counts twice, and so does a play that one request names twice with one time. Navidrome and Airsonic count every report as well.
- `submission=false` is the "now playing" notification of the API. The server checks the request as it checks a submission, answers `ok` and writes nothing: no play count, no last play and no list of the songs that play, because `getNowPlaying` is a stub (§1.2). Navidrome counts no play for the notification either. Airsonic counts a play for both forms.
- Errors of `scrobble`, in the order of the checks: an absent `id` is error 10. Error 0 answers a `submission` that is no boolean, a `time` that is no integer from 0 to 253402300799999, and a number of `time` values that is neither 0 nor the number of `id` values. The largest `time` is the last millisecond of the year 9999, the last time that `model::iso8601` writes with a year of four digits. Error 70 answers a value of `id` that is not the ID of an existing track: a text that `ids::parse` rejects, an empty value, the ID of an album, an artist or a playlist, and an ID that no track row has. Navidrome and Airsonic skip such an ID and answer `ok`. The server answers error 70, as `star` does, so a client learns that the plays were not counted.
- A `scrobble` request counts every play it names or none. `annotations::record_plays` checks that every track has a row and writes the plays in one `IMMEDIATE` transaction, as `annotations::apply` does for the other writes. After an error, and after a write that failed, no play of the request is counted. The number of plays of a request has no limit of its own; the form body limit bounds it (§3.8).
- The plays of an album are not stored (§3.4). `scrobble` writes no row of the album and none of the artist. `playCount` and `played` of an album element are the sum of the play counts of its tracks and the latest play of one of them (§3.8), and the `frequent` and `recent` lists order the albums by these two values (see the list methods). No element reports the plays of an artist.
- A track without a file (§3.4) takes a play as every other track does: a client can report the play of a copy that it holds after the file is gone. Its plays count for its album.
- Plays and the scan: a track keeps its play count and its last play through a rescan, a rename and a move of its file, and an album keeps the sums through a new spelling of its name, because the IDs stay (§1.3). A retag that gives a track another album title moves the plays of the track to the album row that the scan makes for it. When a scan deletes a track row, it deletes the annotation of the track (§3.10 step 6), and the plays of the track leave its album.

Playlist methods (`api/playlists.rs`): `getPlaylists`, `getPlaylist`, `createPlaylist`, `updatePlaylist` and `deletePlaylist`. The handlers read and write the `playlists` and `playlist_tracks` tables with `db::queries::playlists`. They read the songs with `browse::tracks_by_ids` and the annotations of the user with `annotations::get_many`, and they build each song with `model::child` (§3.8). The `playlist` element is a type of the handler module, because no other module returns it. Parameters, responses and versions follow the OpenSubsonic pages of the five methods and of the `playlist` and `playlistWithSongs` responses, and the Subsonic 1.16.1 schema.

- A playlist belongs to the user that created it (`playlists.owner_id`). Every query takes the ID of the user of the request and reads or changes the playlists of that user only. Every method answers the ID of a playlist of another user as the ID of no playlist, with error 70, whatever the `public` value of that playlist is. `public` is stored and returned and has no other effect (§1.3). `owner` is the name of the account that owns the playlist.
- The `playlist` element holds `id`, `name`, `comment`, `owner`, `public`, `songCount`, `duration`, `created`, `changed` and `coverArt`. The API requires `id`, `name`, `songCount`, `duration`, `created` and `changed`. `comment` is absent for a playlist without one. The element has no `allowedUser`, `readonly` and `validUntil`.
- `songCount` is the number of entries. `duration` is the sum of the durations of the songs in milliseconds, rounded once to seconds as the duration of an album is (§3.8). A song with two entries counts twice in both. `created` is the time of the request that created the playlist, and `changed` the time of the last request that changed it, both in the form of §3.8. A scan that deletes a track of the playlist does not set `changed`.
- `coverArt` is the cover art ID of the first song (`model::song_cover_art`, §3.8). It is absent for a playlist without a song and for one whose first song has no cover, also when a later song has one. A playlist has no image of its own.
- `getPlaylists` returns `playlists`, whose `playlist` list holds the playlists of the user without `entry`, in the order of their names without regard to ASCII case. Names that differ by case only are in the order of their bytes, and playlists with one name in the order of their IDs. `username` is optional, and an empty value counts as absent. It must be the name of the user of the request, compared without regard to ASCII case. Another name is error 50, whether an account has it or not, as in `getUser`. With `auth.disabled_unsafe = true` every name returns the playlists of the owner.
- `getPlaylist` returns `playlist` with the `entry` list: the `Child` element of the song of each entry, with the annotation of the user, in the order of the entries. A song with two entries is listed twice. The list is `[]` in JSON and absent in XML for a playlist without a song (§3.8).
- `createPlaylist` without `playlistId` requires `name` and creates a playlist of the user with one entry for each `songId`, in the order of the values. A song that is named twice gets two entries, and a request without `songId` creates a playlist without a song. The new playlist has no comment and `public: false`. An empty `playlistId` and an empty `name` count as absent, so a playlist always has a name; an absent `name` is error 10.
- `createPlaylist` with `playlistId` replaces the entries of that playlist with one entry for each `songId` and keeps the name, the comment, `public` and `created`. `name` is not read in this form, as in Airsonic and Navidrome; `updatePlaylist` renames a playlist.
- `createPlaylist` returns `playlist` with `entry` in both forms, as `getPlaylist` does. That is the answer of API version 1.14.0 and later. Earlier versions answer with the empty response; the server does not compare `v` (§1.3) and sends the playlist to every client. The handler reads the playlist while it holds the write connection, so the answer is the playlist as the request left it.
- `updatePlaylist` requires `playlistId` and returns the empty response. `name` sets the name, and an empty value counts as absent. `comment` sets the comment, and an empty value removes it. `public` is `true` or `false` in any letter case (§3.8). `songIndexToRemove` and `songIdToAdd` may each occur any number of times.
- The API defines no order for a request with several `songIndexToRemove` values and with `songIdToAdd` values. The server follows Airsonic (`SubsonicRESTController.updatePlaylist`), Navidrome (`core/playlists`) and gonic. Every `songIndexToRemove` is the position of a song in the playlist as it is before the request, counted from 0. The entries at these positions are removed, which gives the list that is left when they are removed one by one from the highest position to the lowest. The order of the values changes nothing, and a position that is named twice removes one entry, as in Airsonic and Navidrome. Then one entry for each `songIdToAdd` is appended, in the order of the values. A position therefore never names a song that the same request adds.
- Errors of the parameters: a required `id` or `playlistId` that is absent is error 10. A value that is the ID of no playlist of the user is error 70. A `songId` or a `songIdToAdd` that is the ID of no track row is error 70. That includes a value without the shape of an ID (§3.3), an empty value and the ID of an item of another kind: the handler checks each value with `ids::parse` before a statement runs. A `songIndexToRemove` that is not the position of an entry is error 0 with a message that names the parameter: a value that is no integer, a negative one, and a position at or after the end of the playlist. The reference servers do not agree on that case: Navidrome deletes the rows that have the named positions, so such a position removes nothing, and Airsonic fails after it stored the name. An empty `songIndexToRemove` counts as absent, as an empty value of every parameter that holds a number does (§3.8).
- A playlist holds at most 100 000 entries (`playlists::MAX_ENTRIES`). A list of that many track IDs is a form body of about 4.4 MB, which the form body limit of 8 MiB admits (§3.8). A request with more `songId` or `songIdToAdd` values, and an `updatePlaylist` request after which the playlist would be longer, is error 0 with the message `a playlist holds at most 100000 songs`. The values are counted before they are read. The limit bounds the rows that one request writes and the rows that one request reads.
- A request changes everything it names or nothing. `playlists::create`, `playlists::replace_tracks` and `playlists::update` each run in one `IMMEDIATE` transaction and check the playlist, the positions, the length and the tracks, in that order, before the first write. After an error, and after a write that failed, the name, the comment, `public`, `changed` and every entry are those from before the request. `deletePlaylist` is one statement, and the entries go with the playlist row (`ON DELETE CASCADE`). The time of a write is read once the write connection is held. An `updatePlaylist` request that names nothing to change writes nothing and keeps `changed`.
- An entry is a row of `playlist_tracks`, and the entries of a playlist are its rows in the order of `position`. The position of an entry in the API is its place in that order. A write of the entries stores them at the positions 0 to n − 1. A request that only adds songs to rows without a gap inserts the new rows and leaves the others; every other change of the entries writes the kept rows again. Every value of a request is a parameter of a statement, and a list of track IDs is one JSON array (§3.8).
- Entries and the scan: a scan keeps the ID of a track through a rename and a move of its file (§1.3) and writes no row of `playlist_tracks`, so a playlist keeps its entries and their order. A track without a file keeps its entries and is listed without `path` (§3.4); it is added and removed as every other track. When a scan deletes the track row (§3.10 step 5), the entries of the track are deleted with it (§3.4). The other entries keep their order, and `songCount`, `duration` and the positions of the API follow the entries that are left. The `position` column has a gap from that scan until the next write of the entries of the playlist.
- Each handler that reads runs its statements in one read transaction, so `songCount` and `duration` agree with the `entry` list. A database that cannot be read is error 0 with the message `the server cannot read its playlists`, and one that cannot be written is error 0 with the message `the server cannot store the playlist`.

Play queue methods (`api/queue.rs`): `getPlayQueue` and `savePlayQueue`. A client saves its queue, the current song and the position within that song, and a client on another device reads them to go on from there. The handlers read and write the `play_queue` and `play_queue_tracks` tables with `db::queries::play_queue`. They read the songs with `browse::tracks_by_ids` and the annotations of the user with `annotations::get_many`, and they build each song with `model::child` (§3.8). The `playQueue` element is a type of the handler module, because no other module returns it. Parameters and responses follow the OpenSubsonic pages of the two methods (https://opensubsonic.netlify.app/docs/endpoints/saveplayqueue/, https://opensubsonic.netlify.app/docs/endpoints/getplayqueue/) and of the `playQueue` response (https://opensubsonic.netlify.app/docs/responses/playqueue/), with their errata, and the Subsonic 1.16.1 schema.

- A user has one queue: `user_id` is the key of the `play_queue` table. Every query takes the ID of the user of the request and reads or writes the rows of that user only, so no user reads or replaces the queue of another user.
- `getPlayQueue` reads no parameter. It returns `playQueue` with `current`, `position`, `username`, `changed`, `changedBy` and the `entry` list: the `Child` element of the song of each entry, with the annotation of the user, in the order of the entries. A song with two entries is listed twice. `current` is the ID of the current song as text, which is the form of the OpenSubsonic API; the Subsonic schema declares an integer. `position` is the position within the current song in milliseconds. `username` is the name of the account. `changed` is the time of the last request that saved the queue, in the form of §3.8, and `changedBy` is the `c` value of that request, cut to the 64 characters that the request log holds of it (§3.8).
- The answer always holds `playQueue`, also for a queue without a song. Such a queue has `username`, `changed`, `changedBy` and `position: 0`. It has no `current`, and its `entry` list is `[]` in JSON and absent in XML. The OpenSubsonic API requires the element and its fields `username`, `changed` and `changedBy`. The Subsonic API 1.16.1 answers with the empty response when no queue was saved, and Airsonic and gonic do so. Navidrome sends the element. Feishin reads the fields of the element without a check, so it fails on the empty response. For a user that saved no queue, `changed` is the creation time of the account and `changedBy` is empty: the queue has had no song since the account exists, and no client changed it.
- `savePlayQueue` replaces the queue and returns the empty response. `id` may occur any number of times. The queue gets one entry for each value, in the order of the values, and a song that is named twice is in the queue twice. `position` is 0 without a value. The request stores its `c` value and its time, which is read once the write connection is held.
- A request without `id` and without `current` stores a queue without a song. The OpenSubsonic API defines that request. The Subsonic API 1.16.1 requires `id`, and gonic answers error 10. The request is a change of the queue, so `changed` and `changedBy` are those of that request. Its `position` is checked and not stored.
- A request with `id` values and without `current` is accepted. It stores a queue with those songs, in the order of the values, and with no current song. An empty `current` counts as absent. The stored position is 0: `position` is a position within the current song, so the `position` of such a request is checked and not stored. Supersonic sends this request while its queue holds songs and none of them is loaded, which is its state after a stop and after songs were added to a queue that has not played. The `savePlayQueue` page of the OpenSubsonic API requires `current` unless the request has no `id`, so the server accepts a request that the page tells it to reject. A server that follows the page answers error 10, and it then does not store the queue that Supersonic sends. Navidrome accepts the request as well.
- `getPlayQueue` returns a queue that was saved without `current` with the song of its first entry as `current` and with `position: 0`. The `playQueue` response of the OpenSubsonic API says that a server must send a `current` that is the ID of a song of `entry` when `entry` is not empty. Navidrome answers such a queue in the same way, so a client that was tested against Navidrome gets the answer it expects. The server stores no current song for the queue: `play_queue::get` names the first entry when the queue is read.
- A `current` that is present must be one of the `id` values. Another value is error 0 with a message that names the parameter, also in a request without `id`. The server takes no other song in its place. Airsonic answers error 0 for such a `current` as well. Navidrome takes the first song.
- A value of `id` that is the ID of no track row is error 70. That includes a value without the shape of an ID (§3.3), an empty value and the ID of an item of another kind: the handler checks each value with `ids::parse` before a statement runs. A `position` that is no integer from 0 to 9223372036854775807 is error 0. The value is not compared with the duration of the song. The handler checks the number of the `id` values, their shape, the `current` value and the `position`, in that order, in a request with `current` and in a request without it.
- A queue holds at most 100 000 entries (`play_queue::MAX_ENTRIES`), as a playlist does. A request with more `id` values is error 0 with the message `a play queue holds at most 100000 songs`. The values are counted before they are read. The limit bounds the rows that one request writes and the rows that one request reads.
- A request changes the whole queue or nothing. `play_queue::replace`, `play_queue::replace_without_current` and `play_queue::clear` each run in one `IMMEDIATE` transaction. `replace` checks the number of the IDs, the current song and the tracks, in that order, before its first write, and `replace_without_current` checks the number of the IDs and the tracks. After an error, and after a write that failed, the songs, the current song, the position, `changed` and `changedBy` are those from before the request. Two requests at the same time write one after the other, and the queue of the later one is stored whole. `getPlayQueue` runs its statements in one read transaction, so its answer is the queue of one request. Every value of a request is a parameter of a statement, and the list of track IDs is one JSON array (§3.8).
- An entry is a row of `play_queue_tracks`, and the entries of a queue are its rows in the order of `position`. `replace` stores the entry of the current song at position 0, the entries before it at −1, −2 and so on, and the entries after it at 1, 2 and so on. `current` is an ID, and a queue can hold that song several times; its first entry is the one at position 0. `play_queue.current_id` holds the ID and has no foreign key. The schema has no column for the place of the current entry, and the stored positions hold it. `replace_without_current` stores a queue without a current song: `current_id` has no value, and the entries are at the positions 1 to n. No entry of such a queue is at position 0, which is the place of the entry of a stored current song. A queue with entries has no value in `current_id` in that state only, because `replace` always stores an ID and `clear` stores no entry.
- The queue and the scan: a scan keeps the ID of a track through a rename and a move of its file (§1.3) and writes no row of the two tables, so the queue keeps its entries, their order, the current song, the position, `changed` and `changedBy`. A track without a file keeps its entries and is listed without `path` (§3.4); a request saves it, also as the current song, as every other track. When a scan deletes the track row (§3.10 step 5), the entries of the track are deleted with it (§3.4). The other entries keep their positions and so their order, and `changed` and `changedBy` stay.
- When the deleted track was the current song, `current_id` names no entry. `getPlayQueue` then returns as `current` the song of the entry that followed the deleted one, which is the first entry at a position above 0, and the song of the last entry when none followed. `position` is 0, because the stored value is a position within the deleted track. A queue with a song therefore always has a `current` that is one of its songs, and the listener goes on at the place in the queue where the deleted song was. A queue whose tracks are all deleted is a queue without a song. The scan writes no row for any of this, and the next `savePlayQueue` stores a queue as before. A `savePlayQueue` request that still names the deleted song is error 70 and leaves the queue as the scan left it.
- A queue whose current track was deleted and a queue that was saved without `current` are two states, and the `play_queue` row tells them apart. The first has the ID of the deleted track in `current_id`, and `getPlayQueue` returns as `current` the song that followed the deleted one, or the last song when none followed, with `position: 0`. The second has no value in `current_id`, and `getPlayQueue` returns its first song as `current`, with `position: 0`. `play_queue::get` reads `current_id` before it reads the positions. The two states differ in the stored positions as well: the entries of the first lie around position 0, the place of the deleted song, and the entries of the second are at 1 and above. The two answers therefore differ for the same songs: when a scan deletes the third of four songs, a queue that had it as the current song holds the other three at −2, −1 and 1 and has the fourth song as `current`, and a queue that was saved without `current` holds them at 1, 2 and 4 and has the first. A queue that was saved without `current` stays in that state when a scan deletes one of its tracks: the entries that are left keep their order, and the first of them is the current song.
- A database that cannot be read is error 0 with the message `the server cannot read its play queue`, and one that cannot be written is error 0 with the message `the server cannot store the play queue`.

Lyrics methods (`api/lyrics.rs`): the server has no lyrics in version 1 (§1.3). `getLyrics` and `getLyricsBySongId` answer every song as a server answers a song without lyrics: with a success that holds none. A client that asks for the lyrics of a song shows none and reports no error. No handler opens a file.

- `getLyrics` returns `lyrics` with the one field `value`, whose text is empty: `"lyrics":{"value":""}` in JSON and `<lyrics></lyrics>` in XML. The handler reads neither `artist` nor `title`, so the answer is the same for every request that has a user. Subsonic 1.16.1 returns an empty `lyrics` element when it finds no lyrics, and its schema gives the element text content and the optional attributes `artist` and `title`. The OpenSubsonic API requires `value`, the text of the lyrics, so the JSON element holds it. Navidrome answers a song without lyrics with the same element in both formats.
- `getLyricsBySongId` requires `id`, the ID of a track, and returns `lyricsList` without a field: `"lyricsList":{}` in JSON and `<lyricsList/>` in XML. `structuredLyrics`, the one field of the element, is optional in the OpenSubsonic API, and Navidrome leaves it out for a song without lyrics. `enhanced`, the parameter of version 2 of the extension, is not read.
- Errors of `getLyricsBySongId`: an absent `id` is error 10. Error 70 answers a value that is the ID of no track: a track ID that no row has, the ID of an item of another kind, an empty value and a value without the shape of an ID (§3.3). The handler finds the last three with `ids::parse`, before a statement runs. The OpenSubsonic page of the method names `id` as required and names no error. The two codes are those of the OpenSubsonic error table for a missing parameter and for data that is not found, and Navidrome and gonic answer with them. A database that cannot be read is error 0 with the message `the server cannot read its library`.
- A track without a file (§3.4) has a row, so its ID is the ID of a song, and `getLyricsBySongId` returns the empty `lyricsList` for it.
- `getOpenSubsonicExtensions` does not list `songLyrics`, the extension that `getLyricsBySongId` belongs to. The server answers the method for the clients that call it without the extension, and it advertises no lyrics.
- Both methods need a user, as every method that is not public does (§3.7).

Media methods (`api/media.rs`): `stream` returns the track `id` as its original file, unchanged and with the content type of the track row, or as a transcode to Opus or MP3 (§3.9). It answers GET, HEAD and POST. A success is the bytes of the file or of the transcode and no envelope; an error is the envelope (§3.8).

- `id` is required, and an absent one is error 10. Error 70 answers a value that is no track ID (§3.3), an ID that no track has, a track without a file (§3.4), a file that is gone, a file outside the configured music folders and a file that changed since the scan. The answer is the same for a request that selects a transcode, and no process starts for it.
- The handler reads the track and the path of its file, calls `decide` and answers `Raw` with `media::stream::raw` and `AppState.streams`, and `Transcode` with `media::stream::transcoded` and `AppState.transcoder`. `timeOffset` has an effect on a transcode only, and `estimateContentLength` has none on either answer. A `format` that names no target is read as no `format`.
- HTTP 503 with `Retry-After: 5` and an empty body answers a request that gets no slot within 5 s: a transcode request while `transcoding.max_concurrent` transcodes run, and a request for an original file while the responses of `stream` hold 64 files open (§3.9). It is the one response of the API that is neither HTTP 200 nor a response of the file service. A client repeats the request after 5 s. A HEAD request, HTTP 304 and HTTP 416 need no slot.
- A `Range` header in a unit other than `bytes` is ignored, and the response is the whole file with HTTP 200 (RFC 9110 section 14.2).
- A transcode request gets error 0 with the message `ffmpeg not available` on a server whose ffmpeg does not run or lacks the encoder of the format, and error 0 with the message `ffmpeg produced no output` when ffmpeg ends without output or writes none within 10 s. A transcoded stream whose client takes no chunk for 10 minutes ends, and the connection ends without the end of the body.
- `stream` counts no play. `scrobble` does (§1.3).

Cover method (`api/covers.rs`): `getCoverArt` answers with the bytes of an image and not with the envelope (§3.8). The handler checks the form of `id` and `size` and calls `Covers::get` (§3.11). The service resolves the ID through the database, and it owns the steps of the size, the limits on the bytes of a source and on the memory of a decoded image, the rule for symbolic links and the rule for the music folders. The handler builds no path and opens no file.

- `id` is required, and an absent one is error 10. It is the ID of an album or of a track, which is what the `coverArt` of an album and of a song holds (§3.8). The `coverArt` of a playlist is the one of its first song, so it is such an ID as well. `size` is an integer from 0 to 4294967295. An empty value counts as absent, and any other value is error 0 that names the parameter (§3.8): a negative number, a number with a fraction, a larger number and text. The parameters are checked in this order: `id` is present, `size` is an integer, `id` has the form of an ID.
- Error 70 answers every request for which the server has no cover: a value that `ids::parse` rejects, an ID that no row has, the ID of an artist or of a playlist, an album without a cover, a track without an embedded picture or without a file (§3.4), and a source that the service does not serve, among them a source outside the configured music folders (§3.11). The server has no placeholder image and no artist image (§1.3). The OpenSubsonic API names no answer for an item without a cover. Navidrome sends a placeholder image for such an item.
- A cover is HTTP 200 with the bytes that the service returned, the `Content-Type` that the service reported, `Content-Length`, `Cache-Control: public, max-age=86400` and an `ETag`. The entity tag of the image as it is stored is `"<id>-0-<cover_mtime>"`. The entity tag of a resized cover is `"<id>-<step>-<cover_mtime>-<version>"`. `<step>` is the step of `size` (`covers::served_size`, §3.11), which is 320 for the sizes 161 to 320 and 2000 for every size over 1280. `<version>` is the version of the resized covers (`covers::CACHE_VERSION`, §3.11). The four parts are the ones in the name of the cache file (§3.11), so two requests that get the same bytes have the same entity tag, and a client that holds the cover of one size gets HTTP 304 for every size of that step. A resized cover that another version of the server made has another entity tag, so a client that holds it gets the cover and not HTTP 304. The response has no `Last-Modified`.
- A request whose `If-None-Match` names the entity tag of the cover gets HTTP 304 with `Cache-Control` and `ETag`, without a body and without `Content-Type`. The header holds a list of entity tags or `*`, and a weak tag (`W/`) names the cover as well (RFC 9110 section 13.1.2). The handler reads the cover before it compares the header, because `Covers::get` returns the modification time with the cover. A conditional request therefore reads the cache file, or the source and its header, and a cover that is gone is error 70 for it as well. `Range`, `If-Range`, `If-Match` and `If-Modified-Since` are not read: the answer is the whole cover.
- The request is a GET, a HEAD or a POST with a form body, and the method changes nothing in the answer. The router removes the body of the answer to a HEAD request (§3.8).
- An error is the envelope in the format of the request, with HTTP 200 and without the cache headers. A database that cannot be read is error 0 with the message `the server cannot read its library`. Work on a cover that ended without a result (`CoverError::Unfinished`) is error 0 with the message `the server did not finish the cover`.
- The handler awaits `Covers::get` in the future of the request and starts no task. A client that disconnects drops that future. A request for a stored image then leaves the queue of the service, and a resized cover that waits for its turn is not made (§3.11).
- Present limit: the entity tag holds the modification time that the last scan stored, and a cover without `size` is read from the file as it is now. An image file that is replaced after the last scan is served under the old entity tag until the next scan, and a client that holds the old image gets HTTP 304 for that time. A cover that is replaced by an image with the same modification time keeps its entity tag after the scan as well.

User methods (`api/users.rs`): the server has one account, so `getUser` and `getUsers` return the user of the request. `getUser` requires `username`, and an absent one is error 10. The value is compared with the name of the user of the request without regard to ASCII case, as the lookup of an account is (§3.7). Another name is error 50 with the message `username must be the name of the user of the request`, whether an account has that name or not. With `auth.disabled_unsafe = true` every name returns the owner. `getUsers` returns `users`, whose `user` list holds that one user. The `user` element holds `username` (the stored name); `scrobblingEnabled`, `adminRole`, `playlistRole` and `streamRole` as `true`; `settingsRole`, `downloadRole`, `uploadRole`, `coverArtRole`, `commentRole`, `podcastRole`, `jukeboxRole`, `shareRole` and `videoConversionRole` as `false`; and `folder`, the IDs of the rows of the `folders` table in ID order. It has no `email`.

Scan methods (`api/scan.rs`): `startScan` and `getScanStatus` return the `scanStatus` element with `scanning` and `count` (https://opensubsonic.netlify.app/docs/responses/scanstatus/). Both describe the scans of the server process (§3.10).

- `count` is the number of supported files that the running scan has finished with. When no scan runs, it is the number of the scan of the server process that ended last, and 0 before the first one.
- `startScan` takes `fullScan`, which is `true` or `false` in any letter case; another value is error 0 and starts no scan. The method follows the trigger table of §3.10 and returns without waiting for the scan. Its answer has `scanning: true` when it started a scan and when it found a scan of the server running.
- `getScanStatus` adds `lastScan`: the end time of the scan that ended last, as ISO-8601 in UTC with seconds (`2026-10-11T08:15:30Z`). `lastScan` is not part of the OpenSubsonic response. Navidrome sends it, and it is here for the clients that read it. It is the latest `finished_at` of the `scans` table, formatted by SQLite, so it counts a scan that ended with errors, a cancelled scan, a scan of `wn-server scan` and a scan from before the server started. It is absent until a scan has ended.
- A scan that recorded errors is no API error. `getScanStatus` answers `ok` with `scanning: false`, the count of that scan and its end time as `lastScan`.

`download` and the stubs (`api/stubs.rs`): a handler of that module takes no argument. It reads no parameter, no state and no file, so its answer is the same for every request that has a user. A request without a user gets the authentication error (§3.7).

- `download` returns error 50 with the message `download is disabled on this server`. The response is the error envelope and never holds a byte of a file.
- An empty result is an object without fields under the key of the method: `getArtistInfo` → `artistInfo`, `getArtistInfo2` → `artistInfo2`, `getAlbumInfo` and `getAlbumInfo2` → `albumInfo`, `getSimilarSongs` → `similarSongs`, `getSimilarSongs2` → `similarSongs2`, `getTopSongs` → `topSongs`.
- An empty list is an object whose one field is an empty list, which is `[]` in JSON and absent in XML: `getNowPlaying` → `nowPlaying` with `entry`, `getShares` → `shares` with `share`, `getPodcasts` → `podcasts` with `channel`, `getNewestPodcasts` → `newestPodcasts` with `episode`, `getInternetRadioStations` → `internetRadioStations` with `internetRadioStation`, `getBookmarks` → `bookmarks` with `bookmark`. The OpenSubsonic API marks `entry` as required and the other lists as optional.
- `getAvatar` returns error 70.
- `createUser`, `updateUser`, `deleteUser` and `changePassword` return error 50 with the message `user management is not available on this server`. The `wn-server user` commands manage the account.
