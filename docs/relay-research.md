# Waxnerd Relay: research notes

Written 2026-10-18 for the design in [relay.md](relay.md). Each item answers a question of the planning prompt with evidence from the code, the documents, or the web. A claim marked "unverified" was not checked against a source. File references are to wn-server unless they name `../v2` (wn-cloud) or `../navidrome`.

## 1. Tunnel transport

A subagent compared the options on 2026-10-18 from library sources in the Go module cache and the vendors' documentation. Its full report with source references is not in the repository; the facts that matter are here. "Unverified" marks a claim that was not checked against a primary source.

Cluster facts that affect every option: `waxnerd.com` DNS is at Cloudflare (`dig NS waxnerd.com` answers Cloudflare name servers). `v2.waxnerd.com` resolves to addresses in Cloudflare's proxy ranges, so the site is behind Cloudflare's proxy today (range membership unverified). Cloudflare's Universal SSL covers only first-level subdomains, so `<id>.relay.waxnerd.com` behind the proxy would need Advanced Certificate Manager. Cloudflare's CDN terms for Free, Pro, and Business say that serving a disproportionate share of audio or other large files without the paid services may be limited. Both facts say the relay records must be DNS-only records pointing at the VPS address, not proxied. Let's Encrypt issues wildcard certificates with DNS-01 only; cert-manager's Cloudflare solver takes an API token with `Zone:DNS:Edit` and `Zone:Zone:Read`. k3s ships Traefik v3; its entrypoint defaults are `readTimeout` 60 s, `writeTimeout` 0, `idleTimeout` 180 s; whether the read timeout cuts a long-lived passthrough or WebSocket connection is unverified and needs a test.

Prior art: chisel runs SSH over a WebSocket; frp multiplexes with a yamux fork over TCP, KCP, QUIC, or WebSocket; rathole uses TCP, TLS, Noise, or WebSocket with one data channel per visitor connection (unverified); cloudflared runs QUIC with an HTTP/2 fallback, and in HTTP/2 mode it calls `http2.Server.ServeConn` on the connection it dialed, so Cloudflare's edge is the HTTP/2 client (reversed HTTP/2).

Capacity: one tunnel costs one file descriptor and tens of KiB idle. A 2 vCPU, 4 GB host carries thousands of idle tunnels and several hundred concurrent streams; with yamux, 500 concurrent streams bound about 128 MB of window memory. Bandwidth is the binding limit: a 1 Gbit/s port (unverified) carries about 3,000 streams at 320 kbps or about 1,000 lossless streams. Reference egress prices: Hetzner Cloud includes 20 TB per month and charges about €1 per TB beyond (2026 rate unverified); DigitalOcean charges $0.01 per GiB beyond the plan's allowance. For scale: 200 servers at 2 hours of 320 kbps a day is about 1.7 TB per month; lossless about 5.4 TB.

TCP alone detects a silent drop only after the kernel's retransmission limit, about 15 minutes (unverified), so every option needs an application keepalive. After a drop a Subsonic `download` resumes with a `Range` request; a transcoded `stream` has no fixed byte offsets and resumption is client-specific (unverified).

Handshake sketch for option 1: wn-server dials TLS to `connect.relay.waxnerd.com:443` with ALPN `http/1.1`, verifies the certificate against system roots, and sends one HTTP/1.1 request before any multiplexing: `GET /v1/tunnel` with `Authorization: Bearer <server credential>`, `Upgrade: wn-relay/1`, `Connection: Upgrade`, `Wn-Server-Id: <server id>`, and `Wn-Server-Version`. The edge checks the bearer as v2 checks any CLI token, checks that the token's user owns the server, and checks the relay entitlement. It answers 401, 403, 402, or 409 with a JSON error and closes, or `101 Switching Protocols` with `Wn-Relay-Host` and `Wn-Relay-Session`. After 101 both sides start yamux on the same connection: the edge is the yamux client and opens streams, wn-server is the yamux server and calls `http.Server.Serve(session)`. The edge keeps `server id → session` in memory; a second tunnel for the same server replaces the first, which covers a home IP change that leaves a stale connection. The edge re-checks the credential and the entitlement every few minutes and closes the session when either fails. wn-server reconnects with exponential backoff and jitter; a 401 or 403 stops reconnecting until the credential or the setting changes; a 402 retries slowly.

More than one edge replica: a Postgres registry (`server_id`, pod IP, session id, `connected_at`) with forwarding between pods, or one replica. Sticky routing at Traefik cannot route a public request to the replica that holds a given tunnel. One replica matches the single-node cluster; a restart drops every tunnel and they reconnect within seconds.

Recommendation: option 1a, yamux over one outbound TLS connection, with a custom Go edge in the cluster, one replica, DNS-only records, a DNS-01 wildcard certificate, and TLS passthrough at Traefik on 443. It keeps wn-server's `http.Server` unchanged, bounds edge memory per slow client, gives a known detection time, and its handshake reuses the CLI token check. Reversed HTTP/2 is the second choice and needs a prototype first. WebSocket is only needed if the tunnel must cross an HTTP-terminating proxy. Cloudflare Tunnel and Tailscale Funnel move host names, limits, and terms to a vendor, give wn-cloud no per-connection gate, and conflict with the no-agent rule or the no-extra-account goal.

## 2. Public addressing

Two forms were compared: a host per server (`<server id>.relay.waxnerd.com`) and a path prefix on one host (`relay.waxnerd.com/s/<server id>/`).

Host per server, what stays unchanged in wn-server:

- The web UI cookie `wn_session` has no `Domain` attribute and `Path=/ui/` (`internal/web/web.go`, `setCookie`), so the browser scopes it to one host. Two servers reached through the relay have two cookie jars with no change.
- The `Origin` check of the web UI compares the `Origin` header with `r.Host` (`internal/web/web.go`, `checkOrigin`). With one host per server it holds when the relay package hands the request over with the relay host in `r.Host`.
- Every link the web UI renders is an absolute path (`/ui/...`), and `GET /` redirects to `/ui/`. Nothing needs a base path.
- Subsonic clients take a base URL. `https://<id>.relay.waxnerd.com` is a plain base URL with no path.
- Navidrome builds share links from `X-Forwarded-Host` and `X-Forwarded-Proto`, which the proxy sets from its own request (`internal/proxy/proxy.go`, `Rewrite`; `../navidrome/server/middlewares.go`, `ServerAddress`). A relayed request with `r.Host` set to the relay host gives `https://<id>.relay.waxnerd.com/share/<share id>`. Navidrome's `BasePath` is one value for the process, not per request (`../navidrome/conf/configuration.go`, `BasePath`).

Host per server, what it costs: a wildcard DNS record `*.relay.waxnerd.com` and a wildcard certificate. Let's Encrypt issues wildcard certificates through the DNS-01 challenge only; the cluster's issuer uses HTTP-01 through Traefik (`../v2/deploy/cluster/cluster-issuer.yaml`). DNS-01 needs an API credential of the DNS provider in the cluster. The DNS of `waxnerd.com` is at Cloudflare (item 1). cert-manager supports Cloudflare DNS-01 with an API token. The relay records must be DNS-only, not proxied (item 1). A server id is a UUID of 36 characters, which fits a DNS label (63 characters at most). A shorter label assigned by wn-cloud is possible and is a decision for the owner.

Path prefix, what it saves: one host name and one ordinary certificate from the existing HTTP-01 issuer. No wildcard DNS, no DNS-01 credential.

Path prefix, what it costs in wn-server:

- A base-path setting through the web UI: every rendered link, every redirect, the cookie `Path`, and the `GET /` redirect. The cookie name would also need the server id in it, because two servers on one host would share one cookie jar and both set `wn_session`.
- The proxy would strip the prefix before routing and Navidrome would have to be told the prefix for share links. `BasePath` is process-wide, so Navidrome would run with `BasePath=/s/<id>` for every request, including LAN requests, or the proxy would rewrite share URLs in response bodies.
- Subsonic clients mostly accept a base URL with a path, but the Navidrome share page assets are served under `/share/*` with absolute paths (`../navidrome/server/public/public.go`, `assetsHandler`), which breaks under a prefix without `BasePath`.
- One host for every server means one `Origin` for every server. The web UI's `Origin` check would still pass, and a page of one server could post forms to another server on the same origin. The session cookie would prevent harm, but the isolation that separate hosts give for free would be gone.

Conclusion: host per server. The cost is in the cluster (wildcard DNS and DNS-01), not in wn-server. See the decisions list in `relay.md`.

## 3. The web UI and the proxy behind the relay

Facts from the code:

- `internal/web/web.go` sets `Secure` on the cookie when `r.TLS != nil` (`setCookie`, `clearCookie`). `internal/proxy/proxy.go` sets `X-Forwarded-Proto` from `r.In.TLS` and `X-Forwarded-Host` from `r.In.Host`. These are the only two reads of `r.TLS`.
- The client address is read in `remoteHost` in `internal/proxy/session.go` and `internal/web/web.go` (`r.RemoteAddr` without the port). It keys the three limiters: failed device code exchanges (5 per address, 10 total per 10 minutes), failed Subsonic password checks (10 per address per minute, `internal/proxy/loginlimit.go`), and failed web sign-ins (10 per address, 100 total per 10 minutes). Log lines carry `remote` from `r.RemoteAddr` (`internal/proxy/subsonic.go`).
- The proxy strips `Forwarded` and every `X-Forwarded-*` header from incoming requests before forwarding (`internal/proxy/proxy.go`). No code reads them.
- `SameSite=Lax` on the cookie is unchanged by the relay: the browser sends it on top-level navigations and same-site requests to `<id>.relay.waxnerd.com`. Lax is the right value for a form-based UI.
- The `Origin` check needs `r.Host` to be the host the browser used. The edge receives the request with `Host: <id>.relay.waxnerd.com` and forwards it unchanged; the relay package builds the in-process request with that host.
- The web UI emits no absolute URLs with a scheme. Share links are built by Navidrome from `X-Forwarded-Host` and `X-Forwarded-Proto`.

What a relayed request needs, and the proposed mechanism:

1. **A TLS-terminated mark.** The relay package builds each request in process. It stores a value in the request context through a small stdlib-only package, `internal/relayreq`, with `WithRelay(ctx, clientAddr string) context.Context`, `IsRelayed(ctx) bool`, and `ClientAddr(r *http.Request) string`. The two `r.TLS != nil` reads become `r.TLS != nil || relayreq.IsRelayed(r.Context())`. Only in-process code can set a context value, so no header from any client can set the mark. The LAN path never calls `WithRelay`. Alternative considered: the relay package sets a synthetic `r.TLS = &tls.ConnectionState{}` on the request, which leaves both reads unchanged. It is rejected because `r.TLS` would then lie about the connection, and any later code that reads cipher or certificate fields would see zero values.
2. **The client address.** The edge is the only writer down the tunnel. It puts the client's IP address in a header on the tunneled request (`X-Relay-Client`). The relay package reads that header, deletes it, and stores the address with `WithRelay`. The mark is a context value, so a LAN client that sends the header sets nothing; a new step in the LAN handler deletes the header so it reaches neither the logs nor Navidrome (today the proxy strips forwarded headers on the outgoing request to Navidrome only, `internal/proxy/proxy.go`, `Rewrite`). `remoteHost` in both packages becomes one helper, `relayreq.ClientAddr(r)`, which returns the relayed address when the mark is set and `r.RemoteAddr` without the port otherwise. The limiters and the log lines call it. The log line of a relayed request also carries `relay=true`.
3. **Forwarded headers.** The edge sends `X-Relay-Client` and nothing else. wn-server trusts no `X-Forwarded-*` header from any path. The proxy keeps stripping them. `X-Forwarded-Host` and `X-Forwarded-Proto` toward Navidrome come from `r.Host` and the mark, as today.
4. **The limits.** Through an edge that checks nothing per request, the shared total of 10 failed device code exchanges per 10 minutes lets anyone who finds the relay host lock the owner's own exchanges, and the per-address limits are only as good as the forwarded address. Measures, in `relay.md` section 9: separate budgets for relayed and LAN requests on every limiter with a total; a per-client-address rate limit at the edge; and in v1 `POST /api/v1/session` is refused through the relay with 403 `not_available`, because no first-party client exists yet and the web UI signs in with the app password. The split of the total of 10 between LAN and relay is a decision for the owner.

## 4. What passes

wn-server's router (`internal/proxy/proxy.go`) answers 404 to every path except `/rest/*`, `/share/*`, `/api/v1/*`, `/` and `/ui/*`. Navidrome's native API (`/api/*`), its web UI (`/app/*`), and its server-sent events route (`/api/events`, `../navidrome/server/server.go`) are not reachable through wn-server on the LAN today, and a relayed request goes through the same router, so they are not reachable through the relay either. Navidrome has no WebSocket route (grep of `../navidrome/server` finds SSE only).

`/share/*` is public in Navidrome: the share page, `/share/img/<id>`, the stream `/share/s/<id>` with a signed token, the download `/share/d/<id>`, and the m3u (`../navidrome/server/public/public.go`). The proxy passes it without a check today, and that holds through the relay. A share link made through the relay is reachable by anyone with the link, which is what a share is.

Does the edge need its own allowlist? No, for v1. The edge forwards every request for a host down its tunnel, and wn-server's router is the allowlist. Two cheap refusals at the edge are still worth having and need no per-request authentication: a request with `Upgrade` or `Connection: Upgrade` is answered 400 before forwarding, because nothing behind the relay speaks WebSocket; and a request whose method is not GET, HEAD, POST, PUT, or DELETE is answered 405. Non-HTTP traffic never reaches the edge handler because the edge speaks HTTPS only. A request body limit at the edge (1 MiB; the largest legitimate body is a JSON rating or a form post) keeps a client from streaming data into the home machine.

## 5. Abuse and limits

What the caps protect:

- **Egress cost.** Every relayed byte leaves the cluster once, from the edge to the client. The home upload to the edge is ingress, which VPS providers do not bill (unverified for the provider in use; see item 1 for reference prices). One stream at 320 kbps is 144 MB per hour. A listener who streams 4 hours a day for a month moves about 17 GB.
- **Load on the home server.** A home upload link is often 10 to 50 Mbps. Six concurrent 320 kbps streams use 2 Mbps. Six concurrent raw FLAC streams use 6 Mbps. Transcoding costs one ffmpeg process per stream.
- **The private sharing framing.** A member cap keeps a server from becoming a public service. The edge cannot count identities. wn-cloud enforces the member cap when an invite is accepted, in the phase after v1.

Proposed numbers, for the owner to confirm:

| Cap | Where enforced | Proposed value | What happens at the cap |
|---|---|---|---|
| Concurrent in-flight requests per server | edge, per tunnel | 32 | 429 with `Retry-After: 2` |
| Concurrent audio responses per server | edge, per tunnel, counted by response `Content-Type` `audio/*` | 6 | 429 |
| Egress per server per month | edge, bytes written to clients per tunnel, persisted to Postgres | 200 GB soft, 300 GB hard | Soft: wn-cloud shows a warning on the server page. Hard: the edge answers 503 `egress_cap` to audio responses until the month ends; the web UI and API still pass |
| Request body | edge | 1 MiB | 413 |
| Requests per client IP | edge, all servers | 600 per minute | 429 |
| Listeners per server, the owner not counted | wn-cloud, at invite creation and acceptance (after v1) | 12 (from WAX-936) | The invite is refused |

The edge reads the response `Content-Type` and counts bytes, which is not an authentication check. It never reads the query string for the caps.

Bitrate. Navidrome applies a transcoding ceiling per player (`../navidrome/server/subsonic/transcode.go`, `player.MaxBitRate`), and a player is found by user, client name `c`, and user agent (`../navidrome/core/players.go`, `FindMatch`). The `stream` call also takes `maxBitRate` as a request parameter (`../navidrome/server/subsonic/stream.go`). Two ways for wn-server to cap relayed streams:

- (a) Rewrite the query: on a relayed `/rest/stream`, set `maxBitRate` to the cap when the parameter is absent or higher. One line in the proxy, no player state. `download` is not transcoded by default and is not capped this way. A client that sends `format=raw` is not transcoded by Navidrome; the proxy can drop `format=raw` on relayed requests.
- (b) Give relayed requests their own Navidrome player by appending ` (relay)` to the `c` parameter, then set that player's `maxBitRate` through the native API `PUT /api/player/:id` as wn-server's identity. More moving parts, and the player is created on the first request, so the first stream is uncapped.

Recommendation: (a), with a config key `relay_max_bitrate` in kbps, default 0 (no cap), and the cap off in milestone 1. Whether the default should be 320 is a decision for the owner. A bitrate cap reduces bytes per stream for transcodable formats; it does not limit the transfer rate of a range request.

## 6. Billing hooks

v2 has no payments. `../v2/web/package.json` on `origin/main` lists `cookie`, `eta`, `express`, `htmx.org`, `jose`, `node-pg-migrate`, `pg`, `sharp`, and `typesense`; no payment provider. The README and `deploy/README.md` do not mention payments, subscriptions, or billing.

Where the subscription state lives: two columns on `servers`, `relay_enabled boolean not null default false` and `relay_until timestamptz null`. Relay is on when `relay_enabled` is true and `relay_until` is null or in the future. Whatever grants the entitlement writes the columns: in v1 an operator runs an SQL statement; later a provider's webhook handler writes them, and a `subscriptions` table can be added at that time without changing the edge. Keeping the gate on `servers` keeps the edge's handshake query to one row.

What happens when payment lapses: the gate is at connect time, because the edge has no per-request check. The edge checks the columns at every handshake, and a sweep in the edge re-checks every connected tunnel every 10 minutes. After `relay_until` passes, a grace period of 7 days keeps the tunnel open; the sweep closes it after the grace period with a close reason `relay_not_enabled`, and the handshake refuses a reconnect with 402 `relay_not_enabled`. The grace period is a decision for the owner.

What wn-server shows: `wn-server status` and the status page show the relay state as one of `off` (config), `connecting`, `connected since <time> at <host>`, `not enabled at wn-cloud`, `credential rejected`, and `unreachable since <time>`. The last refusal reason from the edge is shown as text.

## 7. The relay package

`internal/relay` in wn-server.

- **Start and stop.** `serve` (`internal/cli/root.go`) builds the proxy handler, then `relay.New(relay.Options{...})` and `go rl.Run(ctx)` next to the supervisor, the outbox drain, and the reconcile loop. `Run` returns when `ctx` ends. On shutdown it closes the tunnel, which ends in-flight relayed requests the way `srv.Shutdown` ends LAN requests. The package starts only when `relay = true` in `config.toml`, and inside `Run` it waits until a server credential exists, so `wn-server login` after start is picked up on the next connect attempt without a restart.
- **Credential and setting.** `Options.Credential` is a function `func() (token, serverID string, ok bool)` that the CLI implements with a store read. The package does not import `internal/store`. `Options.ConnectURL` is a function that returns the edge address. The CLI implements it with a store read of the value cached from `GET /servers/:id` (`relay.connect_url`), or the `relay_edge_url` config key when set. The relay host is not derivable from `wn_cloud_url`.
- **Handing requests over.** `Options.Handler` is the `http.Handler` that `serve` gives to `http.Server`. With the recommended transport (item 1) the package serves the tunneled requests through Go's `net/http` machinery on the tunnel connection, so each request arrives as an ordinary `*http.Request` with a streaming body, `http.Flusher` works, and `Range` and chunked responses pass as on the LAN. Before `ServeHTTP` the package reads `X-Relay-Client`, deletes it, and sets the mark of item 3. No loopback socket, no second listener.
- **Status.** `Options.OnState` is a callback that reports the states of item 6. The CLI wires it to a holder the web UI and `wn-server status` read, in the way `wncloud.Status` is read today.
- **Imports.** The package imports the standard library, the transport library of item 1, and `internal/relayreq` (stdlib only). It does not import `internal/config`, `internal/store`, `internal/proxy`, `internal/web`, or `internal/wncloud`. Everything it needs comes through `Options`. To extract it into its own binary later, the binary would replace `Options.Handler` with a loopback HTTP client to wn-server and `relayreq` would read the client address from a header on that loopback hop. That extraction is not designed here.

## 8. The edge service

Facts about the cluster (`../v2/deploy/README.md`, `deploy/k8s/web.yaml`, `deploy/cluster/cluster-issuer.yaml`, read from `origin/main`): one k3s node, Traefik ingress, cert-manager v1.21.2 with a Let's Encrypt `ClusterIssuer` named `letsencrypt` that solves HTTP-01 through Traefik, a `web` Deployment with 2 replicas and a readiness probe on `/health`, Postgres on a second server over Tailscale, no Redis, firewall open on 22, 80, and 443. Every deployment choice below is for the owner; the design lists them as decisions.

- **Where it runs.** Its own Deployment `relay-edge` in the `waxnerd` namespace, with its own Service, built from a new directory in the v2 repository (`relay/`, in Go, because the transport of item 1 is yamux and no maintained Node implementation exists) and pushed as a third image by the existing pipeline. One replica in v1. It is not part of the `web` Deployment because the tunnels are long-lived connections and a web rollout would drop every tunnel.
- **Exposure.** Two options. (a) Through Traefik: an Ingress with the host `*.relay.waxnerd.com` for client traffic and `connect.relay.waxnerd.com` for the tunnels, TLS from a wildcard certificate Secret, and Traefik passing long-lived connections to the edge. Traefik proxies WebSocket and HTTP/1.1 upgrades without configuration; HTTP/2 to the backend needs the `h2c` scheme on the Service. (b) The edge terminates TLS itself and is exposed with a `hostPort` (443 is taken by Traefik, so 8443, or a second IP). A third option, (c), is TLS passthrough: an `IngressRouteTCP` on Traefik's `websecure` entrypoint with `HostSNI` for the tunnel endpoint and `HostSNIRegexp` for `*.relay.waxnerd.com` and `tls.passthrough`, so the edge terminates TLS itself with the wildcard Secret mounted. The recommended transport (item 1, yamux over raw TLS) cannot pass an HTTP-terminating Traefik, so it needs (b) or (c). (c) needs no firewall change and no second port. Behind (c) the edge's TCP peer is Traefik; the client address needs PROXY protocol from Traefik to the edge (`proxyProtocol` on the `IngressRouteTCP` service) and source address preservation at the k3s ServiceLB (`externalTrafficPolicy: Local` on Traefik's Service), both unverified on this cluster. Traefik's `readTimeout` of 60 s on the entrypoint may or may not cut a passthrough connection (unverified); if it does, it is set to 0 on `websecure` through a k3s `HelmChartConfig`, which affects every site on the entrypoint.
- **Wildcard TLS.** A wildcard needs DNS-01. The cluster needs a second `ClusterIssuer` (or a solver added to the existing one) with the DNS provider's API token in a Secret, and a `Certificate` for `*.relay.waxnerd.com` and `relay.waxnerd.com` in the `waxnerd` namespace. The DNS is at Cloudflare; cert-manager's Cloudflare solver takes an API token with `Zone:DNS:Edit` and `Zone:Zone:Read` on the zone, in a Secret in cert-manager's namespace (unverified for a ClusterIssuer). The alternative, one certificate per server through HTTP-01, needs an Ingress per server or an ACME client in the edge, and runs into Let's Encrypt's limit of 50 certificates per registered domain per week (unverified against the current limits page).
- **Finding the tunnel for a host.** In v1 with one edge replica: a map in the edge process from server id to tunnel. The host name's first label is the server id. Across replicas later: a table `relay_tunnels (server_id, edge_instance, connected_at, last_seen_at)` in Postgres and forwarding between edge instances, or sticky routing by host at Traefik. Not needed with one replica.
- **Shared state with the web replicas.** Postgres only. The edge writes `servers.relay_connected_at` (null when disconnected) and `servers.relay_last_seen_at` on connect, on disconnect, and on every heartbeat (every 60 seconds), and upserts `relay_usage (server_id, month, bytes)` every minute while bytes flow and at response end. The web replicas read those columns for the server page. No Redis.
- **Health reporting.** `servers.relay_last_seen_at` as the prompt's `last_seen_at`. The edge answers `/health` for its readiness probe with the number of tunnels.
- **Metrics the owner sees on wn-cloud.** On the server page: connected or not, last seen, streams in progress (the edge's per-tunnel gauge, written to `servers.relay_streams` on change), and egress this month from `relay_usage`.
- **Logging.** The edge logs one line per request with the time, the server id, the client IP, the method, the path without the query string, the status, the bytes sent, and the duration. It never logs the query string, because Subsonic clients put `p`, `t`, `s`, and `apiKey` in it, and never logs `Authorization` or `Cookie` headers. Error lines carry the server id and the reason, never a token. The handshake log line carries the server id and the user id, never the bearer, in the way `../v2/web/src/servers.ts` logs verify failures.
